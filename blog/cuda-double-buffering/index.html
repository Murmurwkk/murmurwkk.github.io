When Removing Bank Conflicts Made My GEMM Slower

An XOR swizzle took shared-memory bank conflicts on a 1024³ FP32 GEMM to zero and made the kernel 19.5% slower. Bank addressing, double buffering and cp.async, and where the time went.

更新于 2026/11/6 · 8 个章节
#CUDA#GEMM#shared memory#async pipelining#performance experiments

This GEMM taught me one thing very clearly. On 1024³, putting A into shared memory with an ordinary row layout makes eight different addresses land in the same bank. Switching to a 4-element-group XOR swizzle brought Nsight Compute’s extra shared wavefronts from 4,194,304 down to 0, as low as it can go. And the same kernel’s runtime went from 0.30379 ms to 0.36307 ms: 19.5% slower.

This post is a record of that trade. The conflict really was solved, but whether the kernel as a whole got better depends on resources and residency too. The FP32 GEMM here maps one block to 128×64 outputs, with 128 threads, 8×8 accumulation per thread and K advancing 32 at a time. What changes between versions is the shared layout, the number of buffer slots and the copy instructions. All four implementations handle non-aligned matrices, and everything ran on an RTX 5070 Laptop. The tile here differs from the one in the data reuse post, and timings are reported separately.

I also have to stress that my experiments here are pretty rough, and this post doesn’t really qualify as a proper tutorial; it’s mostly a record of my own learning by trial and error. If you find it dull (honestly, putting it back together, I kept feeling I’d agonized over things that didn’t need agonizing over), feel free to skip to the end and look at the question I’m stuck on. I’d be grateful for any pointers.

Here’s the route. We’ll set up the thread mapping, derive the bank conflict from it and fix it with a swizzle, then build up single buffering, double buffering and cp.async, including one initialization bug worth knowing about. After making all of it correct on tails, offsets and grids, we’ll line up four implementations that each differ by one step and look at what the compiler, the profiler and the clock say about each.

The setup: one 128×64 tile, 128 threads

Inputs are contiguous row-major A[M,K]A[M,K]A[M,K] and B[K,N]B[K,N]B[K,N], output C[M,N]=ABC[M,N]=ABC[M,N]=AB. Each K chunk needs a 128×32 slice of A and a 32×64 slice of B, 6144 floats or 24 KiB. These are reused by the block’s four warps, and each thread keeps its 64 partial sums in registers.

int warp = threadIdx.x / 32;
int lane = threadIdx.x % 32;
int mr = (warp / 2) * 64 + (lane / 4) * 8;
int nc = (warp % 2) * 32 + (lane % 4) * 8;

Each thread owns [mr:mr+8,nc:nc+8] within the tile. Lanes 0–3 of warp 0 compute the same eight rows and four different groups of eight columns, together an 8×32 output strip; lanes 4–7 take the next strip. One warp covers 64×32, and four warps in a 2×2 arrangement make exactly 128×64. For a fixed k, the four threads on the same rows need the same group of eight A elements, each with different B. That’s good reuse. But put A into shared memory as plain row*32+k and you hit bank conflicts.

Fundamentals: shared memory banks

For the 32-bit accesses discussed here, think of shared memory as 32 banks, with the word address mod 32 choosing the bank. Different banks serve in parallel; different words in the same bank need extra service; and the same word read by several lanes is broadcast. That last case has to be separated out from “same bank,” or you’ll overestimate conflicts (CUDA shared memory docs).

Fix the row offset i within a thread. A’s address is

r=64⌊warp/2⌋+8⌊lane/4⌋+i,word=32r+k,bank=k mod 32.\begin{aligned} r&=64\lfloor warp/2\rfloor+8\lfloor lane/4\rfloor+i,\\ word&=32r+k,\\ bank&=k\bmod32. \end{aligned}rwordbank​=64⌊warp/2⌋+8⌊lane/4⌋+i,=32r+k,=kmod32.​

All 32 lanes land in the same bank, but each group of four adjacent lanes reads the same A element. After removing broadcast duplicates, eight distinct words are still fighting over one bank. The cause is that the row pitch exactly equals the bank period, so reading across rows never moves to a different bank.

The textbook fix is padding, one extra element per row, to break that period. Here I also wanted to keep 16-byte copies of four adjacent floats, so instead I permuted four-element groups: split each row’s 32 values into eight groups and move only the group positions.

int a_index(int row, int col) {
    int group = (col / 4) ^ ((row / 8) % 8);
    return row * 32 + group * 4 + col % 4;
}

Take col=0: rows 0–7 stay in group 0, rows 8–15 move to group 1, rows 16–23 to group 2. Along the access path through those eight row groups, bank starting points become 0, 4, 8, …, 28. The eight addresses spread out, and the broadcast among adjacent four lanes survives.

Figure 1: Lanes, addresses and banks for the original and swizzled layouts.

For a fixed row, the XOR is a one-to-one permutation of eight groups, so it never drops or overwrites an element, and the four floats within a group stay contiguous for whole-group copies. Producer and consumer must both use a_index; change only the read side and you fetch a different set of numbers, which isn’t an optimized GEMM. B keeps its original layout in these experiments.

Enumerating all four warps, 32 k values and eight row offsets: the original layout puts at most eight distinct words per bank, and the XOR layout one. But that’s scalar address arithmetic. The compiler may merge several scalar reads into wide instructions, and the real shared pipeline may split requests again. So below we check with SASS and Nsight Compute, rather than reading “eight addresses” as “eight times the time.”

Fundamentals: why double buffering needs two slots

With the layout settled, the next step is advancing along K. Single buffering has one copy of the A/B tiles, and the order is rigid:

load K chunk t
block barrier: all inputs written
compute every multiply-add for this chunk
block barrier: all consumers done reading
overwrite the same storage with chunk t+1

The first barrier protects read-after-write and the second write-after-read. CUDA doesn’t keep the four warps in lockstep: one warp finishing early doesn’t mean the others have let go.

With only one copy of storage, even if you know where the next tile is, you can’t write it yet, because the current computation is still reading that space. A second slot lets chunks t and t+1 coexist briefly. The loop loads tile 0, then uses the current slot while preparing the other; once the other is ready and the current one is fully read, the two slots swap roles.

Figure 2: Slot lifetimes under double buffering.

The async version uses cp.async.cg.shared.global. Data goes from global straight into shared, with no program-visible registers catching the four floats. After issuing the copy, the thread can keep going and wait only when it needs the result. commit_group bundles this thread’s previously issued copies into a group, and wait_group 0 waits for all of this thread’s earlier groups to complete (PTX cp.async semantics).

Put back into the tile loop, the pseudocode matching the implementation is:

if (tiles > 0) {
    load_tile(0, slot0);   // each thread handles its own piece of input
    commit_group();
    wait_group_0();
    __syncthreads();
}
for (int t = 0; t < tiles; ++t) {
    if (t + 1 < tiles) {
        load_tile(t + 1, other_slot);
        commit_group();
    }
    compute_tile(current_slot);
    wait_group_0();
    __syncthreads();
    swap(current_slot, other_slot);
}

The wait can’t replace the block barrier. A thread only waits for its own copies; it knows neither whether others’ copies are done nor whether another warp is still reading the old slot. Only when every thread has waited and then met at the barrier is it guaranteed both that the next tile is fully written and that the current tile is fully read. Then the next iteration can read the new slot and write an even later chunk into the old one.

If loading and compute overlapped perfectly, steady-state time per chunk would approach max⁡(Tload,Tcompute)\max(T_{\rm load},T_{\rm compute})max(Tload​,Tcompute​) instead of Tload+TcomputeT_{\rm load}+T_{\rm compute}Tload​+Tcompute​. That model ignores the first load, the last compute, synchronization and resource contention; it only shows where the pipelining opportunity is. With only one K chunk there is no steady state at all, so speed differences there can’t be explained by it.

Register double buffering, and a priming bug

Once shared is ready, there’s another layer: shared→register. Each thread fetches eight A and eight B values per k to update 64 accumulators. The implementation uses two sets of register operands: while the current set feeds FMAs, the next one is already loading. This small loop also has to prime the first set:

load_fragment(/* k */ 0, /* register slot */ 0);
for (int k = 0; k < 32; ++k) {
    int cur = k & 1;
    if (k + 1 < 32) load_fragment(k + 1, cur ^ 1);
    fma_fragment(cur);
}

Figure 3: Priming the first register set.

Delete the load before the loop, and the first iteration fills only slot 1 while doing FMAs on slot 0. Zeroing slot 0 is wrong too: it deterministically drops the current tile’s k=0 term. Every new shared tile has to re-prime the first set, or you need a separately designed cross-tile preload.

One implementation really did have this bug. It was written as “load the next set, compute the current set,” with no priming. At M=128,N=512,K=64, all 65536 outputs exceeded the budget, with max absolute error 0.992814749. Outputs were finite, guards intact and memcheck reported zero errors. Uninitialized operands don’t necessarily show up as illegal memory accesses, which is why a numerical reference can’t be skipped. (That run also mixed in other stages, so the whole error can’t be pinned on priming; code review can only establish that this term wasn’t built correctly.)

There’s a more targeted input for this bug. Make A have a 1 only in the first position of every 32-element K chunk and 0 elsewhere, with B arbitrary. Then the output depends only on the k=0, 32, 64, … contributions, and you can see directly whether each tile’s first term reached the accumulator. That locates pipeline-initialization errors far more easily than throwing more random samples at it.

Making it correct off the happy path

Take K=33: the second chunk has only one valid k. Take M=129 or N=65: edge output tiles have only some valid positions. The tiled compute stays the same; loads write zero for invalid elements, and write-back checks actual rows and columns.

Zero-filling is legal for GEMM, since the extra products are zero. But it doesn’t remove cooperating threads’ barriers, and it doesn’t let you downgrade a 16-byte read to “use only one element”: the invalid addresses don’t contribute to the output, but the access itself is still out of bounds.

So each four-element group first checks range and actual alignment. If all four are in range and the source pointer is 16-byte aligned, it takes the async wide copy; otherwise it fetches valid elements one by one and zero-fills. With K=33 the row pitch is 132 bytes and different rows meet different alignment conditions, so one kernel can mix async copies and ordinary shared writes.

Both paths write the same XOR layout, to non-overlapping regions. Only after the loop-end async wait and block barrier do consumers read uniformly. If the fallback branch still wrote the plain row layout, aligned matrices would pass and edge elements would be wrong. Range, layout and stage protocol have to be reviewed together.

The grid has to cover correctly too. This post uses a direct 2D grid of ceil(N/64) × ceil(M/128). One implementation remapped column tiles in groups of eight:

tile_row = blockIdx.x >> 3
tile_col = blockIdx.y * 8 + (blockIdx.x & 7)

but didn’t exclude the padding tiles this created. N=64 needs only one column, yet the extra column blocks still read B and wrote C, producing 82 memcheck errors on 128×64×64; the first reported was a 16-byte async out-of-bounds read. The remapping might improve cache locality between blocks, provided it’s still a correct mapping onto valid output tiles. Here I used the direct grid and didn’t treat the out-of-bounds implementation as a performance baseline.

The four formal variants plus one compatibility entry pass 240 FP64 numerical checks, including K=0, tails, 0–3 float offsets and first-term-only inputs. Each of the four variants also passes 48 memcheck and 48 racecheck runs with zero errors and zero hazards. These are prerequisites for the timings below; shapes and budgets are in the appendix.

Four implementations, one step apart

Now the four implementations side by side. They share the thread mapping above, the 8×8 outer product and register fragment priming, and each pair of neighbors differs in just one design choice:

I didn’t test a raw async version or three- or four-stage pipelines, so this isn’t a combinatorial search. What it can answer is what each step along this rewrite path cost and what it bought.

What the compiler emitted

The async version keeps cp.async.cg.shared.global, cp.async.commit_group, cp.async.wait_group 0 and bar.sync 0 in PTX; in SM120 SASS they become:

LDGSTS.E.BYPASS.128 ...
LDGDEPBAR
... compute and other instructions ...
DEPBAR.LE SB0, 0x0

That confirms the async global→shared copy, commit and wait really made it into machine code. The static disassembly has five LDGSTS sites, two commits and two waits across the preload, the loop and branches. Site counts aren’t per-tile execution counts, and they don’t say how much copying is actually hidden behind compute.

Compiled resources changed at the same time:

Introducing the XOR costs the whole kernel 40 more registers. One XOR doesn’t need 40 registers; the address expressions, live ranges and scheduling all changed together. Two slots then double the storage, and registers reach 211. Zero spills only means nothing overflowed into extra storage; it doesn’t mean residency came for free.

Think of a wavefront as a unit of service in the shared pipeline. Even a conflict-free wide read may take several ideal wavefronts; “extra” is actual minus ideal computed from real instructions and participating threads, not total minus one. The main reads are LDS.128 in SASS, four floats per lane, which don’t fit the one-scalar-read eight-address model from before.

Exporting per-SASS-address counts from raw’s Source page, the excess concentrates at 64 LDS.128 sites. For example, LDS.128 R20,[R4] has actual 131072 and ideal 65536; the differences at all 64 sites sum to 4194304, matching the total exactly. This real wide instruction’s actual/ideal is 2, not the 8 from scalar deduplication.

ncu --import pipeline-raw.ncu-rep --page source --print-source sass `
  --metrics memory_l1_wavefronts_shared,memory_l1_wavefronts_shared_ideal --csv

The recheck order matters: pick the same template instance, take differences by SASS address, then plug the target read’s lane addresses back into the formula. That’s how you say exactly where an optimization acts, rather than screenshotting a “fewer conflicts” percentage (NCU metrics and SourceCounters).

Extra wavefronts drop to zero for all three XOR implementations, while the independent hardware counter l1tex__data_bank_conflicts_pipe_lsu_mem_shared_op_ld.sum drops from raw’s 6297071 to swizzle single’s 7399. That 7399 still isn’t zero. I haven’t traced the remainder item by item, so the two measures can’t be combined into “the kernel has no bank conflicts at all.”

Meanwhile, register block limit falls from 4 to 3 to 2 and shared block limit from 4 to 2, and achieved occupancy falls with them. The layout really did improve, and there’s also less resident work available to hide waiting. Total time depends on both sides, plus other instruction changes mixed in.

The timings: why removing conflicts slowed 1024³

Device time comes from an independent warm benchmark: three rounds of 30 batches per configuration, with the median of round medians as the center. NCU uses kernel replay with default cache and clock control, only to explain accesses; timings don’t come from its replay.

Figure 5: The four implementations across three square sizes.

On 1024³, XOR single buffering is about 19.5% slower. raw’s three rounds span 0.30325–0.30822 ms and swizzle’s 0.36302–0.36312 ms, with no overlap. Clearing the target reads’ extra wavefronts doesn’t offset the other costs of rewriting the layout. More registers and lower residency are concrete leads, but the current experiments can’t decompose that 19.5%.

Adding the second slot helps 1024³, yet 2048³ goes from 2.47729 ms to 2.82787 ms. A second slot gives room to load ahead and also consumes another copy of resources. Switching to async copies brings 2048³ down to 2.25238 ms, about 20.4% less time than synchronous double buffering with the same layout, but only about 3.5% less than the original raw single’s 2.33407 ms. The first comparison measures swapping the copy mechanism; the second measures the whole design. Those two gains shouldn’t be blended.

Short K tests whether we’re crediting every change to pipeline overlap. 128×64×32 has one output tile and one K chunk, nothing to prefetch, and async is 11.78 µs against raw’s 12.54 µs. That small difference only says the copy path and compiled schedule changed overall; it’s not evidence of cross-tile overlap. At K=64 the two are 12.71 and 12.66 µs, with overlapping three-round ranges.

Figure 6: Small shapes, device-only and with host round trip.

Counting pageable host transfers and synchronization, microsecond-level kernel differences shrink further within total waiting. The end-to-end times in the figure exclude allocation, compilation and handle creation, and shouldn’t be mixed with repeated calls on GPU-resident inputs.

Eight more shapes check whether the tile fits; speed ratios are relative to each row’s own raw single, from an independent measurement batch:

Figure 7: Relative speed by shape.

8192×64×128 fills output tiles exactly, with raw and async at 38.822 and 34.453 µs. Swap M and N and there are only 64 valid output rows, so half of each 128-row tile sits empty, and the numbers become 39.771 and 39.395 µs. Same FLOPs; the tile mapping no longer fits. 512×512×16 likewise has no steady-state pipeline, and 14.448→12.855 µs can’t be explained as cross-chunk overlap either.

On 4096³, raw’s center is 23.958 ms and async’s 24.898 ms, with three-round ranges of 22.838–28.531 and 22.793–32.870 ms. The variation is larger than the roughly 4% difference between centers, so there’s no clear verdict that async is slower. It’s still faster than same-layout synchronous double buffering’s 31.950 ms, but that doesn’t show the XOR async design as a whole beats the plain layout.

What this does and doesn’t show

  • It shows that the XOR swizzle eliminates the extra shared wavefronts it targets (4,194,304 → 0), traced to specific LDS.128 sites.
  • It shows that the same change raised registers from 128 to 168 and lowered occupancy, and that the kernel got 19.5% slower on 1024³ with non-overlapping ranges.
  • It shows that async copies beat synchronous double buffering by about 20% on 2048³, but the whole design beats the original by only about 3.5%, and nothing is clearly decided on 4096³.
  • It shows two real correctness traps, an unprimed register buffer that passes memcheck and a remapped grid that reads out of bounds, and how targeted inputs catch them.
  • It doesn’t decompose copy, wait and compute cycles, and the residual 7399 hardware bank conflicts aren’t traced. TMA, other GPUs, fixed clocks and production call chains weren’t tested.

My open question

So here’s what the facts say: trying techniques on an operator without first simulating it against a targeted roofline model is pretty much meaningless. At this point I did try to build a roofline model and work through the math, but the relationships I derived were enormously complicated, and nudging a few parameter values made the arithmetic intensity swing wildly.

So I’d really appreciate it if anyone passing by could point me in the right direction. For a given operator, is telling what limits it something you can only judge from experience, or by just running a baseline kernel and reading Nsight-style results? And does deriving formulas from basic hardware parameters have real practical value in operator design?

Source interfaces, test scope and reproduction commands

📝 Note: Paths in this appendix such as bench_mur/ and rep_mur/ are in my private research repository, so they aren’t public; they’re listed so each result can be traced. The CUDA kernels the post cites are public in Murmurwkk/cuda-operators.

Environment and measurement method

Test device: RTX 5070 Laptop GPU, 8 GB, SM120, driver 610.88; built with CUDA Toolkit 13.1.115 and MSVC 2022. Environment cross-checks recorded runtime API version 13.3. Since CUDA 13 the Windows runtime can ship with the display driver, so it can differ from the build Toolkit; see the CUDA Runtime API versioning notes. The original GEMM environment records queried nvcc and the driver; the runtime field comes from a separate environment check.

The performance protocol follows the previous post: 20 device warm-ups, 10 pilot runs to estimate repeats per batch, a target of about 20 ms, 1–2000 repeats per batch, 30 batches, 3 rounds with shuffled task order. Data is reused and L2 isn’t flushed. End-to-end timing is separate and includes pageable host H2D (A, B), the kernel, D2H (C) and synchronization, excluding allocation, compilation and cuBLAS handle creation. Table centers are the median of three round medians; error bars in figures show the min–max of the three round medians, not statistical confidence intervals.

The four implementations are compiled into separate executables and don’t link against each other’s old solve. GPU experiments run serially; start and end temperatures and clocks are recorded, but clocks weren’t locked and the laptop’s full power state wasn’t controlled.

Interfaces and correctness checks

All inputs are contiguous row-major FP32 matrices A[M,K] and B[K,N], with output C[M,N]=A×B. Kernels use ordinary FP32 FMA, no Tensor Cores and no TF32. Only this explicit layout contract is supported; arbitrary strides, input/output aliasing and NaN/Inf special semantics are outside this validation.

The shared implementation is in gemm/gemm_pipeline.cuh. The two old files keep their own independently compilable solve entries, so same-named symbols in the repository don’t link against each other:

FileArgument order keptPurpose
mulmatrix_let_merged.cusolve(A,B,C,M,N,K)Original merged calling convention; also provides an async launch with a stream
mulmatrix_let2.cusolve(A,B,C,M,K,N)Keeps the dimension order the old implementation actually interpreted; the old function used to swap the last two internally

solve still returns synchronously for compatibility with old callers; timing uses the stream launch without host synchronization after every kernel. The two entries have different dimension orders, so the test wrapper adapts them explicitly; copying a uniform-looking declaration doesn’t make them the same ABI.

The old code was archived as-is with SHA-256 hashes, then the shared tile and consumer mapping were extracted to rebuild separable comparisons. The new implementation fixes boundaries, initial registers and the stage protocol, and drops the old eight-column grid remapping. Because more than one thing changed, differences between old and fixed versions aren’t used for single-optimization performance attribution.

The full CPU FP64 checks cover 12 shapes, in M, N, K order:

1×1×0, 1×1×1, 7×13×3, 15×17×15,
63×65×31, 64×64×32, 65×63×33, 127×129×17,
128×128×32 (one aligned, one offset), 129×131×65, 256×256×129

Pointer offsets cover 0, 1, 2 and 3 floats. Each shape has four distributions: random, all zeros, alternating signs and first-element-per-K-tile nonzero. Across the four performance versions plus the let2 compatibility entry, all 240 checks pass. Outputs are pre-filled with NaN and guarded before and after, separately checking for missed writes, non-finite values and sentinel damage from out-of-bounds writes.

The CPU reference accumulates term by term in double, with an error budget of 1e-6 + 16*FLT_EPSILON*sum(abs(Aik*Bkj)). This is an explicit budget for this experiment, not a floating-point error theorem for every K and input distribution. Large shapes in the performance experiments additionally check 257 deterministic positions against a CPU FP64 reference and compare against full cuBLAS pedantic FP32 output, with a cuBLAS budget of 3e-4 + 3e-4*abs(reference). Large matrices didn’t get a full CPU FP64 reference; their validation is a full GPU comparison plus a sampled high-precision reference.

Compute Sanitizer runs 48 memcheck and 48 racecheck cases for each of the four versions, all with zero errors and zero hazards. They cover short K, multiple K tiles, offsets and tails. Finite tests can’t prove correctness for all inputs and architectures, but they cover several independent failure types beyond ordinary numerical tests. Both checks for gemm_8 were rerun once, and those logs pass too.

The old mulmatrix_let2.cu has a truncated loop statement and reports 10 errors when compiled as-is, so it wasn’t used as a runnable old baseline. That compile log, the failure record for the merged version with only a type alias added, and the fixed version’s results are saved separately in the experiment directory.

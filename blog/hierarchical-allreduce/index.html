Why Hierarchical AllReduce Isn't 8× Faster

Sending one-eighth of each gradient off-node doesn't help if all eight eighths leave through the same network card. Following one gradient, then the bytes, through BlueConnect, TACCL and multi-port rings.

更新于 2026/11/6 · 5 个章节
#AllReduce#NCCL#communication optimization#distributed training#paper deep dive

In data-parallel training, every GPU computes gradients on different samples, so every parameter ends up with G×HG\times HG×H contributions that have to be summed. Inside a node you have NVLink; between nodes you have InfiniBand, which is a lot slower. The common idea follows naturally: reduce inside the node first, so less data has to leave, then distribute the global result back.

But “each GPU only sends one-eighth of the gradient off-node” doesn’t make anything eight times faster. Those eight eighths may all squeeze through the same network card in the end. And every position in the result still has to collect every input exactly once.

So this post follows one vector twice. First we follow the gradient through a hierarchical reduction and make sure every position gets every contribution exactly once (and see how two common mistakes break that). Then we follow the bytes out to the node’s egress, and see what that means for papers like BlueConnect, TACCL and Trivance, and for how communication plugs back into a training step.

Part 1: following the gradient

Splitting one gradient across three nodes

Take HHH nodes with GGG ranks each. A rank is one communication participant; in our example, each owns one GPU. Node hhh, local index ggg has input xh,g∈RNx_{h,g}\in\mathbb R^Nxh,g​∈RN, and position iii always means the same parameter. The goal is

y[i]=∑h=0H−1∑g=0G−1xh,g[i],0≤i<N.y[i]=\sum_{h=0}^{H-1}\sum_{g=0}^{G-1}x_{h,g}[i],\qquad 0\le i<N.y[i]=h=0∑H−1​g=0∑G−1​xh,g​[i],0≤i<N.

What gets split is the range of vector positions, never anyone’s contribution. Each shard is responsible for some parameters, and every parameter it’s responsible for must include all ranks’ contributions.

Let’s make it concrete: three nodes, four GPUs each, 16 elements per GPU, split into four shards covering positions 0–3, 4–7, 8–11 and 12–15. We’ll follow just position 5, which belongs to shard 1. Filling inputs with consecutive integers starting from 1, the twelve values at this position are

g=0g=1g=2g=3node sumh=06223854120h=17086102118376h=2134150166182632\begin{array}{c|rrrr|r} &g=0&g=1&g=2&g=3&\text{node sum}\\\hline h=0&6&22&38&54&120\\ h=1&70&86&102&118&376\\ h=2&134&150&166&182&632 \end{array}h=0h=1h=2​g=0670134​g=12286150​g=238102166​g=354118182​node sum120376632​​

These are just hand-computable stand-ins for gradients. Every node should end up with 120+376+632=1128120+376+632=1128120+376+632=1128.

Step 1: ReduceScatter inside each node. Sum by position, then hand different positions’ results to different ranks. GPU 1 on each node now holds 120, 376 and 632 respectively. The jjj-th owner on node hhh gets

sh(j)=∑g=0G−1xh,g(j),s_h^{(j)}=\sum_{g=0}^{G-1}x_{h,g}^{(j)},sh(j)​=g=0∑G−1​xh,g(j)​,

where the superscript (j)(j)(j) is a position range. At this point a GPU holds all of its node’s contributions for one shard, and nothing about the other shards.

Step 2: AllReduce across nodes. Group same-numbered owners across nodes: shard 0 with shard 0, shard 1 with shard 1, and so on. Each group does one AllReduce:

y(j)=∑hsh(j)=∑h∑gxh,g(j).y^{(j)}=\sum_hs_h^{(j)}=\sum_h\sum_gx_{h,g}^{(j)}.y(j)=h∑​sh(j)​=h∑​g∑​xh,g(j)​.

That’s where position 5’s three node sums finally meet, in group 1. After this stage, GPU 1 on every node has 1128. The other three GPUs don’t have this position yet, but each holds a different correct shard.

Step 3: AllGather inside each node copies the four shards back into the full vector:

y=concat⁡(y(0),y(1),y(2),y(3)).y=\operatorname{concat}(y^{(0)},y^{(1)},y^{(2)},y^{(3)}).y=concat(y(0),y(1),y(2),y(3)).

This only restores position ranges; no more addition. Now every GPU has the same global result (NCCL collective semantics).

Figure 1: Simplified to two nodes and shard 0 only, to show that each node sum enters the global sum exactly once. A real implementation sends every shard through, then distributes results as needed. The summing node in the figure doesn’t mean one GPU sends and receives everything.

The three stages together are RS–AR–AG: intra-node ReduceScatter, cross-node AllReduce, intra-node AllGather. Correctness rests on two independent conditions: each shard collects every contribution, and the shards cover the full position range. It doesn’t need a power-of-two node count, and it doesn’t care which network layer is faster.

Two ways to get it wrong, and a counter that catches both

A common mistake is to read “GPU 1 holds all of its node’s contributions” as “GPU 1 holds the whole vector.” If, after ReduceScatter, only GPU 0 goes cross-node, position 5’s three node sums never meet. GPU 0 can represent shard 0, not other positions.

A single-proxy scheme can be correct, though: reduce the full node sum to one proxy, AllReduce among proxies, then broadcast inside each node. It differs from the sharded scheme only in who holds each shard and which paths it takes; the sum it computes is identical.

The opposite mistake double counts. First do an intra-node AllReduce, so all four GPUs hold the same node sum. Then feed all those copies into one global sum:

∑h∑g=0G−1sh=G∑hsh=Gy.\sum_h\sum_{g=0}^{G-1}s_h=G\sum_hs_h=Gy.h∑​g=0∑G−1​sh​=Gh∑​sh​=Gy.

1128 becomes 4512. Every GPU still gets the same answer, so “all GPUs agree” doesn’t prove the reduction was right.

One case deserves a note. After an intra-node AllReduce, build four independent same-numbered groups, each taking one copy of the node sum per node and reducing across nodes. All four groups correctly get 1128. That costs four extra full vectors on the wire, but nothing is numerically over-counted. The difference is whether copies end up in the same addition.

To catch these mistakes directly, attach a provenance count to every output position: one column per original rank, incremented each time that rank’s input is added in. In a correct result every real position is all ones. A missing shard shows up as 0, double counting as values above 1.

Figure 2: From an actually run CPU integer model: three nodes, four GPUs each, length 13. The program pads to 16, processes four shards and trims the padding. The first 13 rows should each have 12 ones; padding has no original contributions. Sending only shard 0 cross-node keeps just the first four real positions; re-adding intra-node copies puts 4 in every cell.

The point of the model isn’t to simulate network time with NumPy. It’s to make values and provenance counts travel the same path. Here’s the reduction part of collective_case, with input construction and the deliberately broken branches omitted; local_chunks[h][j] holds both a shard’s values and its provenance matrix:

global_chunks = [
    (sum(local_chunks[h][j][0] for h in range(nodes)),
     sum(local_chunks[h][j][1] for h in range(nodes)))
    for j in range(local_ranks)
]
final_values = np.concatenate([x[0] for x in global_chunks])[:length]
final_counts = np.concatenate([x[1] for x in global_chunks])[:length]
assert np.array_equal(final_values, expected)
assert np.all(final_counts == 1)

The check sweeps node counts 1, 2, 3, 4, local rank counts 1, 2, 4 and lengths 1, 2, 3, 7, 8, 13, 17, for 84 combinations, and the correct scheme passes all of them. Padding to G⌈N/G⌉G\lceil N/G\rceilG⌈N/G⌉ also covers N<GN<GN<G (zero is the additive identity), though that isn’t the same as testing real NCCL zero-count calls; length 0 isn’t in the model.

Using non-overflowing int64 separates reduction structure from floating-point rounding. With real gradients each contribution should still appear once, but hierarchy changes the association order of additions, so results needn’t match serial summation bit for bit. High-precision references, non-finite checks and sensible tolerances still matter, and the tolerance can’t be so loose that a missing shard slips through.

📝 Note: The final AllGather doesn’t always need to run. If each GPU owns only one shard of optimizer state, it only needs the matching global gradient shard to update parameters. FSDP hybrid sharding’s gradient reduction is exactly a ReduceScatter within the shard group plus AllReduce of same-numbered shards across replica groups (see FSDP and Megatron); a parameter AllGather happens later when forward needs full parameters. That’s a different tensor with a different lifetime, not “copy the full gradient immediately” (FSDP §3.2.2).

Part 2: following the bytes

Ring traffic, counted at the right boundary

Only once the reduction is correct does it make sense to ask how much less was sent. Let each rank’s full input be SSS bytes, and assume a standard chunked ring: PPP participants in a circle, each round sending one chunk to the next.

ReduceScatter takes P−1P-1P−1 rounds of S/PS/PS/P; AllGather another P−1P-1P−1. Each rank sends

Vrank=2P−1PS.V_{\rm rank}=2\frac{P-1}{P}S.Vrank​=2PP−1​S.

That counts bytes sent, not sent plus received. It describes this ring’s payload, not every NCCL algorithm’s rounds, and it doesn’t mean links actually run at full speed.

In the hierarchical scheme, intra-node RS plus AG sends, per GPU,

Vlocal,rank=2G−1GS.V_{\rm local,rank}=2\frac{G-1}{G}S.Vlocal,rank​=2GG−1​S.

In the middle there are GGG cross-node groups, each handling a shard of size S/GS/GS/G with HHH participants. Each GPU sends cross-node

Vcross,rank=2H−1HSG.V_{\rm cross,rank}=2\frac{H-1}{H}\frac SG.Vcross,rank​=2HH−1​GS​.

There’s that 1/G1/G1/G. But GGG GPUs on the same node send simultaneously, and their bytes add up. At the node egress it’s still

Vcross,node=2H−1HS.V_{\rm cross,node}=2\frac{H-1}{H}S.Vcross,node​=2HH−1​S.

That’s exactly the node payload of the single-proxy scheme with a ring AllReduce among proxies. Sharding changes owners and concurrency opportunities; it doesn’t shrink what the node as a whole has to exchange by another factor of GGG.

A flat ring has to be counted by actual path, too. Put all HGHGHG ranks in one ring with same-node ranks adjacent, and each node has just one ring edge crossing to the next node. That edge carries S/(HG)S/(HG)S/(HG) per round over 2(HG−1)2(HG-1)2(HG−1) rounds, so the node’s cross-boundary send is

Vflat,cross,node=2HG−1HGS.V_{\rm flat,cross,node}=2\frac{HG-1}{HG}S.Vflat,cross,node​=2HGHG−1​S.

Intra-node ring edges don’t go through the NIC, so you can’t multiply per-rank sends by GGG to get cross-node traffic. Interleaving ranks would add cross-node edges; multiple channels, bidirectional rings or other topologies need recounting by path.

With eight nodes of eight GPUs and a 256 MiB full vector:

Accounting boundaryHierarchical send volume
Per GPU, intra-node RS + AG448 MiB
Per GPU, cross-node56 MiB
Per node, cross-node total448 MiB
Flat ring with same-node ranks adjacent, per node cross-node504 MiB

Seen from the node, hierarchy cuts 504 MiB to 448 MiB. Seen from one GPU, each carries 56 MiB across. Those are statements about different boundaries and can’t substitute for each other. And as node count grows, both node-egress formulas approach 2S2S2S, so payload reduction alone buys less and less.

Bandwidth is per resource, not per communicator

If all 448 MiB leaves through one egress of effective bandwidth BnodeB_{\rm node}Bnode​, then even ignoring launch, synchronization and contention, the time can’t be lower than

Tcross≥Vcross,nodeBnode.T_{\rm cross}\ge \frac{V_{\rm cross,node}}{B_{\rm node}}.Tcross​≥Bnode​Vcross,node​​.

Only if there really are GGG concurrent, non-contending paths of effective bandwidth BBB each, with evenly split shards, does the bound become Vcross,node/(GB)V_{\rm cross,node}/(GB)Vcross,node​/(GB). At a declared 25 GB/s, that’s about 18.79 ms through one egress versus about 2.35 ms through eight independent ones.

That 8× gap on the right comes from eight physical resources, not from creating eight communicators. The 25 GB/s is an accounting assumption, not a measured NIC speed; a NIC rated at 200 Gbit/s may not deliver that in a real system either. Wherever paths merge again (PCIe uplink, NIC or switch port), the total bytes have to be counted at that shared point.

Latency, launches and the alpha-beta view

Large messages make bandwidth the dominant term; small messages care about fixed per-step latency. With α\alphaα as ring per-step latency and reduction compute ignored, a simple model is

TAR(P,S)≈2(P−1)α+2P−1PSB.T_{\rm AR}(P,S)\approx2(P-1)\alpha+2\frac{P-1}{P}\frac SB.TAR​(P,S)≈2(P−1)α+2PP−1​BS​.

Chain intra-node RS/AG with cross-node AR, assuming each cross-node shard has its own equal-speed path:

Thier≈2(G−1)αlocal+2G−1GSBlocal+2(H−1)αcross+2H−1HSGBcross.\begin{aligned} T_{\rm hier}\approx{}&2(G-1)\alpha_{\rm local} +2\frac{G-1}{G}\frac{S}{B_{\rm local}}\\ &+2(H-1)\alpha_{\rm cross} +2\frac{H-1}{H}\frac{S}{G B_{\rm cross}}. \end{aligned}Thier​≈​2(G−1)αlocal​+2GG−1​Blocal​S​+2(H−1)αcross​+2HH−1​GBcross​S​.​

If node bandwidth is shared, the last term’s denominator becomes the node’s total effective bandwidth. Launches and queueing across groups may not overlap either, so swapping a divisor doesn’t make the model accurate. What the formula does is put “fewer steps on the slow link,” “better use of concurrent paths” and “an extra intra-node stage” into one comparison.

What the papers assume

BlueConnect: the same decomposition, more levels

BlueConnect pushes this decomposition to multi-level networks. Write ranks as 3D coordinates (a,b,c)(a,b,c)(a,b,c) with axis sizes p0,p1,p2p_0,p_1,p_2p0​,p1​,p2​. ReduceScatter along ccc, then ReduceScatter the result along bbb, then once more along aaa. One owner’s payload shrinks as

S⟶Sp2⟶Sp2p1⟶Sp2p1p0.S\longrightarrow\frac S{p_2}\longrightarrow\frac S{p_2p_1} \longrightarrow\frac S{p_2p_1p_0}.S⟶p2​S​⟶p2​p1​S​⟶p2​p1​p0​S​.

At that point each shard has every contribution but lives with one owner; then reverse AllGathers along a,b,ca,b,ca,b,c restore the position ranges level by level. The cross-node AR in RS–AR–AG can itself be split into RS+AG, so the two are mathematically continuous (BlueConnect §3; conditions and limitations in §3.4).

The decomposition can put large early payloads on fast paths and shrunken shards on slow ones. But it still needs a suitable participant hierarchy, and it’s still bound by shared uplinks: one small shard per GPU at some level doesn’t mean small total node traffic.

The authors’ training experiments used 48 IBM S822LC machines, each with four P100-SXM2 GPUs, intra-node NVLink and single-port 100 Gbit/s InfiniBand. ResNet-50/ImageNet-1K, batch 32 per GPU, total batch 6144 on 192 GPUs, FP32 gradients, data preloaded on RAM disk. What carries over is the method of decomposing collectives by network level, not a fixed speedup attached to the algorithm.

TACCL: shorter paths aren’t automatically faster kernels

The models above treat “send a shard and reduce it” as one step. On a GPU it may become receive, sum, write an intermediate buffer, read it again, send, and whether those can be fused changes the time directly. A shorter path doesn’t guarantee a faster implementation.

TACCL (NSDI 2023) synthesizes communication plans from a user-supplied communication sketch. On AllReduce across two DGX-2s with messages of at least 512 MB, it was up to 9% slower than NCCL 2.8.4-1. The authors attribute that negative result to the backend lacking fused receive-reduce-copy-send operations: work saved at the path level can be eaten back by extra instructions and synchronization (TACCL Figure 8(i)).

The same paper’s headline 6.7× comes from small-to-medium AllGather on two DGX-2s (32 GPUs), not this AllReduce. §7.2 also shows that more execution instances raise small-message latency; the authors’ explanation, synchronized memory-access scheduling at send start, is a hypothesis. Larger messages are more likely to benefit from extra parallelism. Message size decides how launch cost trades against parallel bandwidth.

Trivance: the multi-port assumption

Multi-port algorithms change a different assumption: how many directions you can send in at once. Trivance targets bidirectional rings and multi-dimensional tori and uses concurrency across directions to cut logical steps. Its §6 is SST packet-level simulation; Appendix E defaults to 800 Gb/s links and adds no constraint that “all interfaces share one node-wide injection limit,” and Appendix D requires those paths to be usable simultaneously (Trivance).

On a real machine where two directions end up sharing one congested uplink, the reduction is still mathematically correct, but the simulation’s concurrency condition is gone. That’s the same resource question as eight GPUs sharing one NIC, in a different topology.

So: BlueConnect teaches how to layer, TACCL’s negative result is a reminder that the execution backend has costs, and Trivance requires spelling out port concurrency. Their headline speedups can’t be lined up and ranked against each other.

Plugging communication back into training

Communication also has to connect back to training. Backward writes gradients on the compute stream, and the communication stream must wait for a shard to be ready before reading it. Cross-node reduction waits for the intra-node ReduceScatter’s result, and the optimizer waits for the shard it needs. A normal NCCL call returning only means the operation was enqueued on a CUDA stream, not that the data is usable by any consumer; cross-stream dependencies need stream/event semantics (NCCL CUDA Stream Semantics).

Position 5’s mathematical ownership becomes, in an implementation, buffer offset, shard length, dtype and the communicator’s rank mapping. Every node must interpret “shard 1” by the same rule, with consistent padding and trimming. The CPU provenance model doesn’t verify real network offsets, packet order or failure recovery, and doesn’t implement GPUDirect RDMA completion and visibility. If a retry adds the same contribution again, the provenance count goes above 1, and resending alone doesn’t fix that.

What training actually waits on is the last gradient on the critical path. If some communication gets much faster but was already hidden behind backward compute, the step barely changes; a tiny tail reduction that blocks the optimizer may decide the step time. So measurements should separate the intra-node stage, the cross-node stage, the full reduction and the training step. Per-GPU bytes, node-egress bytes, GB/s and step time answer different questions, and the prettiest one can’t stand in for the other three.

Conclusion

Let’s recap both journeys. Following the gradient: hierarchical AllReduce is correct when every shard collects every contribution exactly once and the shards cover all positions, and a provenance counter catches both missing and double-counted shards, which “every GPU got the same answer” can’t. Following the bytes: hierarchy cuts per-GPU cross-node traffic by GGG, but node egress traffic stays near 2S2S2S, and any speedup beyond that needs physically independent paths. BlueConnect, TACCL and Trivance each work only under their own resource and backend conditions.

Count the reduction per position and count the bytes per physical link; any number you skip will come back as a surprise.

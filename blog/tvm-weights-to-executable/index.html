Where TVM's Fusion Stops

Two matmuls became one and five functions became two, yet three temporary matrices survived. Following one Relax program down to TIR loops to see what TVM's fusion actually removed.

更新于 2026/11/6 · 8 个章节
#Relay#TVM#compilers#paper reading#quantization

When a compiler reports that it “performed fusion,” what it eliminated could be at any of several levels: function calls, intermediate matrices, or just grouping a few operators into one region. Those have very different performance consequences.

In this post I hand a very short Relax program to TVM and save the intermediate representation at every stage. Two identical matrix multiplies get deduplicated into one, and five tensor-compute functions get fused into two. Then you open the generated fused_* function, and three 32×6432\times6432×64 intermediate buffers are still there, with four full passes over the data, one after another. It compiles, the numbers check out, and you still have to read the artifacts layer by layer to know what optimization actually happened.

The environment is Relax in Apache TVM 0.27.0.post1, targeting LLVM CPU. The Relay paper provides design background, but the code and observations come from Relax artifacts; interfaces, pipelines and performance numbers from the two eras don’t transfer.

We’ll follow the program through four stages: folding and CSE, then fusion (where we’ll find what got merged and what didn’t), then a symbolic batch dimension, and finally int8 quantization, the one stage that deliberately changes the program’s meaning. Along the way we’ll count the bytes that full fusion would save.

The test program

X∈RB×DX\in\mathbb R^{B\times D}X∈RB×D is the input and W∈RD×DW\in\mathbb R^{D\times D}W∈RD×D a constant weight. Compute Z=XWZ=XWZ=XW, then split into two paths: one adds a bias and applies ReLU, the other scales by a constant, and the two are summed.

Z=XW,b=b0+b1,Y=ReLU⁡(Z+b)+αZ,α=0.125.Z=XW,\quad b=b_0+b_1,\quad Y=\operatorname{ReLU}(Z+b)+\alpha Z, \qquad\alpha=0.125.Z=XW,b=b0​+b1​,Y=ReLU(Z+b)+αZ,α=0.125.

DDD is fixed at 64 and BBB is the row count. b0,b1b_0,b_1b0​,b1​ are length-64 constant vectors broadcast across rows. This isn’t a stripped-down real model; it just puts three things side by side: a constant that can be computed ahead of time, a duplicated computation that can be shared, and an intermediate value read by two consumers.

Written casually in array code:

z0 = x @ W
z1 = x @ W
bias = b0 + b1
r = maximum(z0 + bias, 0)
y = r + 0.125 * z1

A human sees line two and wants to reuse z0. A compiler first has to establish that the two computations are interchangeable. Here the inputs are the same and there are no side effects, so they can be shared. With random sampling, mutable state or effectful calls, identical names and arguments wouldn’t be enough. That’s why the Relay paper’s §3.1 spends time on explicit bindings and evaluation order: a program isn’t just an effect-free DAG of operators (Relay paper).

In Relax, bb.emit creates a binding that later code can reference. Two independent matmuls are emitted on purpose, so CSE has to discover the duplicate itself rather than having z0 shared while building the graph in Python:

x = relax.Var("x", relax.TensorType((32, 64), "float32"))
bb = relax.BlockBuilder()
with bb.function("main", [x]):
    with bb.dataflow():
        z0 = bb.emit(relax.op.matmul(x, relax.const(W)))
        z1 = bb.emit(relax.op.matmul(x, relax.const(W)))
        bias = bb.emit(relax.op.add(relax.const(b0), relax.const(b1)))
        a = bb.emit(relax.op.add(z0, bias))
        r = bb.emit(relax.op.nn.relu(a))
        s = bb.emit(relax.op.multiply(z1, relax.const(np.float32(.125))))
        y = bb.emit_output(relax.op.add(r, s))
    bb.emit_func_output(y)
mod = bb.get()

Stage 1: folding and CSE

At this level the program has seven high-level operations. FoldConstant computes b0+b1b_0+b_1b0​+b1​ into one constant, leaving six; EliminateCommonSubexpr merges the two XWXWXW into one, leaving five:

mod = relax.transform.FoldConstant()(mod)
mod = relax.transform.EliminateCommonSubexpr()(mod)

In the saved IR, the second multiply’s binding becomes lv1 = lv, and the scale branch uses the existing lv directly. lv is the formula’s ZZZ; no second copy is allocated.

The weight is a constant too, but the matmul can’t be folded away, because XXX only exists per request. The compiler can store and prepare WWW, but XWXWXW still runs at runtime. That’s also the line between constant folding and CSE: folding consumes values known at compile time, while CSE makes identical computations within one run happen once.

Figure 1: Operation and function counts at each stage, from the saved IR.

Seven operations becoming five doesn’t mean two-sevenths less time. One B×DB\times DB×D by D×DD\times DD×D multiply is about 2BD22BD^22BD2 FLOPs, while each elementwise op is on the order of BDBDBD, and node sizes in a graph don’t reflect that gap. Operation counts tell you whether a rewrite happened; using them to estimate performance goes badly wrong.

Stage 2: fusion, and what didn’t fuse

After those two steps the compute dependencies are clear, but memory traffic isn’t decided yet. Relax stays at the tensor level; TIR expands operators into loops, reductions and buffers; LLVM finally generates CPU code. A TIR PrimFunc can be thought of as a low-level function that describes tensor computation explicitly, possibly with several loop nests and several temporary arrays.

Figure 2: The compilation route from tensor expressions to CPU code.

The same folded, deduplicated program went down two compilation paths. One goes straight into build lowering; the other first inserts an explicit set of passes:

passes = tvm.transform.Sequential([
    relax.transform.LegalizeOps(),
    relax.transform.AnnotateTIROpPattern(),
    relax.transform.FuseOps(),
    relax.transform.FuseTIR(),
])
mod = passes(mod)

The order is deliberate. LegalizeOps replaces high-level ops with callable low-level computations. Pattern annotation identifies access patterns like elementwise, broadcast and reduction. FuseOps picks regions that can be processed together. FuseTIR then merges the low-level functions within each region. Choosing regions and arranging loops are different levels of the problem (TVM fusion docs).

This small graph has a fork: ZZZ feeds both the bias branch and the scale branch, and all uses meet at the output add. Absorb only the first branch into the matmul and the second still needs to read ZZZ, so its storage may not go away. Region analysis has to account for every consumer, and if the program also returned ZZZ as an extra output, its externally visible lifetime couldn’t be cut at all.

The actual artifacts: the base path has five compute PrimFuncs, matmul/add/relu/multiply/add1. The explicit fusion path has just two, matmul and fused_add_relu_multiply_add1. The second name is long and lists all four elementwise ops. The real question is how far that “includes” goes.

Open the generated function and the first thing you see is three 32×6432\times6432×64 buffers:

T_add_intermediate = T.sblock_alloc_buffer((T.int64(32), T.int64(64)))
compute_intermediate = T.sblock_alloc_buffer((T.int64(32), T.int64(64)))
T_multiply_intermediate = T.sblock_alloc_buffer((T.int64(32), T.int64(64)))

They hold the bias-add, ReLU and scale results. Then come four full passes over the data. The first two, as generated:

for ax0, ax1 in T.grid(T.int64(32), T.int64(64)):
    with T.sblock("T_add"):
        v_ax0, v_ax1 = T.axis.remap("SS", [ax0, ax1])
        T.reads(lv[v_ax0, v_ax1], param_0[v_ax1])
        T.writes(T_add_intermediate[v_ax0, v_ax1])
        T_add_intermediate[v_ax0, v_ax1] = lv[v_ax0, v_ax1] + param_0[v_ax1]
for i0, i1 in T.grid(T.int64(32), T.int64(64)):
    with T.sblock("compute"):
        v_i0, v_i1 = T.axis.remap("SS", [i0, i1])
        T.reads(T_add_intermediate[v_i0, v_i1])
        T.writes(compute_intermediate[v_i0, v_i1])
        compute_intermediate[v_i0, v_i1] = T.max(T_add_intermediate[v_i0, v_i1], T.float32(0.0))

T.grid gives the iteration space, SS marks both axes as spatial, and T.reads/writes declare which buffers each block touches. Even without knowing TVMScript, the last assignment of each block tells the story: the first pass writes all of lv+bias, and the second reads it back for ReLU. The scale loop and the final add loop follow.

So at this stage, the function boundaries have merged, but not a single loop. Fusing just the elementwise part would look more like this pseudocode:

for i in range(B):
    for j in range(D):
        z = Z[i, j]
        Y[i, j] = max(z + bias[j], 0) + 0.125 * z

One scalar z would serve both branches, and none of the three intermediate matrices would need to be stored. Go one step further and put this logic in the matmul’s epilogue, and z comes straight from the accumulator, saving even the write and re-read of ZZZ. Each step has different preconditions. In this artifact, function merging has happened; elementwise loop fusion and a GEMM epilogue haven’t.

These observations come from static-fused-fusion.py, IR from just before LLVM. Later optimization can still change storage and instructions, so the buffer count here isn’t a measured DRAM access count, and it doesn’t show that no TVM backend can fuse this graph. Target, pass configuration, schedule and version all change the result. What this artifact shows is how far one specific compilation path got.

Less traffic doesn’t mean proportional speedup, either. The matmul’s reads of X,WX,WX,W and its 2BD22BD^22BD2-scale compute stay. CPU caches catch some temporary matrices between adjacent stages. And cramming too much into one kernel can change register pressure and vectorization. The next step would be to schedule the generated loops, then measure runtime and real memory behavior. This experiment did no CPU performance tuning and doesn’t compare this CPU code against hand-written CUDA.

What the saved IR does give is a testable target: eliminate three intermediate matrices and several separate passes. If you only watch operator count go from five to two, it’s easy to report an optimization that hasn’t happened yet as a gain you already have.

Stage 3: a symbolic batch dimension

None of this computation needs BBB at compile time. Replace the input type’s first dimension 32 with a symbolic batch, and the shape relationships of the matmul, broadcast and branch join are still determined. Constant folding and CSE counts don’t change either, since they don’t need to know how many rows there are.

With a more general WWW of shape D×HD\times HD×H:

[B,D]×[D,H]⟶[B,H],[B,H]+[H]⟶[B,H].[B,D]\times[D,H]\longrightarrow[B,H],\qquad [B,H]+[H]\longrightarrow[B,H].[B,D]×[D,H]⟶[B,H],[B,H]+[H]⟶[B,H].

A dynamic first dimension isn’t an arbitrary shape: the reduction dimension must match, the bias width must equal HHH and the two branches’ outputs must be compatible. That information helps the compiler plan storage and gives the runtime entry the means to reject bad input. Type relationships can’t prove low-level address safety, but they do stop a 63-column matrix from going into a computation built for 64.

The actual runs produced four LLVM CPU .so files: static and symbolic batch, each with base and explicit fusion. The symbolic version was compiled once and run at B=1,7,32,129B=1,7,32,129B=1,7,32,129; the static version at B=32B=32B=32. The last build steps:

with tvm.target.Target("llvm"):
    lowered = relax.get_pipeline("default")(mod)
executable = relax.build(lowered, target="llvm", relax_pipeline=None)
executable.export_library("model.so")
vm = relax.VirtualMachine(executable, tvm.cpu())
actual = vm["main"](tvm.runtime.tensor(x, tvm.cpu())).numpy()

relax_pipeline=None is there because the script already ran and saved the lowering explicitly, and shouldn’t run the same pipeline twice. The exported library was reloaded, a new VM built and fed the same input, and the outputs matched the pre-export ones bit for bit.

There’s a small trap in the reference values. b0+b1b_0+b_1b0​+b1​ was already added in FP32 during folding, so an independent reference has to take that FP32 bias, together with the actually stored X,WX,WX,W, and promote everything to FP64. Adding the two biases in FP64 from the start erases a rounding step that really exists in the program, and then you’re not comparing the same thing.

The symbolic version also has a shape_func. Counting it, base and fused have six and three PrimFuncs; the five and two from before counted only tensor-compute functions. Forget the shape function and “how many functions were generated” has two answers.

What changes here is loop bounds, not the data dependency graph, which is a different kind of dynamism from “look at an intermediate result, then decide how many iterations to run.” Relay handles more general programs with conditionals, recursion and type structure, which explains why a high-level IR is more than operators wired together. These four libraries don’t exercise recursive control flow, though, so symbolic batch working doesn’t vouch for those capabilities.

Stage 4: int8 changes what equivalence means

Everything so far (folding, sharing, fusion) aims to preserve the program’s semantics. Lowering to int8 is different: it deliberately changes the represented values, introducing rounding and saturation. That boundary has to be visible to the compiler, or an innocent-looking arithmetic reordering can change the result.

Keep the same Z=XWZ=XWZ=XW and use symmetric quantization:

q(z)=clip⁡(round⁡(z/s),−127,127),z^=sq(z),q(z)=\operatorname{clip}(\operatorname{round}(z/s),-127,127), \qquad \hat z=sq(z),q(z)=clip(round(z/s),−127,127),z^=sq(z),

then feed the same Z^\hat ZZ^ to both the bias/ReLU and scale branches. The quantization point sits at the shared point, so both consumers see the same represented values. If each branch quantized separately with different scales, that would be a different program, and the original sharing relationship wouldn’t apply.

A smaller sss resolves ordinary values more finely and saturates large ones sooner; a larger sss widens the range and coarsens the rounding step for ordinary values. Fusion doesn’t make that trade-off go away. In general q(a+b)q(a+b)q(a+b) can’t be swapped for q(a)+q(b)q(a)+q(b)q(a)+q(b), and a saturation point can’t be moved across freely. Relay splits quantization into annotation, calibration and realization so these numerical decisions connect with later compiler transforms (Relay §4.2).

To see how much the calibration target matters, an independent NumPy experiment built a 256×64256\times64256×64 FP32 input and 64×6464\times6464×64 weight, with input row 0 deliberately scaled up 20×. Only ZZZ is quantized, both downstream branches use dequantized values, and final YYY is compared. These are constructed inputs, not activations sampled from a real model, and the four TVM CPU libraries weren’t run in int8.

Measured over all rows, the error cares most about preserving the amplified row 0, so max calibration wins. Measured over ordinary rows, the 99.5th percentile wins, and widening the range further loses precision. A tiny clipping fraction isn’t enough on its own either: 0.1038% counts elements, not the clipped magnitude, and overall output error is still 22.1182%.

There’s no model accuracy here to tell us which threshold is better. What the experiment shows is that the calibration criterion has to match what you evaluate. A compiler can merge an already-decided quantized computation into fewer loops, but fusion can’t decide for the application whether to preserve outliers or ordinary values.

What this does and doesn’t show

  • It shows, from saved IR, that constant folding and CSE work as expected (seven ops to five, one shared ZZZ), and that explicit fusion merges five compute functions into two.
  • It shows that the fused elementwise function still allocates three 32×6432\times6432×64 intermediates and makes four separate passes, so the ideal traffic reduction from 10Q10Q10Q to 3Q3Q3Q or QQQ hasn’t happened in this artifact.
  • It shows that symbolic batch builds once and runs correctly at four batch sizes, with ten correct rejections.
  • It shows, on constructed data, that the int8 calibration threshold that’s “best” depends on which rows you evaluate.
  • It doesn’t measure runtime, DRAM traffic or hardware counters, doesn’t tune schedules, doesn’t run TVM in int8 and doesn’t reproduce the Relay paper’s benchmarks.

Conclusion

Whether this one line of math is ready to deploy breaks into three separately answerable questions:

  1. Was the duplicated multiply eliminated? Yes, and the IR proves it.
  2. Do the generated loops make extra passes over intermediates? Yes: three buffers and four passes are still there after “fusion.”
  3. Does the chosen numerical representation still serve the task? That depends on the calibration target, as the int8 experiment shows.

Reading compiler artifacts this way gets closer to the optimization actually being done than remembering which passes ran.

“Fused” is a claim about function boundaries; whether the loops and buffers went with them is something you have to open the IR to see.

Environment and entry points

Measured on WSL2 Ubuntu, Python 3.12.3, NumPy 2.5.4 and Apache TVM 0.27.0.post1, targeting LLVM CPU. bench_mur/editorial/style-v2/systems_tvm_cpu/bootstrap.sh installs pinned dependencies, and run.sh runs experiment.py, saving the four libraries, IR at each stage, inputs/outputs and rejection diagnostics. Results are in rep_mur/blog-rewrite/style-v2/systems/tvm-cpu/; the loop analysis corresponds to static-fused-fusion.py there.

Material boundaries

IR printouts omit constant metadata, and constants are saved separately as NPZ, so the full program can’t be rebuilt from the printouts alone; rebuild from experiment.py. This version uses TensorType; don’t copy TensorStructInfo from other versions’ examples. Export and reload were verified in the same environment; cross-version and cross-machine compatibility weren’t tested.

The quantization and ideal-traffic ledger come from bench_mur/systems/relay_design_evidence.py, with results stored separately in rep_mur/blog-rewrite/systems/relay/; they’re not results from a TVM int8 backend. Real CPU outputs were re-checked through an independent NumPy path by systems_tvm_plot.py.

The Relay paper’s performance experiments ran on a Threadripper 1950X, Titan V and similar, with different devices, runtimes and batch sizes for vision and NLP. Its pass ablations reflect incremental effects under the combined configurations of the time and can’t be used to attach a speedup to this Relax CPU artifact. This post didn’t rerun the paper’s model accuracy or performance benchmarks, and didn’t sample CPU memory-access hardware counters.

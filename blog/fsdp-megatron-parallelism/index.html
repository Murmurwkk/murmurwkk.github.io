Megatron vs. FSDP, Derived from a Two-Layer MLP

A 7B model's training state is 104 GiB on its own. Shard the state or shard the computation: deriving what tensor parallelism and FSDP each save and where their communication comes from.

更新于 2026/11/6 · 8 个章节
#FSDP#Megatron#tensor parallelism#distributed training#paper deep dive

Take a 7B-parameter model. Account for each parameter at the usual 16 bytes for mixed-precision Adam, and the model state alone is 104.31 GiB. You have eight GPUs. One training step has to be split across them somehow.

There are two fundamentally different ways to do it, and they save memory in different places:

  • Shard the state. Each GPU stores one-eighth of the weights. When a layer is needed, the full weights are gathered, and each GPU processes different samples. This saves the memory spent storing model state.
  • Shard the computation. The weights stay split from start to finish. All eight GPUs compute the same sample’s matrix multiplies together and sum partial results at the end. This splits the work in progress, not just the storage.

The first is FSDP (built on ZeRO); the second is Megatron-style tensor parallelism. They often appear in the same config file precisely because their communication happens in different places.

In this post we’ll follow one two-layer MLP through one full update, and at every step ask two questions: when does each array need to be complete, and when is a slice enough? That’s enough to derive tensor parallelism from scratch, then data parallelism and ZeRO. From there we’ll get FSDP’s parameter lifecycle and its memory/communication trade-offs, see how the two compose on a 2D device grid, and finish with pipeline parallelism and what it does to microbatch sizes.

The running example: one full update of an MLP

Rows are tokens, so the input is X∈Rn×hX\in\mathbb R^{n\times h}X∈Rn×h. The MLP widens from hhh to fff, applies an elementwise activation, and maps back to hhh:

Z=XA,H=ϕ(Z),Y=HB,Z=XA,\qquad H=\phi(Z),\qquad Y=HB,Z=XA,H=ϕ(Z),Y=HB, A∈Rh×f,B∈Rf×h,Y∈Rn×h.A\in\mathbb R^{h\times f},\qquad B\in\mathbb R^{f\times h},\qquad Y\in\mathbb R^{n\times h}.A∈Rh×f,B∈Rf×h,Y∈Rn×h.

Biases and dropout are omitted so we can see where communication comes from. In a Transformer, nnn usually merges microbatch size and sequence length, hhh is the hidden width and fff the intermediate width. ϕ\phiϕ can be GeLU or any elementwise function. What matters is that it doesn’t mix hidden channels; everything below depends on that one property.

In the backward pass, call the incoming gradient G=∂L/∂YG=\partial L/\partial YG=∂L/∂Y:

∂L∂B=H⊤G,D=(GB⊤)⊙ϕ′(Z),\frac{\partial L}{\partial B}=H^\top G,\qquad D=(GB^\top)\odot\phi'(Z),∂B∂L​=H⊤G,D=(GB⊤)⊙ϕ′(Z), ∂L∂A=X⊤D,∂L∂X=DA⊤.\frac{\partial L}{\partial A}=X^\top D,\qquad \frac{\partial L}{\partial X}=DA^\top.∂A∂L​=X⊤D,∂X∂L​=DA⊤.

The forward pass needs weights. The backward pass needs weights and some forward activations. The optimizer then modifies the weights. So GPU memory never holds just AAA and BBB: activations, gradients and optimizer state all have their own lifetimes.

Whether a way of splitting this is valid comes down to two things: what array does this GPU compute, and what operation fills in the missing part? Matching shapes don’t mean the math says to add them.

Tensor parallelism: split on both sides of the nonlinearity

Let’s start by splitting AAA along its output dimension:

A=[A0 A1 ⋯ AT−1],At∈Rh×(f/T).A=[A_0\ A_1\ \cdots\ A_{T-1}], \qquad A_t\in\mathbb R^{h\times(f/T)}.A=[A0​ A1​ ⋯ AT−1​],At​∈Rh×(f/T).

Every GPU has the full XXX and computes only its own group of hidden channels:

Zt=XAt,Ht=ϕ(Zt).Z_t=XA_t,\qquad H_t=\phi(Z_t).Zt​=XAt​,Ht​=ϕ(Zt​).

(In distributed programs one process is a rank; here, think one rank per GPU.) Because ϕ\phiϕ is elementwise, HtH_tHt​ needs nothing from other ranks’ ZZZ, so computation flows straight on to the second layer.

Split the second layer along its input dimension, at the same boundaries:

B=[B0B1⋮BT−1],Bt∈R(f/T)×h.B= \begin{bmatrix} B_0\\B_1\\\vdots\\B_{T-1} \end{bmatrix}, \qquad B_t\in\mathbb R^{(f/T)\times h}.B=​B0​B1​⋮BT−1​​​,Bt​∈R(f/T)×h.

Then

Y=HB=∑t=0T−1HtBt.Y=HB=\sum_{t=0}^{T-1}H_tB_t.Y=HB=t=0∑T−1​Ht​Bt​.

Each GPU’s HtBtH_tB_tHt​Bt​ is n×hn\times hn×h, but every element contains only some hidden channels’ contribution, so one sum is needed here. If the next layer needs the full YYY, that’s an AllReduce: reduce, then put the same result back on every GPU in the group. And the wide HHH between the two matmuls stays sharded the whole time; it never has to be gathered and re-split.

Figure 1: Megatron’s MLP split. N,H,FN,H,FN,H,F in the figure are n,h,fn,h,fn,h,f in the equations. Both paths compute on the same XXX with different intermediate channels; their outputs are partial results for the same tokens.1

Why not split both layers the same way? If the first layer split its input dimension, you’d get Z=Z0+Z1Z=Z_0+Z_1Z=Z0​+Z1​, and the nonlinearity immediately blocks independent computation:

ReLU⁡(1−2)=0,ReLU⁡(1)+ReLU⁡(−2)=1.\operatorname{ReLU}(1-2)=0, \qquad \operatorname{ReLU}(1)+\operatorname{ReLU}(-2)=1.ReLU(1−2)=0,ReLU(1)+ReLU(−2)=1.

Partial sums have to be collected before the activation. Column-parallel followed by row-parallel postpones the one reduction until after both layers. The communication’s location is dictated by the algebra, not by tuning.

Backward walks back through the same hidden channels. Each rank independently computes

∂L∂Bt=Ht⊤G,Dt=(GBt⊤)⊙ϕ′(XAt),\frac{\partial L}{\partial B_t}=H_t^\top G,\qquad D_t=(GB_t^\top)\odot\phi'(XA_t),∂Bt​∂L​=Ht⊤​G,Dt​=(GBt⊤​)⊙ϕ′(XAt​), ∂L∂At=X⊤Dt.\frac{\partial L}{\partial A_t}=X^\top D_t.∂At​∂L​=X⊤Dt​.

Only the input gradient needs a cross-shard sum:

∂L∂X=∑tDtAt⊤.\frac{\partial L}{\partial X}=\sum_tD_tA_t^\top.∂X∂L​=t∑​Dt​At⊤​.

Parameter gradients already line up with each rank’s own weight shard; only the input gradient carries partial contributions to merge.

📝 Note: The full GGG exists on several GPUs, but those are copies of one logical gradient. Replicating it TTT times isn’t the same as summing TTT independent losses. Each forward replication and reduction has a corresponding backward operation, and autodiff has to carry those semantics.1

I checked this algebra on CPU in FP64. XXX is 11×811\times811×8, the weights are 8×248\times248×24 and 24×824\times824×8, the intermediate channels are split four ways, and the activation is tanh so it’s easy to differentiate independently. These results only show the forward/backward split is correct; no cross-GPU communication was run and no four-GPU speedup was measured. (Original Megatron uses GeLU; tanh relies on the same elementwise property.)

Data parallelism: replicate the computation, not the state

Tensor parallelism has several GPUs jointly computing one input. To process more samples per step, you can instead replicate the whole computation and give each copy a different batch. The weights are logically identical; the gradients come from different samples.

With data-parallel degree DDD and equal data per group, the target gradient is

g=1D∑d=0D−1gd.g=\frac1D\sum_{d=0}^{D-1}g_d.g=D1​d=0∑D−1​gd​.

Compare this with the TP sum above. The object being reduced has changed: TP completes one operator’s hidden-channel contributions, while DP merges one parameter’s gradients across samples. And if each GPU computes a token-averaged loss with different effective token counts, the merge must be weighted by count; averaging per-GPU means silently changes the training objective.

Classic data parallelism has every replica store full weights, gradients and optimizer state. But plain Adam updates per coordinate:

mi←β1mi+(1−β1)gi,vi←β2vi+(1−β2)gi2.m_i\leftarrow\beta_1m_i+(1-\beta_1)g_i,\qquad v_i\leftarrow\beta_2v_i+(1-\beta_2)g_i^2.mi​←β1​mi​+(1−β1​)gi​,vi​←β2​vi​+(1−β2​)gi2​.

Bias correction and the parameter update are per coordinate too. A rank responsible for coordinate iii only needs the reduced gig_igi​ to maintain mim_imi​, viv_ivi​ and that parameter; it never needs other coordinates’ moments. That redundant replication is the first thing ZeRO eliminates.2

A typical mixed-precision Adam ledger per parameter: 2 bytes of low-precision weight, 2 bytes of gradient, 4 bytes of master weight and two 4-byte moments, for 16 bytes total. With fixed dtypes and PPP parameters:

What gets shardedModel state per GPU
Everything replicated16P16P16P
Optimizer state sharded(4+12/D)P(4+12/D)P(4+12/D)P
Gradients sharded too(2+14/D)P(2+14/D)P(2+14/D)P

For 7B parameters and eight-way data parallelism, the four rows are 104.31, 35.86, 24.45 and 13.04 GiB (parameters counted in decimal, GiB as 2302^{30}230 bytes). FP32 gradients, or an implementation without a separately resident low-precision weight, would change the ledger, and none of these rows include activations or temporary buffers.

Reducing and then keeping only the owner’s slice of the gradient is a ReduceScatter: merge contributions to each coordinate, then send different slices of the result to different ranks. Each owner then updates its parameter slice with its gradient slice, and the full Adam state never needs to reappear on every GPU.

Operations that need global information still need communication. Say two gradient shards are 3 and 4 and the global clipping threshold is 1. You must first compute the norm 32+42=5\sqrt{3^2+4^2}=532+42​=5 and scale to (0.6,0.8)(0.6,0.8)(0.6,0.8). Clipping each shard separately gives (1,1)(1,1)(1,1), which doesn’t even have the target norm. Overflow detection likewise requires all relevant ranks to agree on whether to skip the update.

FSDP: shards at rest, full weights in use

The optimizer can work on a slice of parameters. A matmul usually can’t. Back to XAXAXA: with only state sharding and no TP, a rank holds only a fragment of AAA and can’t do the full multiply. Before computing, it has to AllGather different parameter positions into the full AAA.

For fully sharded FSDP that reshards after forward, one parameter group’s lifecycle looks like this:

resident parameter shard
    ↓ AllGather
full parameters for forward
    ↓ free full parameters
resident shard + activations needed by backward
    ↓ AllGather
full parameters for backward
    ↓ ReduceScatter
reduced gradient shard
    ↓ Adam
updated resident parameter shard

AllGather collects different parameter coordinates; ReduceScatter merges gradients from different samples. Both names contain gather/scatter, but the math is completely different. The FSDP2 docs describe full sharding with this lifecycle and represent parameters as DTensors, a different representation from the FlatParameter in the FSDP paper.3 The lifecycle is shared; the exact grouping and reshard behavior depend on the actual API.

The memory you forgot: full buffers

Resident state of 13 GiB doesn’t mean you can train in 13 GiB. Wrap the whole 7B model as one parameter group, and the full 2-byte weights need roughly another 13.04 GiB while in use. Finer sharding shrinks the resident shard further; it can’t shrink that full expansion.

So the size of each parameter group becomes a knob between memory and communication. At 350M parameters per group, a full buffer is about 0.652 GiB; computing one group while prefetching the next means two, about 1.304 GiB. Add activations, gradients and workspace to approach the real peak.

Let L(t)\mathcal L(t)L(t) be the set of full parameter groups alive at time ttt:

Mpeak=max⁡t[Mstate(t)+qp∑i∈L(t)Ui+Mactivation(t)+Mtemporary(t)].M_{\mathrm{peak}} =\max_t\left[ M_{\mathrm{state}}(t) +q_p\sum_{i\in\mathcal L(t)}U_i +M_{\mathrm{activation}}(t) +M_{\mathrm{temporary}}(t) \right].Mpeak​=tmax​​Mstate​(t)+qp​i∈L(t)∑​Ui​+Mactivation​(t)+Mtemporary​(t)​.

UiU_iUi​ is the number of parameters in group iii and qpq_pqp​ the bytes per expanded parameter, assuming the expanded buffer and resident shard are separate copies. Implementations that reuse storage need to subtract the overlap, and an allocator’s reserved memory already includes part of allocated, so it can’t be added in again wholesale.

Figure 3: Budgets computed under the conventions above, excluding activation peaks. With the whole model as one group there’s no “next group,” so “current group” and “plus one prefetched” bars are the same height.

Finer groups mean smaller full buffers and more collectives. At 25M per group, 7B needs 280 groups; with two gathers and one reduce-scatter each, that’s 840 collectives per step. At 350M per group it’s 20 groups and 60 collectives. The same bytes split into many small operations raise launch and management overhead, and shrink the compute window available to overlap communication.

Prefetching: earlier isn’t always better

Prefetching isn’t “earlier is better” either. Gathering weights early means compute waits less, but it extends the full buffers’ lifetimes; too many overlapping buffers can force the allocator to wait or reclaim. The FSDP paper trained GPT-175B on A100 80 GB over the stated 2 Tb/s RoCE network, with BF16, Adam, activation checkpointing and block length 2048. In its 128–512 GPU, batch 1/2 experiments, 128 GPUs at batch 2 hit allocator pressure. Rate-limiting over-commitment helped there, but in Figure 6 RegNet barely benefited and DeepViT gained about 5% overhead.4

Those positive and negative results say the same thing: rate-limiting shortens memory lifetimes, and it can also leave communication unable to finish in time. Memory savings alone don’t predict step time.

Chorus schedules “when to prefetch” together with “whether forward’s full parameters should be kept for backward.”5 Here’s a toy version of why that has to be global. A stretch has only 16 MiB free; current group U and next group V need 10 MiB each. Keeping U saves a gather in backward, but then V can’t be materialized early. Each choice is locally worthwhile, and together they exceed the budget. In a stretch with 24 MiB of headroom, the combination works. Whether to keep something depends on the whole live interval, not just its next use.

That work profiles compute time and memory constraints and then schedules parameter materialization, with both ZeRO-style and SimpleFSDP implementations. Its main experiments use 4–16 A100 PCIe 40 GB GPUs, four per node with four 100 Gb/s RoCE links, plus a sensitivity analysis on four H800/NVLink GPUs. How much headroom you can squeeze out depends on those conditions; there’s no universal prefetch depth you can skip measuring.

Counting the bytes

We can also estimate communication volume. With parameter and gradient payloads of QQQ bytes each, ideal ring collectives and counting only bytes sent per rank, DDP’s single gradient AllReduce is

VDDP=2D−1DQ.V_{\mathrm{DDP}}=2\frac{D-1}{D}Q.VDDP​=2DD−1​Q.

Full sharding with release after forward does two AllGathers and one ReduceScatter:

VFSDP=3D−1DQ.V_{\mathrm{FSDP}}=3\frac{D-1}{D}Q.VFSDP​=3DD−1​Q.

That 1.5× comes from this particular lifecycle. Changing communication precision, keeping parameters, adding gradient accumulation or changing the sharding scheme all require recounting, and it certainly doesn’t mean step time is fixed at 50% more. If communication takes ccc and there’s aaa of independent compute to overlap with, you still wait at least max⁡(0,c−a)\max(0,c-a)max(0,c−a) even in the ideal case. Prefetching aims for data to arrive in time to be consumed; arriving earlier still isn’t necessarily faster.

Two dimensions: which axis is t and which is d?

Now stack both splits on the same MLP. Two-way data parallelism times four-way tensor parallelism gives eight devices labeled (d,t)(d,t)(d,t).

Fix ddd and vary ttt: that’s a TP group jointly processing one input. Fix ttt and vary ddd: that’s a DP/FSDP group holding the same hidden-channel shard while processing different data.

Device groupRelationship between tensorsWhat needs merging
Same ddd, different tttDifferent hidden channels of the same tokensPartial sums of outputs and input gradients
Same ttt, different dddData replicas of the same logical weight shardParameter gradients from different samples

TP defines the logical weights At,BtA_t,B_tAt​,Bt​ first. FSDP then shards the storage of that slice, and what it gathers before computing is still At,BtA_t,B_tAt​,Bt​; it never reassembles all ttt channels back into the full layer.

It’s worth keeping this distinction explicit in code. Both arrays are n×hn\times hn×h: one is a partial result for the same tokens, the other is a complete result for different tokens. The communication library doesn’t know the semantics, so with the wrong process group, every shape check still passes.

This is why TP solves something FSDP alone can’t: when the full weights of a required compute unit are still too big, TP splits them along the compute dimension. The cost is a reduction inside each layer, on the critical path, almost every layer. Putting TP across a slow link and letting parameter prefetch cross the same link put the waiting in completely different places.

Pipeline parallelism: move layers, and the microbatch count moves with them

One more situation: each layer fits, but all the layers plus their state still don’t fit on one group of devices. Assign consecutive layers to different stages and pass inputs through them in sequence; that’s pipeline parallelism. A TP group from earlier can be one stage’s internal team.

With a single input, later stages wait for earlier ones’ results, and in backward earlier stages wait for later ones’ gradients, so most of the cluster is idle. Split a batch into multiple microbatches and different microbatches can be in different stages at once. They’re still one parameter update; the optimizer runs after gradients are accumulated.

A slot model with balanced stages and free communication gives the shape. With KKK stages, mmm microbatches and unit slot τ\tauτ, useful work is mτm\taumτ and the fill/drain bubble is (K−1)τ(K-1)\tau(K−1)τ:

TbubbleTuseful=K−1m,TbubbleTtotal=K−1m+K−1.\frac{T_{\mathrm{bubble}}}{T_{\mathrm{useful}}} =\frac{K-1}{m}, \qquad \frac{T_{\mathrm{bubble}}}{T_{\mathrm{total}}} =\frac{K-1}{m+K-1}.Tuseful​Tbubble​​=mK−1​,Ttotal​Tbubble​​=m+K−1K−1​.

Different denominators give different percentages, so say which one you’re quoting. Real 1F1B and interleaved schedules also deal with forward/backward time differences, communication, activation storage and stage imbalance; this model only shows which way the microbatch count pushes.

With bbb samples per microbatch, the global batch is

Bglobal=Dmb.B_{\mathrm{global}}=Dmb.Bglobal​=Dmb.

TP and PP don’t appear in this product; they cooperate on the same data. Fix the global batch at 128 with DP=4 and PP=8, raise bbb from 1 to 8, and the microbatch count mmm falls from 32 to 4, while the ideal bubble share of total time rises from 17.95% to 63.64%.

Figure 4: Ideal bubble fraction vs. microbatch size at a fixed global batch.

Big microbatches fill the matmuls better; small ones fill the pipeline better. Both pressures act on the same config. Raising the global batch to get more microbatches also changes how many samples each update aggregates and the optimization trajectory, so it’s not an unconditional systems speedup.

FSDP’s release policy adds another term. Release full parameters after every microbatch and the next microbatch may need to gather again; keep them and communication drops but lifetimes grow. Two configurations that are each the most memory-efficient on their own aren’t necessarily best together.

Megatron’s large-scale results are exactly an allocation of these axes. In the paper’s Table 1, the 1008B model runs on 3072 A100 80 GB GPUs with TP=8 and PP=64, so DP=6, with global batch 3072, sequence length 2048, 128 layers, hidden width 25600 and 160 attention heads. On Selene, the eight GPUs in a node use NVLink/NVSwitch, and each node has eight 200 Gbit/s InfiniBand NICs. That configuration measured 163 TFLOP/s per GPU, about 502 PFLOP/s total.6

TP=8 matches the fast in-node interconnect, PP carries most of the layer partitioning, and DP scales sample throughput. These are training-iteration throughputs; the same paper’s 84 days is a projected full run on 450B tokens. The FLOP count includes activation recomputation, and the table changes model, batch size and GPU count together, so it’s weak scaling and can’t be read as strong scaling (same model, more GPUs).

Conclusion

Back to the MLP one last time. A training step is always the same set of mathematical operations:

  • partial sums over different hidden channels have to be completed;
  • gradients from different samples have to be merged with the right weights;
  • Adam’s state has to line up with parameter coordinates.

TP, FSDP and PP change where those objects live and when they appear. Once the correspondence is clear, an OOM or a stall has a specific meaning: a required operator is too big, too many full parameter copies are alive at once, or the pipeline doesn’t have enough microbatches. Each calls for changing something different.

Every parallelism strategy is an answer to one question: when does this array need to be whole?

Reproducing the numerical checks and budget figures

Environment and method

Entry point:

py -3.13 bench_mur/systems/training_parallel_evidence.py

It runs full and sharded forward/backward for the two-layer MLP plus finite-difference checks, and computes the state budgets and ideal pipeline bubbles, with the full implementation as reference. In the materials directory rep_mur/blog-rewrite/systems/training/, tp_inputs.npz holds the first input set and tp_equivalence.csv the 32 error sets. Three budget CSVs back the state, parameter-group and pipeline figures, and run.json records environment and script hashes.

All of this runs on CPU. No 7B model was loaded and no multi-process FSDP/Megatron training was run. The papers’ multi-GPU throughput was not reproduced locally, and the budget figures don’t measure activations, allocators or real networks.

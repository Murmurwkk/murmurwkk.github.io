Six TensorRT Engines from One Linear Layer

One MatMul → Add → Relu graph, built six ways in FP32 and FP16. Which shapes each engine accepts, where FP16 overflows, and what a reused execution context really costs per call.

更新于 2026/11/6 · 6 个章节
#TensorRT#dynamic shapes#numerical precision#GPU experiments

Take one set of weights and one tiny MatMul → Add → Relu graph, and build six TensorRT engines from it: a wide-range one, a two-segment one and one pinned to exactly 64 rows, each in FP32 and in FP16.

Writing the plan file to disk is just the beginning. Each engine still has to answer three questions, and each answer comes with its own checks:

  1. Which shapes does it accept?
  2. Can FP16 still hold this graph’s results?
  3. Can one execution context be reused, and what does each call actually cost?

Whether fixed shapes or half precision are faster is something to measure, not assume; all six engines are measured here. All experiments ran on an RTX 5070 Laptop (SM120) under Windows 11, using the official TensorRT 10.14.1.48.post1 CU13 Windows wheel, so APIs and numerical behavior are tied to that version. The graph is small enough to follow by hand, including computing exactly where it overflows.

We’ll start with the model, the build and a check of the ONNX path, then take the three questions in order: profile constraints and a shape the setters accept but execution rejects; FP16 overflow and how to separate representation error from execution error; and the lifecycle cost from plan file to steady-state calls.

The model and the build

The model is

Y=ReLU⁡(XW+R),X,R∈RM×64,W∈R64×64.Y=\operatorname{ReLU}(XW+R),\qquad X,R\in\mathbb R^{M\times64},\quad W\in\mathbb R^{64\times64}.Y=ReLU(XW+R),X,R∈RM×64,W∈R64×64.

MMM is the request’s row count and can vary; width is fixed at 64. RRR is added elementwise and must have the same shape; it isn’t a length-64 broadcast bias. Inputs and outputs are contiguous row-major.

Most weight columns are drawn from a fixed-seed normal with standard deviation 1/81/81/8. The first column is all ones and the second alternates +1,−1+1,-1+1,−1. The first makes the accumulation range easy to compute by hand; the second makes it easy to see error when nearly equal inputs cancel. All six engines share the same original FP32 weights, converted to the storage type only when building FP16.

The network code maps one-to-one onto the formula. Names and logging are omitted; dt is trt.float32 or trt.float16, and weight is a NumPy array of the matching type:

flags = 1 << int(trt.NetworkDefinitionCreationFlag.STRONGLY_TYPED)
network = builder.create_network(flags)
x = network.add_input("x", dt, (-1, 64))
r = network.add_input("residual", dt, (-1, 64))
x.set_dimension_name(0, "rows")
r.set_dimension_name(0, "rows")

w = network.add_constant(weight.shape, weight).get_output(0)
z = network.add_matrix_multiply(
    x, trt.MatrixOperation.NONE, w, trt.MatrixOperation.NONE).get_output(0)
u = network.add_elementwise(z, r, trt.ElementWiseOperation.SUM).get_output(0)
y = network.add_activation(u, trt.ActivationType.RELU).get_output(0)
y.name = "y"
network.mark_output(y)

-1 leaves room for the row count at runtime, and rows declares that both inputs share that dimension. The graph only describes the computation; it doesn’t provide an execution plan for every shape. The builder also needs an optimization profile bounding the dynamic dimension’s min, opt and max. Here that’s M=1/64/512M=1/64/512M=1/64/512, called wide below:

profile = builder.create_optimization_profile()
profile.set_shape("x", (1, 64), (64, 64), (512, 64))
profile.set_shape("residual", (1, 64), (64, 64), (512, 64))
config.add_optimization_profile(profile)
config.clear_flag(trt.BuilderFlag.TF32)
serialized = builder.build_serialized_network(network, config)

The serialized engine keeps the choices made at build time. After loading, an execution context holds the dynamic state a particular run needs. With dynamic shapes, the two are cleanly separated: the network and weights can be reused, while request row count, bound addresses and execution resources live in a specific context.

A request has to select a profile, set both input shapes, infer the output shape, bind actual device addresses and submit. Below, tx,tr,ty are pre-allocated CUDA tensors and stream is their stream:

assert context.set_optimization_profile_async(profile_id, stream.cuda_stream)
assert context.set_input_shape("x", tuple(tx.shape))
assert context.set_input_shape("residual", tuple(tr.shape))
assert not context.infer_shapes()
assert tuple(context.get_tensor_shape("y")) == tuple(ty.shape)

for name, tensor in [("x", tx), ("residual", tr), ("y", ty)]:
    assert context.set_tensor_address(name, tensor.data_ptr())
assert context.execute_async_v3(stream.cuda_stream)
stream.synchronize()

The script uses PyTorch to manage CUDA storage, streams and events, and TensorRT for compute. A raw pointer carries no dtype, stride or allocation length. Before binding, the caller has to guarantee all three match the engine’s contract and keep the tensor alive until the device is done. Pass an FP32 pointer to an FP16 engine and nothing converts it for you.

Checking the ONNX path

A real model would typically be built through the ONNX parser, with the same build and execution responsibilities on the caller’s side. So the same MatMul → Add → Relu graph was also saved with ONNX 1.19.1, weights as initializers, inputs declared ['rows',64], opset 18, IR version 9. The file passed the checker, went to the parser, and was built into an FP32 wide engine.

This path doesn’t go through torch.onnx, so it validates only the ONNX file, parsing and TensorRT execution, not other exporters. Full outputs at seven row counts (1,3,17,64,65,257,5121,3,17,64,65,257,5121,3,17,64,65,257,512) were compared with both the ONNX CPU ReferenceEvaluator and an independent FP64 formula. Max error against FP64 ranged from 4.242×10−74.242\times10^{-7}4.242×10−7 to 7.585×10−67.585\times10^{-6}7.585×10−6, and max difference against ONNX CPU was 7.629×10−67.629\times10^{-6}7.629×10−6, all finite and within the FP32 budget.

Figure 1: The ONNX-parsed engine against FP64 and ONNX CPU references.

After the parser reports success there’s still a full output to check. A parser accepting a file doesn’t prove the parsed computation matches the math you mean to deploy.

Question 1: which shapes does an engine accept?

With wide in hand, two more profile schemes make the comparison. Split uses two profiles for small and large row counts; fixed accepts only 64 rows. Each comes in FP32 and FP16, for six engines total.

SchemeMin MMMOpt MMMMax MMM
wide164512

The opt size is one target point for the builder’s choice of implementation; it doesn’t mean every size in range was tuned separately. Some tactics are only available when min, opt and max are equal, so fixed and wide may get completely different implementations. Profiles should follow the real request distribution, and slogans like “wider is more convenient” or “narrower is faster” don’t hold in general (dynamic shapes docs).

The constraint the profile doesn’t show

A profile only bounds each input individually. In this graph the two inputs must also satisfy MX=MRM_X=M_RMX​=MR​. With profile ppp selected, the real admission domain is

Dp={(X,R):Mmin⁡,p≤MX=MR≤Mmax⁡,p,KX=KR=64}.\mathcal D_p=\left\{(X,R): M_{\min,p}\le M_X=M_R\le M_{\max,p},\quad K_X=K_R=64 \right\}.Dp​={(X,R):Mmin,p​≤MX​=MR​≤Mmax,p​,KX​=KR​=64}.

Figure 2: Drawn for split profile 0. The rectangle holds combinations where each row count is individually legal; the network only accepts the diagonal. (7,9)(7,9)(7,9) is inside the rectangle and off the diagonal. That point is a real rejection experiment; the figure isn’t a sweep of every integer point.

Here’s the surprising part. Setting XXX to 7 rows and RRR to 9, both set_input_shape calls return true. Only at execute_async_v3 does the shared-dimension relation fail, and execution returns false. A caller that treats the setters as success may go on to read whatever the previous call left in a reused output buffer.

Other errors are caught earlier: 0 or 513 rows for wide/split, 63 columns for any scheme, and 63 or 65 rows for fixed are all rejected when setting the shape. Across the six engines that’s 22 shape-rejection checks. The application entry point already knows both tensors’ shapes, so it can reject mismatches up front, and still check the backend’s final return status.

The two APIs’ return conventions mustn’t be mixed up either. In this version, build-time IOptimizationProfile.set_shape returns None on success and throws on inconsistency, while runtime IExecutionContext.set_input_shape returns a boolean. A uniform assert set_shape(...) would treat a successful build as a failure (Profile API).

Question 2: does FP16 hold the answer?

Both precisions use strongly typed graphs. The FP32 version has FP32 inputs, weights, residual and output; the FP16 version has all FP16; TF32 is explicitly disabled. That keeps the comparison clean: storage types are fixed in the graph, not a “prefer FP16 if you can” hint to the builder.

Storage type still doesn’t mean every internal step rounds in that type. Matmuls change accumulation, and the residual and activation may be fused after the multiply. The saved engine inspector output shows wide FP32 keeps an independent GEMM followed by a fused residual-add-plus-ReLU, while wide FP16 fuses GEMM, residual and ReLU together. Both also include shape logic, so inspector entry counts aren’t kernel launch counts (Engine Inspector).

FP16 tactic names contain f16f16 and tensor16x8x16; the FP32 GEMM name contains ffma. These names trace build choices, but they don’t give dynamic instruction counts or Tensor Core utilization, and an sm80 string in them doesn’t tell you the architecture (the hardware is SM120). No dynamic instruction sampling was done for these engines, so the performance mechanism stops at that evidence gap.

An overflow you can compute by hand

Output overflow doesn’t require guessing internals. Set every element of XXX to 2000 and R=0R=0R=0; with the first weight column all ones,

Yi0=ReLU⁡(∑k=0632000×1)=128000.Y_{i0}=\operatorname{ReLU}\left(\sum_{k=0}^{63}2000\times1\right)=128000.Yi0​=ReLU(k=0∑63​2000×1)=128000.

2000, 0 and 1 are all exactly representable in FP16, but 128000 exceeds FP16’s maximum finite value of 65504. However precise the internal accumulation, the result can’t be stored as a finite FP16. Shrinking the profile’s maximum row count doesn’t help: each row accumulates 64 terms independently, and MMM doesn’t enter at all (numeric range notes).

In the actual runs, all six FP16 configurations submitted successfully and produced positive infinity in the entire first column; at 512 rows that’s 512 non-finite outputs. FP32 keeps 128000. Across the six directly built engines, four input patterns and each engine’s legal test shapes, there are 120 cases: 105 finite results pass the diagnostic budget, and 15 FP16 overflows are kept as numeric-range failures, not rewritten as usable output because they were expected.

If a model really has to handle magnitudes like this, it needs a wider type at the right place, or scaling/normalization where the model allows it. Guaranteeing finite inputs is nowhere near enough; operator outputs and accumulation ranges are part of the type decision too.

Two references, two kinds of error

Finite results need two references. The FP16 engine reads inputs and weights that are already rounded, so comparing directly against the original FP32 model mixes representation change with execution error. With ϕ\phiϕ for ReLU, define

Y0=ϕ(XW+R),Ys=ϕ(XsWs+Rs),Y_0=\phi(XW+R),\qquad Y_s=\phi(X_sW_s+R_s),Y0​=ϕ(XW+R),Ys​=ϕ(Xs​Ws​+Rs​),

both computed in FP64. Y0Y_0Y0​ uses the original FP32 stored values; YsY_sYs​ first rounds to the engine’s actual storage type, then promotes to FP64. With engine output Y^\widehat YY, elementwise

Erepr=Ys−Y0,Eexec=Y^−Ys,Etotal=Erepr+Eexec.E_{repr}=Y_s-Y_0,\quad E_{exec}=\widehat Y-Y_s,\quad E_{total}=E_{repr}+E_{exec}.Erepr​=Ys​−Y0​,Eexec​=Y−Ys​,Etotal​=Erepr​+Eexec​.

Figure 3: The two references and how the total error splits between them.

The first term is how much the stored inputs, weights and residual changed things; the second is how much the actual arithmetic and output rounding added once those stored values are fixed. The two can reinforce or cancel, so the sum of their squared RMSEs generally isn’t the total’s squared RMSE.

Expanding the representation change before the activation:

ΔZ=XΔW+ΔXW+ΔXΔW+ΔR.\Delta Z=X\Delta W+\Delta XW+\Delta X\Delta W+\Delta R.ΔZ=XΔW+ΔXW+ΔXΔW+ΔR.

The same weight rounding is amplified by input magnitude, and the alternating second column makes nearly equal inputs cancel, which exposes rounding on small results. ReLU is 1-Lipschitz in absolute difference but crushes every negative to zero, hiding part of the pre-activation difference, so looking only at the final output can’t localize error layer by layer.

These are this experiment’s numeric tolerances, not a task-accuracy standard.

Question 3: what does a call cost?

Only once the numeric range is settled does it make sense to ask what a call costs. TensorRT’s lifecycle includes at least build, deserialization, context creation, shape and address binding, first execution and steady-state execution. “The model is cached” doesn’t say which of those are done.

Build and plan size

Each of the six engines was built once, with an empty timing cache, a 64 MiB workspace cap and optimization level 3. Wide FP32 took 5.575 s with a 63652-byte plan; wide FP16 took 8.353 s with a 140660-byte plan. FP16 weights are smaller, yet the file is bigger, because the plan also contains execution implementations and other data; weight bytes don’t predict plan size.

Split FP32/FP16 are 122044/263620 bytes, enlarged by two profiles; fixed is 65060/148236 bytes. Build order was fixed and each has one sample, so these seconds can’t rank profile build efficiency. The builder times candidate implementations one by one; keeping the actual plan and timing cache is what lets you trace its choices (build reproducibility).

Context memory is reported on its own terms. Wide and split FP32 report 131072 B and fixed reports 18432 B; split’s two profiles report 16384 B and 131072 B, and a default context has to account for the largest. All three FP16 engines report 0 B. That excludes inputs, outputs, weights, the CUDA context and runtime libraries, so it doesn’t mean the process uses no GPU memory.

From plan file to first call

After loading the file, whether a request has to build a context makes a visible difference. The experiment gave each engine a fresh process, recording import, CUDA init, deserialization, context creation, binding and first execution. For wide:

These stages exclude input generation, allocation and transfer, so summing the table as an end-to-end request is wrong. The OS and display driver were already running, so it’s not a machine cold start, and with one fresh-process sample per engine, it’s certainly not a cold-start P99.

Even with a warm process and engine, a fresh execution context alone costs a first submission: at 64 rows, 348.1 μs for wide FP32 and 299.3 μs for wide FP16. Saving the plan but rebuilding the context per request still leaves a noticeable stage before steady-state calls.

Figure 5: First submissions use host timing and wait for completion; steady batches are CUDA event intervals divided by 100. They show the order of magnitude of lifecycle cost and shouldn’t be divided to announce a kernel speedup.

Keeping a context doesn’t make shape changes free, either. In one diagnostic switching from 64 to 257 rows, split has to change profile: FP32 setup took 3.484 ms and the next execution 219.6 μs; FP16 took 6.692 ms and 299.1 μs. Wide doesn’t change profile, with setup around 0.120/0.113 ms. Setup here includes profile selection, shape inference and address binding, with few samples, so the difference can’t be pinned precisely on one profile API.

Steady-state time within one bucket doesn’t represent a request stream that keeps crossing buckets, and the docs state that execution has to update related resources after shape or profile changes (shape-change overhead). Bucketing buys better-suited implementations at the price of routing and switching; which side wins can only be measured on the real request sequence.

The last set has all resources in place. Fixed FP32 doesn’t win, and FP16 wide and split are nearly identical. At 512 rows, wide/split are 26.73/27.04 μs for FP32 and 21.73/17.57 μs for FP16. A difference at one point doesn’t establish that bucketing is always faster.

Figure 6: Steady-state per-call time across schemes and precisions.

Host submission time hugs the event interval, which says this small graph’s measurement is strongly limited by submission supply. Events time the stream, Python still issues each execution individually, and gaps where the GPU has finished and the next call hasn’t arrived count in the interval too. So 20 μs can’t be read as pure device time for GEMM plus activation.

The FP16 graph also changes storage type and fusion boundaries at the same time. Without a timeline and dynamic counters, the difference can’t be decomposed further into Tensor Cores, memory traffic and fewer launches. That part of the performance mechanism remains unmeasured, and inspector tactic names can’t fill it in.

What this does and doesn’t show

  • It shows that a mismatched shared dimension can pass both shape setters and only fail at execution, and that the shape APIs’ return conventions differ between build and runtime.
  • It shows a hand-computable FP16 overflow (128000 > 65504) on all six FP16 configurations, kept as 15 failures among 120 cases, and splits finite error into representation and execution parts.
  • It shows the lifecycle cost of a fresh process, a fresh context and a profile switch, and that steady-state differences between profile schemes are small and overlapping for this graph.
  • It doesn’t measure dynamic instruction counts or Tensor Core utilization, so performance mechanisms are untested.
  • It covers one tiny graph on one GPU and TensorRT 10.14.1; FP16 ONNX, other exporters, version changes and cross-machine plan compatibility weren’t tested.

Conclusion

Let’s recap the three questions. Which shapes an engine accepts is decided by profiles and by graph-level dimension relationships, and the second can slip past the shape setters. Whether FP16 holds the answer depends on output and accumulation range, not just input range, and finite error splits cleanly into what representation changed and what execution added. What a call costs depends on which lifecycle stages a request actually pays for. A fresh context or a profile switch can cost more than the steady-state call itself.

In practice: if requests recur at fixed shapes, reuse a prepared context and measure that; if they cross buckets often, put switching back into the request path when you measure; and if inputs can produce results like 128000, fix the type range before chasing microseconds. The APIs and numeric behavior here are tied to TensorRT 10.14.1 and need re-checking on other versions; plans weren’t built with extra compatibility modes, and cross-system or cross-machine compatibility wasn’t verified (release notes, support matrix).

An engine that builds is a promise about shapes and types; checking every return value and every output is how you find out whether it keeps it.

Environment and measurement method

Windows 11, RTX 5070 Laptop SM120 (8151 MiB), driver 610.88, Python 3.13.5, PyTorch 2.14.1+cu130, TensorRT 10.14.1.48.post1 official CU13 Windows wheel. Process runtime and driver API both report 13030. The experiments didn’t invoke nvcc; the installed Toolkit 13.1 doesn’t mean TensorRT compiled anything with it.

Both precisions use strongly typed graphs with TF32 disabled, a 64 MiB workspace cap, optimization level 3, one timing iteration per tactic, and an empty timing cache per engine. No other team tasks ran on the GPU during experiments, and the display GPU wasn’t clock-locked.

Entry points and records

Builds, 22 rejections, 120 numerical checks, six fresh processes and 1320 steady batches come from bench_mur/tensorrt/run.py, cold.py and plot.py, recorded in rep_mur/blog-rewrite/tensorrt/.

bench_mur/editorial/style-v2/tensorrt_outputs.py reruns the six engines’ 120 numerical cases plus seven ONNX cases, saving inputs, weights, residuals and full outputs, 127 arrays in all, in rep_mur/blog-rewrite/style-v2/tensorrt/. An independent check accumulates 64-column outer products without calling the original reference helper, confirming that 112 finite cases meet the budget and 15 FP16 overflows stay failures; profile latency wasn’t re-measured.

The ONNX engine build took 8.408 s, one sample; FP16 ONNX and other exporters weren’t tested. Source files, weights, engines and arrays all have SHA-256 hashes. run.py --output can target a new directory, but cold.py and plot.py don’t inherit it automatically, so reruns should use one path to avoid mixing old and new engines and timings.

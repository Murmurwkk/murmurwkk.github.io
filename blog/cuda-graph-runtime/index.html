CUDA Graphs Save Launches, Not Work

A graph cut a four-kernel attention chain from 33 μs to 12 μs on the GPU, yet the smallest full request got slower. What capture saves, what it binds, and when replay pays off.

更新于 2026/11/6 · 7 个章节
#CUDA Graph#Attention#RAII#Selective Scan#inference runtime

CUDA Graphs merge many kernel launches into one replay. On a four-kernel attention chain, that takes the device interval from about 33 μs down to about 12 μs, a 2.7× win. Then you include copying inputs in and results out, and for the smallest shape the full request gets slower.

Both of those numbers are real, and the gap between them is what this post is about. Two things are easy to skip over:

  • A graph saves submission work, not computation. How much time it saves depends on what the GPU was waiting for before.
  • Graph nodes store the device addresses from capture time. Whether those addresses still point to the right buffers on later replays is the program’s responsibility, not CUDA’s.

For one replay to actually run correctly, the graph has to be built in advance, the addresses have to stay alive, and the next input mustn’t overwrite one that’s still being read.

The setup: two explicit implementations, one that launches four kernels individually and one that captures those same four launches into a graph. The test subject is single-head dense attention with no causal or padding mask. All GPU experiments ran on an RTX 5070 Laptop (SM120), and the conclusions cover only these two implementations and the listed shapes.

We’ll start with the test subject and what capture records, then pin down the address semantics with an experiment. After that we’ll measure device time against full-request time and the cost of building a graph, and finish with resource lifetimes: how to free memory safely while the GPU is still working, tested on a multi-stage Selective Scan.

The test subject: four-kernel materialized attention

Inputs are contiguous FP32 Q∈RM×dQ\in\mathbb R^{M\times d}Q∈RM×d and K,V∈RN×dK,V\in\mathbb R^{N\times d}K,V∈RN×d, and the output is

O=softmax⁡(QKTd)V.O=\operatorname{softmax}\left(\frac{QK^T}{\sqrt d}\right)V.O=softmax(d​QKT​)V.

MMM is the number of queries, NNN the number of keys/values and ddd the vector width. The implementation takes a deliberately observable, materialized path: transpose KKK, compute scores, row-wise softmax, then multiply by VVV. All four kernels run on the caller’s stream:

transpose K → QK / sqrt(d) → row softmax → PV

The transpose buffer needs NdNdNd floats and the score buffer MNMNMN, for a workspace of 4(Nd+MN)4(Nd+MN)4(Nd+MN) bytes. Softmax overwrites scores with probabilities in place, and PV consumes the probability matrix. Normal submission issues four launches every call; the graph version captures the same entry point, with the same algorithm and the same intermediate tensors.

Why not use online (flash-style) attention? Because it doesn’t fully materialize the probability matrix, which changes kernel count, memory traffic and compute organization all at once, and then a performance difference can’t be pinned on the graph alone. The entry point used here, attention_materialized_launch, takes ready-made inputs, outputs and workspace, and doesn’t allocate or synchronize internally, so submission style can be compared in isolation.

Fundamentals: what capture records

A normal call hands operations to CUDA one at a time. However small the four kernels are, the host has to prepare arguments and submit each one, and the GPU may idle between them waiting for the next to arrive. A graph does that repeated preparation up front. Capture produces a description of nodes and dependencies, instantiation produces an executable instance, and from then on one launch submits the whole workflow (CUDA Graph programming guide).

The minimal skeleton, with error checks omitted and all pointers allocated before capture:

cudaStreamBeginCapture(stream, cudaStreamCaptureModeThreadLocal);
attention_materialized_launch(q, k, v, out, M, N, d,
                              score, kt, stream);
cudaStreamEndCapture(stream, &graph);
cudaGraphInstantiate(&exec, graph, 0);

// Can be launched repeatedly afterwards; on the same stream, update inputs first, then run the graph.
upload_current_inputs(stream);
cudaGraphLaunch(exec, stream);

graph is a description and exec a prepared execution instance. Neither is an output, and neither stores data for anyone. Single-stream capture fixes the order: softmax only after scores are ready, PV only after probabilities are ready. The test counts exactly four nodes in the graph, to guard against the entry point submitting on another stream and capturing something unexpected.

Capture also has an error path to handle. If a C++ exception is thrown after BeginCapture, the stream doesn’t leave capture mode just because local variables unwind. The implementation tracks capture state, ends capture and discards the useless graph on the exception branch; a targeted test throws after submitting four nodes and confirms that capture works again after cleanup. Capturing again into an object that already holds a graph is rejected, so an old handle can’t be silently overwritten (capture invalidation and termination).

Graph nodes store addresses, not variables

Here’s the semantic that matters most. A normal launch reads its function arguments every time; capture stores the arguments as they were in the graph node. Say q points to address A at capture time. Later you change a C++ variable to address B. The graph node knows nothing about that and keeps reading A on every replay. But it re-reads A’s contents each time, so writing new data into A does produce new results.

Figure 1: The graph node holds the address captured at A; reassigning the host pointer to B doesn’t reach it.

Three operations separate these semantics. First, keep the Q/K/V addresses fixed, write inputs from seeds 0, 17 and 42 in turn, and check each replay against an independent CPU FP64 attention. Then leave A’s contents alone, allocate a separate, still-live B, and point the member query_input used by normal submission at B:

query_input = alternative_q;
cudaGraphLaunch(exec, stream); // node arguments still point at A from capture time

direct();                     // the normal call reads the current query_input, i.e. B

The graph gets old Q with old K/V; the normal call gets new Q with old K/V; both pass their respective reference checks. Finally, restore the pointer member and write seed-99 contents into the original allocation, and the graph produces the correct result for the new input. The result tracks the data, so this isn’t a cached output.

📝 Note: Always using the same input can hide another bug. If the very first computation already filled the output correctly, a timed “graph” that never actually ran would keep passing validation by reading the last correct value. SOL-ExecBench §4.4.1 documents a case like this, where CuTe DSL didn’t pass the capture stream to the kernel. (The paper’s B200 performance isn’t compared with this laptop GPU.) (paper case)

Designing around fixed addresses

Since addresses get baked in, the wrapper changes shape too. A Request holds a stream, Q/K/V/O, both workspaces, the graph and the exec, for one fixed (M,N,d)(M,N,d)(M,N,d). New input just updates storage and replays; a different shape is rejected by the entry point before copying, and gets its own instance. These fixed shape buckets trade generality for a guarantee that graph and storage can’t get out of sync during argument updates.

CUDA Graphs do support qualifying argument and structural updates, so you’re not limited to one shape per graph; this post just doesn’t implement that update protocol. The graph update constraints also mean you need a re-instantiation fallback when an update fails. If you cache several fixed instances, the cache key needs more than shape: dtype, layout, operator or weight version and workspace requirements all have to be part of it.

Concurrency raises a storage-identity problem. If two same-shape requests share one score buffer, B’s QK may overwrite A’s freshly written scores before A’s softmax reads them. In-graph dependencies can be perfectly correct and still not protect memory shared outside the graph.

The experiment gives two 4×127×324\times127\times324×127×32 requests their own streams, execs and full storage, interleaves 20 rounds of submissions, and gets a maximum absolute error of 3.86×10−83.86\times10^{-8}3.86×10−8. That checks isolation, not how much the two requests actually overlap. And one cudaGraphExec_t launched on two streams can’t stand in for this design: launches of the same exec are ordered after that exec’s previous launch and can’t run concurrently with themselves (Runtime Graph API).

Measuring it: device interval vs. full request

On the RTX 5070 Laptop, Nsight Systems recorded both submission styles. The data comes from CUDA/CUPTI events: three consecutive normal calls and three replays after skipping the first execution, each zeroed at the first kernel and drawn on a shared time scale. Colors are transpose, QK, softmax and PV.

All four event intervals shrink; two of the four full requests don’t benefit. For the smallest shape, normal end-to-end ranges 104.60–120.35 μs against the graph’s 114.55–118.30 μs, overlapping ranges. For the largest, 120.95–130.20 μs against 133.00–138.25 μs. Copies, synchronization and host activity are on the critical path, and this experiment didn’t decompose them further, so the slowdown can’t be pinned on any one API.

A CUDA event interval also isn’t the sum of kernel durations. Time when the start event has fired and the next kernel hasn’t been submitted yet, with the device idle, counts too. Conversely, a host batch average includes both submission and waiting, and submission can overlap device compute, so the two can’t simply be added. The clock is on the GPU; that doesn’t mean every microsecond of the interval is spent on floating-point work.

So which number is yours? For a decode sub-chain with inputs already on the GPU, the event numbers are the direct signal. For an interface that copies full Q/K/V from the CPU every time, the last two columns are closer to the real cost. Real serving also has queues, variable sequence lengths, KV addresses and request routing, none of which are implemented here, so a fixed-request event speedup doesn’t convert directly into goodput.

Call preparation plus first execution CCC, and the saving per steady-state reuse ΔT=Tdirect−Tgraph\Delta T=T_{direct}-T_{graph}ΔT=Tdirect​−Tgraph​. The rough break-even count is

R=CΔT,ΔT>0.R=\frac{C}{\Delta T},\qquad\Delta T>0.R=ΔTC​,ΔT>0.

Using host batch-average differences as the denominator gives about 1.23, 1.24, 1.44 and 2.78 reuses for the four shapes. That counts the useful first execution as cost, so it’s conservative, and no per-request cumulative crossover was measured. Using end-to-end differences is more direct, and for the two shapes that didn’t benefit, there’s no finite crossover at all.

So a graph cache should be reserved for instances that recur and actually benefit. A shape seen once may not be worth a graph, and keeping many shapes alive ties up static buffers. Preparation cost, where inputs live and cache footprint have to be decided together.

Lifetimes: when is the GPU actually done?

cudaGraphLaunch returning only means the work was submitted, not that the graph’s last PV finished. The graph holds device addresses but doesn’t gain C++ ownership of those allocations. If a wrapper object is destroyed after launch returns and frees Q/K/V or the score buffer, still-running nodes will read freed memory.

For a long-lived fixed-request object, the simplest and safest answer is fine: the destructor waits on its own stream, then destroys exec, graph and storage. It’s reused for the life of the service and isn’t destroyed per request, so blocking the host once at shutdown is acceptable. The pinned host buffers in the end-to-end test are owned the same way and freed only after waiting on the relevant stream; otherwise an H2D or D2H could still touch freed host memory during exception unwinding.

Stream-ordered workspaces

Short-lived workspaces are a different case. Synchronizing and freeing a temporary workspace at the end of every operator call would artificially break up a chain of asynchronous submissions. Device memory release can instead be enqueued on a stream: allocate, initialize, compute, then submit cudaFreeAsync. The host may leave scope before the device finishes, but memory reuse can’t jump ahead of earlier consumers (stream-ordered allocator).

This is a separate implementation from the waiting Request above. OrderedWorkspace, built to test this policy, is move-only (no copies) and holds an allocation plus one chain of completion dependencies. A move transfers the pointer and the responsibility to free it, not device data. The destructor submits the free at the end of the dependency chain; an explicit close() can report errors, while the destructor only records cleanup failures and doesn’t throw.

Using a workspace across streams needs one more event edge. handoff(next) records an event on the old stream, makes the new stream wait on it, then hands responsibility for the eventual release to the new stream:

Figure 5: Handing a workspace from one stream to another.

If A and B borrow the workspace simultaneously, remembering which stream the most recent host call used isn’t enough. All outstanding uses have to converge onto one completion chain before the release can follow. This wrapper supports only serial handoff; it doesn’t try to infer when arbitrary parallel borrowing ends.

Testing it on a multi-stage consumer: Selective Scan

To make early unwinding cover a multi-stage device consumer, the lifetime experiment uses a zero-initialized Selective Scan:

hb,t,d,s=eΔb,t,dAd,shb,t−1,d,s+Δb,t,dBb,t,sub,t,d,h_{b,t,d,s}=e^{\Delta_{b,t,d}A_{d,s}}h_{b,t-1,d,s} +\Delta_{b,t,d}B_{b,t,s}u_{b,t,d},hb,t,d,s​=eΔb,t,d​Ad,s​hb,t−1,d,s​+Δb,t,d​Bb,t,s​ub,t,d​, yb,t,d=∑sCb,t,shb,t,d,s+Ddub,t,d,hb,−1,d,s=0.y_{b,t,d}=\sum_s C_{b,t,s}h_{b,t,d,s}+D_du_{b,t,d}, \qquad h_{b,-1,d,s}=0.yb,t,d​=s∑​Cb,t,s​hb,t,d,s​+Dd​ub,t,d​,hb,−1,d,s​=0.

b,t,d,sb,t,d,sb,t,d,s index batch, time, channel and state; uuu is the input, Δ\DeltaΔ a positive step, AAA governs state transition, BBB couples input into state, CCC reads state out, and DDD is the direct input-to-output term. The experiment uses negative AAA and positive Δ\DeltaΔ and verifies only this zero-initialized recurrence. It doesn’t implement cross-request state continuation and isn’t full Mamba inference.

The implementation computes per-chunk affine summaries, propagates prefixes, then recomputes and reduces outputs, so the workspace is read and written by several kernels in turn. The test size is batch 2, length 513, 3 channels and 33 states, split into three time chunks, one prefix group and two state tiles, for a 32,000-byte workspace after 256-byte alignment.

The tests cover four cases: leaving scope after a move, cross-stream handoff, throwing after submission, and calling close twice. All four match a time-recursive CPU FP64 reference with maximum absolute error 4.8432×10−84.8432\times10^{-8}4.8432×10−8, and each case does exactly one allocation and one release submission with zero cleanup errors. The moved-from object is nulled, and closing twice doesn’t free twice.

To reliably open the window where the host has returned but the device hasn’t finished, the test inserts an artificial 20,000,000-GPU-cycle delay before the work. In all four profiler-free cases, querying the completion event after scope exit returns “not finished.” The delay exists only to create an observable window and isn’t part of any Scan performance result.

Figure 6: Purple is the CPU submitting the release, gray the artificial delay, orange the last use.

This figure uses separate small initialization and consumption kernels to spread the window out, instead of the Scan’s stages crowding together. The last use completes safely after the free API returns because the release is ordered after it. That doesn’t show physical memory was returned to the OS; when the pool returns pages wasn’t measured, and length 513 doesn’t reach the over-1024-chunk long-sequence boundary of the Scan.

memcheck, racecheck and synccheck all report zero issues on both the Graph and Scan paths. Cross-stream global memory ordering still depends on the dependencies above; racecheck mainly checks shared-memory hazards. Streams, the context and any optional audit objects also have to outlive the workspace: once the context is destroyed, the resource class has no chance to issue a legal release.

What this does and doesn’t show

  • It shows that graph replay cuts this four-kernel chain’s device interval by 2.4–2.9× on all four shapes, and that graph nodes bind capture-time addresses while re-reading their contents.
  • It shows that once host copies and synchronization are included, two of four shapes get slower, and that break-even after preparation is only a few reuses where there’s any benefit at all.
  • It shows that stream-ordered release with explicit cross-stream handoff keeps a multi-kernel workspace valid after the host returns, with zero sanitizer reports.
  • It doesn’t decompose the end-to-end slowdown into specific API costs, and doesn’t measure real serving goodput, queueing or variable-length requests.
  • It doesn’t implement graph argument/structure updates, parallel borrowing of one workspace or memory-pool page return.

Conclusion

Let’s recap. A CUDA Graph saves submission work, so it shines when the GPU was idling between small launches, and it does nothing for copies and synchronization sitting on the critical path. Capture binds addresses, not variables, so the program owns the guarantee that those addresses stay alive and hold the right data. That shapes everything from fixed shape buckets to per-request storage. And because launch returning doesn’t mean the device is done, every buffer needs an owner that either waits or orders its release after the last consumer.

A graph remembers where your data was; making sure it’s still there, and still yours, is your job.

Steady-state compute warms up 20 times, then a pilot picks a batch of about 20 ms, up to 4000 iterations; 30 batches per round, 3 rounds, with modes interleaved. Each round’s median is taken, then the median of three rounds; ranges in the figures are the min to max of the three round medians. End-to-end warms up 5 times per round and measures 30 requests, also over three rounds.

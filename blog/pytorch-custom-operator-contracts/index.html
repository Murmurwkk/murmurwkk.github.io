A Custom SwiGLU Op in PyTorch: Everything but the Kernel

The SwiGLU kernel is one sigmoid and one multiply. Shipping it means handling offset views, the current stream, autograd and FakeTensor, each of which can break it on its own.

更新于 2026/11/6 · 8 个章节
#PyTorch#CUDA#SwiGLU#autograd#operator integration

The elementwise part of SwiGLU does exactly two things: one sigmoid and one multiply. Writing that kernel is the easy part. Whether the operator can actually ship depends on four requirements PyTorch places on it:

  1. The tensor may come from an offset view.
  2. The call won’t necessarily be on the default stream.
  3. Training needs to differentiate through the output.
  4. At compile time, there’s no real data at all.

None of these appear in the gating formula, and any one of them can make the kernel unusable.

The scope is pinned down first: only contiguous FP32 [2,N] tensors on CUDA, with the gate values in the first row and the gated values in the second, returning a freshly allocated [N]. The forward is hand-written CUDA; the backward stays as differentiable PyTorch operations. That way what one fusion saves stays visible, and the information the framework needs can be filled in piece by piece.

We’ll start with the layout and a scalar kernel, then add a vector path and see why “contiguous” isn’t the same as “aligned.” After that comes registration with PyTorch on the right stream, a backward pass that needs no new kernel, and FakeTensor support for compilation. Last, we’ll measure where the fused version’s time actually goes.

Fundamentals: laying out the two inputs

A SwiGLU feed-forward layer has two linear projections. Call their results aaa and bbb; the computation is

yi=SiLU⁡(ai)bi=aiσ(ai)bi,σ(a)=11+e−a.y_i=\operatorname{SiLU}(a_i)b_i =a_i\sigma(a_i)b_i,\qquad \sigma(a)=\frac{1}{1+e^{-a}}.yi​=SiLU(ai​)bi​=ai​σ(ai​)bi​,σ(a)=1+e−a1​.

Both projections and the output projection that follows are outside this operator, so the performance numbers below cover only the elementwise gate, not an FFN speedup. The full layer in the SwiGLU paper should be read with the same scope in mind.

Packing into [2,N] means a0,…,aN−1a_0,\ldots,a_{N-1}a0​,…,aN−1​ sit contiguously in the first half and b0,…,bN−1b_0,\ldots,b_{N-1}b0​,…,bN−1​ in the second. Output iii reads x[i] and x[N+i].

In [N,2], by contrast, the paired values are usually x[2*i] and x[2*i+1]. Same element count, completely different meaning.

Figure 1: Same element count, different pairing.

A real model’s projection output may also be [batch,tokens,2*hidden], with the two halves inside each token. The total length matches, but it can’t be treated as this [2,N]: after flattening, the two halves usually don’t each occupy half of the whole storage. Supporting that layout would mean computing per-row halves or explicitly paying for a reorder. I chose the two-row layout to make the interface and execution relationship explicit; it can’t directly accept every model’s projection output.

Here’s the formula with scalar access first. n is always the per-half length:

__device__ __forceinline__ float silu_times(float a, float b) {
    float e = __expf(-fabsf(a));
    float s = a >= 0.f ? 1.f / (1.f + e) : e / (1.f + e);
    return (a * s) * b;
}

__global__ void swiglu_scalar(const float* x, float* out, int64_t n) {
    for (int64_t i = int64_t(blockIdx.x) * blockDim.x + threadIdx.x;
         i < n; i += int64_t(blockDim.x) * gridDim.x) {
        out[i] = silu_times(x[i], x[n + i]);
    }
}

Why not just write 1 / (1 + exp(-a))? For a very negative aaa, the sigmoid’s answer is near zero, but the intermediate e−ae^{-a}e−a can overflow first. Taking e=e−∣a∣e=e^{-|a|}e=e−∣a∣ and computing 1/(1+e)1/(1+e)1/(1+e) or e/(1+e)e/(1+e)e/(1+e) on each side keeps that intermediate stable. The final product can still exceed FP32, and the fast exponential __expf has approximation error, so this isn’t an implementation that promises finite results for every floating-point input.

At the source level, each output reads two floats and writes one, an ideal traffic of 12N12N12N bytes. Computing SiLU and the multiply separately adds one more write and read of the intermediate, another 8N8N8N bytes. That’s a tensor-boundary budget; actual DRAM traffic also depends on caching. Fusion also collapses two calls into one, which for small NNN may matter more than the bytes saved.

Contiguous doesn’t mean 16-byte aligned

The scalar kernel works for any non-negative NNN. To read four adjacent values at once, add a vector version: each thread reads two float4s and computes four outputs. Now the question changes from “are the elements contiguous?” to “is this wide access’s address legal?”

What PyTorch calls contiguous is a relationship between strides and shape; it doesn’t require a view to start at the allocation’s first byte. For example:

N = 8
storage = torch.randn(2 * N + 8, device="cuda")
x = storage[1 : 1 + 2 * N].view(2, N)
assert x.is_contiguous()

There’s no gap between this tensor’s two rows, but its start is one float, 4 bytes, past the underlying allocation’s start. Force it into a float4* and 16-byte alignment is broken. reinterpret_cast only changes how a pointer is interpreted; it doesn’t move data.

So the vector version’s entry condition is

N mod 4=0,addr⁡(a) mod 16=addr⁡(b) mod 16=addr⁡(y) mod 16=0.N\bmod4=0,\qquad \operatorname{addr}(a)\bmod16= \operatorname{addr}(b)\bmod16= \operatorname{addr}(y)\bmod16=0.Nmod4=0,addr(a)mod16=addr(b)mod16=addr(y)mod16=0.

The second half starts at x+N, so it counts too, and the output’s raw pointer can’t be assumed aligned either. If any condition fails, the whole call falls back to the scalar version. There’s no vector body with scalar head and tail for a few edge elements; I’d rather a whole call be a bit slower and the scope be clear. CUDA’s device memory access rules state explicit natural-alignment requirements for this kind of access.

The host entry point is written accordingly:

cudaError_t swiglu_launch(const float* input, float* output,
                         int64_t total_elements, cudaStream_t stream);

total_elements is the combined count of both halves, divided by two inside the function. A negative or odd total is an error; zero returns success immediately without launching zero blocks; a non-empty task rejects null pointers. The function doesn’t allocate or synchronize, the caller provides input and output storage, and they may not overlap.

Bugs at this layer can be located with a very short comparison. The simplified entry being compared takes its length as total_elements/2 and decides on float4 by whether the length divides by four, checking neither odd totals nor pointer alignment. With total length 7, it “succeeds” on three values from each half and misses the last one. With total length 0, it tries to launch zero blocks and returns cudaErrorInvalidValue. On the one-float-offset input above, the launch itself succeeds, and only on completion does it report cudaErrorMisalignedAddress. Those three problems are in argument semantics, launch configuration and device access, and adding a tail loop fixes none of them.

The corrected entry ran 96 combinations of lengths and address offsets, with max absolute error 7.15×10−67.15\times10^{-6}7.15×10−6 and clean memcheck, racecheck and synccheck. The disassembly’s vector branch really does contain LDG.E.128 and STG.E.128, and the scalar branch LDG.E and STG.E. That only shows wide accesses were generated; it doesn’t give a speedup, since work per thread, number of parallel threads and actual call cost all change too.

From torch.ops to the current CUDA stream

The raw entry knows pointers, lengths and streams; PyTorch users only have tensors. In between sits a C++ function that checks the tensor’s semantics first, then submits the computation:

at::Tensor swiglu_cuda(const at::Tensor& x) {
    TORCH_CHECK(x.is_cuda(), "SwiGLU requires a CUDA tensor");
    TORCH_CHECK(x.scalar_type() == at::kFloat, "SwiGLU requires float32");
    TORCH_CHECK(x.dim() == 2 && x.size(0) == 2,
                "SwiGLU requires shape [2,N]");
    TORCH_CHECK(x.is_contiguous(), "SwiGLU requires contiguous [2,N]");

    c10::cuda::CUDAGuard guard(x.device());
    auto out = at::empty({x.size(1)}, x.options());
    const auto stream = c10::cuda::getCurrentCUDAStream(x.get_device());
    C10_CUDA_CHECK(swiglu_launch(x.const_data_ptr<float>(),
        out.mutable_data_ptr<float>(), x.numel(), stream.stream()));
    return out;
}

The output inherits the input’s device and dtype but gets new storage, leaving the input untouched. Non-contiguous tensors are rejected. Calling contiguous() internally instead would widen the interface, but adds a possible allocation and copy that timing would have to include. The contiguous offset slice from the previous section is legal, though, and the raw entry picks a safe access branch for it.

CUDAGuard and the current stream do two different jobs. The guard makes allocation and submission land on the input’s device. The current stream continues whatever order the caller has already set up on that device. A user can perfectly well produce x on a non-default stream and call the gate right after. As long as both are submitted to the same stream, the gate is ordered after the producer. Hard-coding the default stream would lose that order.

Figure 2: The wrong path in this figure reads input that hasn’t been updated yet.

A device-wide sync after the fact doesn’t help: it can wait for the wrong read to finish, but can’t make it not have happened. Consuming across streams needs events or waits to build the dependency, and storage borrowed by another stream has to follow the framework’s lifetime rules. An extension’s first job is to preserve the caller’s existing order; it can’t infer every external producer from a pointer (PyTorch stream semantics).

Registering with the dispatcher is what lets Python find it by operator name:

TORCH_LIBRARY(mur_swiglu, m) {
    m.def("forward(Tensor x) -> Tensor");
}
TORCH_LIBRARY_IMPL(mur_swiglu, CUDA, m) {
    m.impl("forward", TORCH_FN(swiglu_cuda));
}

The first block defines the schema; the second registers the CUDA implementation. The schema has no input-mutation or output-alias annotations, because the implementation really is out-of-place. The framework uses this information to check and transform programs, so a real in-place write can’t hide behind a signature claiming to be pure. Only CUDA dispatch is registered here; CPU tensors are out of scope (official C++/CUDA extension tutorial).

Once the extension library is loaded, torch.ops.mur_swiglu.forward(x) is callable. Training is still only half done, though: PyTorch sees a custom node and has no idea how to differentiate it.

Backward without another kernel

Write the upstream gradient as gi=∂L/∂yig_i=\partial L/\partial y_igi​=∂L/∂yi​. Since σ′(a)=σ(a)(1−σ(a))\sigma'(a)=\sigma(a)(1-\sigma(a))σ′(a)=σ(a)(1−σ(a)), the product rule on aσ(a)ba\sigma(a)baσ(a)b gives

∂L∂ai=gibiσ(ai)[1+ai(1−σ(ai))],∂L∂bi=giaiσ(ai).\frac{\partial L}{\partial a_i} =g_i b_i\sigma(a_i) \left[1+a_i(1-\sigma(a_i))\right], \qquad \frac{\partial L}{\partial b_i}=g_i a_i\sigma(a_i).∂ai​∂L​=gi​bi​σ(ai​)[1+ai​(1−σ(ai​))],∂bi​∂L​=gi​ai​σ(ai​).

Each output depends only on the two inputs at the same index, so the Jacobian has no cross-element coupling. Backward doesn’t need to build a matrix: multiply elementwise by the upstream gradient and put the two halves’ gradients back into [2,N].

def setup_context(ctx, inputs, output):
    (x,) = inputs
    ctx.save_for_backward(x)

def backward(ctx, grad):
    (x,) = ctx.saved_tensors
    a, b = x[0], x[1]
    s = torch.sigmoid(a)
    da = grad * b * s * (1 + a * (1 - s))
    db = grad * a * s
    return torch.stack((da, db), dim=0)

torch.library.register_autograd(
    "mur_swiglu::forward", backward, setup_context=setup_context)

What’s saved is a tensor, not a raw address pulled out of one. Backward needs the forward’s a,ba,ba,b, and save_for_backward both keeps the storage alive and participates in version checking. If the user modifies the input in place after forward, backward should raise a version mismatch; if it didn’t, it would compute “the derivative at the new input” and attach it to the old output’s graph. A targeted test does trigger that version error.

Figure 3: The forward is a custom node; the backward is ordinary PyTorch.

Leaving backward as PyTorch operations has another benefit: with higher-order gradients enabled, the framework can keep tracing. For a single output,

∂2y∂a2=bσ(a)(1−σ(a))[2+a(1−2σ(a))],\frac{\partial^2y}{\partial a^2} =b\sigma(a)(1-\sigma(a))[2+a(1-2\sigma(a))],∂a2∂2y​=bσ(a)(1−σ(a))[2+a(1−2σ(a))], ∂2y∂a∂b=σ(a)[1+a(1−σ(a))].\frac{\partial^2y}{\partial a\partial b} =\sigma(a)[1+a(1-\sigma(a))].∂a∂b∂2y​=σ(a)[1+a(1−σ(a))].

Second-order gradients differ from an independent FP64 reference by at most 8.39×10−88.39\times10^{-8}8.39×10−8. That doesn’t mean hand-written CUDA gets higher-order gradients for free; it’s because the registered backward is itself differentiable. Replace it with another opaque CUDA kernel and derivative support has to be added for that too.

A complete call:

from bench_mur.pytorch.extension import load_extension
import torch

custom = load_extension()  # compile and load the C++/CUDA code, and complete the Python registration
x = torch.randn(2, 33, device="cuda", requires_grad=True)
y = custom(x)
y.sum().backward()
assert y.shape == (33,)
assert x.grad.shape == (2, 33)

33 isn’t a multiple of four, but it’s a legal per-half length. This should take the scalar path and return both rows of gradients normally; a model’s legal shape shouldn’t change to suit float4.

FakeTensor only asks about shapes

Autograd handles derivatives; compile-time tracing also needs the output’s metadata. In a FakeTensor environment, inputs have shape, dtype and device, and no values for a CUDA kernel to read. This operator’s output length depends only on x.shape[1], so it can be registered separately:

@torch.library.register_fake("mur_swiglu::forward")
def fake(x):
    torch._check(x.device.type == "cuda")
    torch._check(x.dim() == 2)
    torch._check(x.shape[0] == 2)
    torch._check(x.dtype == torch.float32)
    torch._check(x.is_contiguous())
    return x.new_empty((x.shape[1],))

This function doesn’t call CUDA, read pointers or compute a sigmoid. It just tells the compiler that a legal input produces a new tensor on the same device, of the same type, with length NNN. Its checks have to match the real entry’s, or you get programs that compile and are then rejected at runtime. Operators whose output length depends on data can’t copy this; it works here because the interface already fixes the shape relationship (FakeTensor registration).

Registering a fake doesn’t expose the kernel’s sigmoid to the compiler. A compiled graph knowing how to connect this node isn’t the same as being able to fuse its internals with neighboring operators. In the test environment, aot_eager, fullgraph=True, dynamic=True ran forward and backward for N=17,33,65N=17,33,65N=17,33,65, with max differences of 1.19×10−71.19\times10^{-7}1.19×10−7 and 2.38×10−72.38\times10^{-7}2.38×10−7. The default Inductor backend failed with TritonMissing on both ordinary expressions and the custom operator. So this confirms AOT integration only. It can’t claim Inductor works, let alone use the eager baseline in place of a compiled-fusion baseline.

Different tests answer different questions. opcheck checks whether the schema, FakeTensor, autograd registration and AOT dispatch fit together; it doesn’t derive gradients for us. gradcheck checks numerical gradients by finite differences, and its default method targets double precision, while this interface only implements FP32. The experiment uses eps=0.001, atol=rtol=0.003 as an auxiliary check and keeps the non-double-precision warning. The main numerical evidence is still an independent forward and backward on the same FP32 inputs promoted to FP64 (opcheck and gradcheck).

Numerical tests cover N=0,1,3,4,7,8,31,32,33,257,1024,1025,65536N=0,1,3,4,7,8,31,32,33,257,1024,1025,65536N=0,1,3,4,7,8,31,32,33,257,1024,1025,65536, each at storage offsets of 0, 1, 2 and 3 floats, with both random gate values and gate values cycled from [−100,−40,−5,−0.1,0,0.1,5,40,100][-100,-40,-5,-0.1,0,0.1,5,40,100][−100,−40,−5,−0.1,0,0.1,5,40,100], 104 combinations in all. All four opcheck groups pass: empty input, odd NNN, aligned input and offset input. Seven unsupported inputs are explicitly rejected. Where the fused time actually goes

The performance comparison uses two clearly defined entries: custom(x) and F.silu(x[0]) * x[1]. Both include Python call, dispatcher and output allocation, and exclude compilation, input generation and host transfers; inputs don’t require gradients, so there’s no backward. Data comes from PyTorch 2.14.1+cu130 on an RTX 5070 Laptop.

Each group warms up 20 times, then runs three rounds of 30 batches, with 200 calls per batch for small lengths and 50 for large ones, alternating the two methods by round. CPU wall clock records the Python submission loop, and CUDA events record the same batch’s interval on the stream. Event intervals include device time spent waiting for the next host submission, so they can’t be written up as single-kernel execution time.

The start event has already reached the device while Python is still running the call loop, and the end event is enqueued only after the loop finishes submitting. That gap is real call cost, but it isn’t some CUDA computation that never happened.

Whether a very short kernel gets fed in time already sets the order of magnitude. Fusion really does cut framework work and intermediate tensors, and it really is faster, but the gain can’t all be credited to “sigmoid computes faster in CUDA.”

Ranges in the figures are the 5th to 95th percentiles of 90 batch means, not single-request tail latency; the laptop GPU wasn’t clock-locked and repeated inputs didn’t flush caches. One key comparison is still missing: compiler-fused F.silu(a) * b. Inductor didn’t run on this machine, so the existing data only answers “does hand-written fusion beat eager?”, not “is it still worth maintaining against the compiler?”

What this does and doesn’t show

  • It shows a custom operator that handles offset-but-contiguous views (scalar fallback), the caller’s current stream, autograd with version checking and second-order gradients, and FakeTensor shape propagation under aot_eager.
  • It shows three distinct entry-point bugs (odd length, zero-block launch, misaligned float4) that a tail loop alone wouldn’t fix, and 104 numerical cases passing against FP64.
  • It shows that the fused call is about 1.5–1.7× faster than eager for small and medium NNN, mostly through less framework work, and that unaligned inputs lose the vector path at large NNN.
  • It doesn’t run Inductor (it failed with TritonMissing), so there’s no compiled-fusion baseline. AMP, vmap, other dtypes, multi-GPU device switching and full-model training weren’t tested.

Conclusion

Let’s recap. The kernel was a few lines. Everything else was contract: a layout that says which elements pair, alignment checks that “contiguous” doesn’t imply, a launch on whatever stream the caller is using, a schema that tells the truth about mutation, a backward that saves tensors rather than pointers, and a fake that predicts output shape without data. Each of those has its own test, and none of them can be replaced by checking that one random output looks right.

A usable custom operator has to make these boundaries visible to its callers. What’s done here is FP32, the contiguous two-row layout, a CUDA forward and a traceable backward.

Writing the CUDA kernel is the smallest part of shipping a custom operator; the contract around it is the operator.

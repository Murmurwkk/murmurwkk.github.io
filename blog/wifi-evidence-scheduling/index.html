When Two Estimators Share One Observation

Giving a heading estimator first call on WiFi fixes cut the position filter's accepted fixes from 42 to 7 and never produced a heading correction. Shared evidence needs ownership, not just an order.

更新于 2026/11/6 · 9 个章节
#WiFi positioning#factor graphs#evidence scheduling#NIS#post-mortem

Our indoor navigation system has one WiFi positioning provider and two parts of the estimator that want its output. The position filter takes each WiFi fix as it arrives, checks it against the current prediction and, if it fits, adds a position constraint. The heading estimator collects a stretch of walking and several WiFi fixes, fits how the whole trajectory should be rotated, and only then decides whether to correct the heading.

The heading estimator needs time to build its case, and the position filter grabs every fix it can. So we tried what sounded like a reasonable change: give the heading estimator first call on each fix, and pass the position filter only what it didn’t take.

On the first walk we tested, the WiFi provider produced the same 90 fixes as always. The position filter accepted 7 of them instead of 42, and its first accepted fix came at 233.5 s instead of 85.0 s. The heading estimator, which the change was meant to help, never issued a single heading correction. Reverting the order brought the old results back exactly. A later version swung the other way: once the position filter had committed, the heading estimator stopped doing anything at all.

Both failures are bad answers to one design question, and that question is what this post is about: once one consumer has reserved or used an observation, when may another consumer still use it?

We’ll go through the three versions in order, with a small toy filter that reproduces the first failure. Then we’ll look at what goes wrong statistically when both consumers simply share every observation, and at the bookkeeping that would make sharing safe.

Two consumers, one stream of fixes

A WiFi fix passes through several stages before it changes the state, and each consumer has its own:

  • Position filter: routed to it → gated against the prediction → accepted → committed to the graph.
  • Heading estimator: routed to it → used to build a rotation hypothesis → used to confirm it → authorized → applied.

Any stage can stop a fix. Two runs with the same 90 fixes can end with very different numbers of constraints in the graph, and counts at different stages aren’t comparable: “56 fixes reached the position gate” and “7 were accepted” don’t contradict each other.

The gate is the standard one. For a fix ztz_tzt​ with noise covariance RtR_tRt​, compare it with the predicted state x^t−\hat x_t^-x^t−​:

νt=zt−Htx^t−,St=HtPt−HtT+Rt,dt2=νtTSt−1νt.\nu_t=z_t-H_t\hat x_t^-,\qquad S_t=H_tP_t^-H_t^T+R_t,\qquad d_t^2=\nu_t^TS_t^{-1}\nu_t .νt​=zt​−Ht​x^t−​,St​=Ht​Pt−​HtT​+Rt​,dt2​=νtT​St−1​νt​.

The position filter accepts the fix when the normalized innovation squared (NIS) dt2d_t^2dt2​ is at most 9.21, the 99% chi-square threshold for a 2D Gaussian innovation. Notice what the gate compares against: the current prediction, not the truth. That detail drives everything in the next section.

Why losing early fixes costs more than the fixes themselves

The arithmetic doesn’t add up the way you’d expect. On walk A, the heading estimator took 34 fixes and accepted position fixes fell by 35. On walk B it also took 34, and accepted fixes fell by only 18. Even the rejections moved: 49 on walk A under heading-first versus 48 before, although 34 fewer fixes reached the gate.

The early fixes explain it. On walk A, the fix at 85.0 s had an NIS of 7.085, comfortably inside the gate, and heading-first routed it away. On walk B, the fix at 76.0 s, with NIS 6.260, went the same way. Without those early corrections, the prediction x^t−\hat x_t^-x^t−​ drifts further from the truth. The next fix can be bit-for-bit identical and still fail the gate, because its innovation is now measured against a worse prediction.

A 1D toy makes the feedback visible. The truth and every observation are 0, but the filter’s motion model pushes the prediction forward by 0.8 per step. Initial variance is 0.25, process variance 0.1 per step, observation variance 1, and the gate stays at 9.21 (in 1D that number has no chi-square meaning; it’s just the same threshold). The observations are noise-free, so each run is deterministic.

Compare two rules over 20 steps. One checks position every step. The other reserves the first 6 steps for a heading estimator that never delivers, then lets position checks resume.

When the reserved rule opens the gate at step 7, the NIS is already 16.08, and every later observation is rejected. Six withheld observations turned into twenty lost ones. (The first rule still ends 2.16 away from the truth, because its motion model is wrong. Checking every fix doesn’t fix a bad model.)

The toy doesn’t reproduce walk A’s map, optimizer or noise, and it can’t divide walk A’s error among causes. It shows the mechanism exists: the same fixes and the same threshold don’t guarantee the same acceptances, because the gate’s reference point depends on which fixes came before.

From walk A alone you’d conclude “heading-first breaks positioning.” The two walks together support something narrower. Putting a slow consumer in front of a fast one on the same provider can break timing the fast one depended on, and how much it hurts depends on the trajectory and on which fixes come later.

Version 2: position-first restores the old behavior, failures included

The fix put the position filter back first. Every fix is gated by the position filter at its original NIS, and only fixes it rejects go to the heading estimator. A position acceptance cancels any heading correction in the same window that hasn’t been applied yet.

That restored the old outputs exactly. Across four walks (581, 416, 1,085 and 896 output rows), position-first and position-only trajectories differ by at most about 1.2×10−71.2\times10^{-7}1.2×10−7 m, with identical floor sequences.

Exactly the old behavior also means the old failures. On a harder walk, both runs reached only 9 position fixes, the first at 415.0 s, and the error at the last reference point went from 12.3 m without WiFi to 29.6 m with it. Restoring the order removed the regression; it didn’t fix walks the position filter had never handled well.

Notice how narrow this fix is. “The position filter sees each fix first” is one decision. “The heading estimator is barred for the rest of the walk” is a much broader one, and that’s where the next version went wrong.

Version 3: position locks out heading

The next version changed how the heading estimator built and confirmed its hypotheses. Under it, once the position filter had committed, the heading estimator stood down. On a long, difficult walk, the provider produced 194 fixes and 25 became position constraints. After the position filter committed, the heading estimator took zero further steps: no hypothesis, no confirmation, no correction.

Overall error got worse than not using WiFi at all: P75 / P90 went from 76.3 / 103.6 m to 93.3 / 120.8 m. That’s the mirror image of version 1. The position filter got its early fixes, and the slow path that could have recovered the heading never got another chance.

Two cautions. This version changed the heading estimator’s strategy as well as the priority behavior, with no ablation separating them, so not all of the regression belongs to the lock-out. And the error at the last reference point improved, from 6.7 m to 2.5 m. Pick the endpoint, the tail or the overall score, whichever looks best, and you can tell opposite success stories about the same run.

So priority needs a scope: one transaction, one stage that can be undone, or a state condition you can justify statistically. Shutting a consumer out permanently is a modeling decision, and it needs its own test of whether recovery is still possible.

The tempting fix: let both consumers see everything

If reserving fixes starves one consumer and locking out starves the other, why not hand every fix to both? Two readers of the same data are fine computationally. Statistically, you have to follow where the information ends up.

The simplest case shows why. Prior x∼N(0,4)x\sim\mathcal N(0,4)x∼N(0,4), one measurement z=2z=2z=2 with noise variance 1. Using it once:

P+=(14+1)−1=0.8,x^+=0.8×2=1.6.P^+=\left(\tfrac14+1\right)^{-1}=0.8,\qquad \hat x^+=0.8\times2=1.6 .P+=(41​+1)−1=0.8,x^+=0.8×2=1.6.

Now copy the measurement and treat the copy as independent:

P~+=(14+1+1)−1=49,x~+=49 (2+2)=169.\tilde P^+=\left(\tfrac14+1+1\right)^{-1}=\tfrac49, \qquad \tilde x^+=\tfrac49\,(2+2)=\tfrac{16}{9}.P~+=(41​+1+1)−1=94​,x~+=94​(2+2)=916​.

No new information arrived, and the reported variance fell from 0.8 to 0.44. The estimate also moved, from 1.6 to 1.78, toward a measurement it has effectively counted twice.

In navigation the copy is much better hidden. A WiFi fix first corrects the position filter’s trajectory. The heading estimator then fits a rotation to that corrected trajectory, against the same WiFi fixes, and sends the result back as an independent heading measurement. There are no duplicate measurement IDs anywhere. The duplication travels through the updated state, the shared fingerprint map and the common reference data.

So “can both consumers use this fix?” is really three questions:

  • Do the raw sources overlap? Do two derived measurements use the same scan or the same reference sample?
  • Does one estimate already contain the other’s information? Was the trajectory the heading estimator fits already corrected by fixes the position filter used?
  • Are the errors independent? Even with disjoint scans, fingerprint-map error, multipath and device bias are shared.

Disjoint raw sources answer the first question and say nothing about the third. Routing only position-rejected fixes to the heading estimator is also a selection on the data, and any test the heading estimator runs later has to account for it.

📝 Further reading: Cossette et al. (IJRR 2024, §3.2–3.3 and §4) treat the related problem of several estimators that represent the same physical state. Cross-correlation doesn’t vanish because the implementations are separate, and unknown correlation can be handled conservatively at the cost of using less information (paper).

In the exact-copy example, giving each copy half the information weight recovers the single-measurement answer. That works only because we know they’re the same measurement. Real overlap between the two consumers is partial and unknown, so it’s no basis for a general “halve everything” rule.

Ownership: reserve, commit, release

If fixes are going to be shared, sharing needs bookkeeping, not a boolean flag per consumer. Our ownership module had the right shape. A claim binds to the derived measurement and also to its lineage, its episode and the raw evidence it came from. A consumer can reserve several bindings together, commit them when they change the state, and release them if its attempt is cancelled.

The states mean different things, and the scheduler has to respect the difference:

  • Reserved: a consumer is holding the fix while it works.
  • Committed: the fix has changed the state.
  • Released: a cancelled attempt gives its unused reservations back before they go stale.

Record the observation time, processing time, reservation time and commit time separately as well. That’s the only way to tell a late correction apart from the state that was actually available when a decision was made.

Version 1 showed the cost of reservations that never pay off; version 3 showed the cost of permanent exclusivity. A policy that avoids both needs reservation deadlines and release conditions for the heading estimator, and position priority scoped to a clear transaction or stage. I haven’t built or validated that policy yet.

What a fair test of the next policy looks like

Freeze the fix sequence, the provider outputs, the error model, the thresholds and the scoring code, and change only the ownership policy. For every fix, record its raw source, whether the position filter gated it and with what NIS, any reservation and why it was released, which consumer finally used it, and when that use was committed. If the measurements or the model change along with the policy, the result belongs to the whole combination, not to scheduling.

The bar for “solved” is three conditions at once:

  1. Early position fixes are preserved.
  2. A heading estimator that needs to recover can keep collecting.
  3. A harmful heading correction is still refused.

Getting walk A back to 42 accepted fixes shows none of these on its own.

What this does and doesn’t show

  • It shows, from saved outputs, that heading-first cut walk A’s accepted position fixes from 42 to 7 with no heading correction issued, and that position-first matches position-only to about 10−710^{-7}10−7 m on four walks.
  • It shows, with a toy filter, that withholding early observations can make a gate reject every later one, and that counting one observation twice shrinks the reported variance with no new information.
  • The early NIS values, candidate digests and the version 3 lock-out come from saved run records. The full per-fix event stream wasn’t kept, so the causal chain in between can’t be fully re-verified.
  • Version 3 changed more than one thing, with no ablation.
  • Walk A has 10 reference points and walk B has 6. The quantiles describe these walks, not routes in general.

Conclusion

Putting the heading estimator first took walk A’s early, perfectly acceptable WiFi fixes away from the position filter. The prediction drifted, the gate rejected what came later, and 42 accepted fixes became 7, while the heading estimator still delivered nothing. Putting the position filter back first restored the old behavior exactly, old failures included. Making position priority permanent starved the heading estimator instead.

Underneath, it’s one problem. Two consumers of one observation need explicit ownership (reserve, commit, release), priority with a scope, and tracking of information that flows through the updated state rather than through measurement IDs.

Scheduling evidence is part of the statistical model: get it wrong and you’ve changed what the estimator believes, not just when it hears about it.

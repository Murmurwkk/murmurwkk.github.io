What Quantizing the KV Cache Costs in Speed and Accuracy

Fewer bytes per key don't guarantee faster attention: decoding, addressing and reductions can hand the savings back. One INT8 decode step measured, then how absmax, rotation and QJL change attention.

更新于 2026/11/6 · 8 个章节
#CUDA#KV Cache#quantization#TurboQuant#Attention

Every time a model generates its next token, attention reads the whole history again. Keys and values were computed in earlier steps and don’t need recomputing, but they still have to take part in the current query’s dot products and then the weighted sum. The longer the context, the bigger that cache; the more sequences running at once, the more copies sit in GPU memory.

Compressing K/V from floats to integers is the direct way to shrink it. But how much smaller the cache gets and how much faster attention gets are two different questions. How integers are decoded, which addresses neighboring threads read, how reductions are divided: each of these can hand the saved bytes right back. And lowering bit width changes attention weights too. A quantizer that reconstructs vectors well isn’t necessarily one that preserves the dot product the current query cares about.

So this post has two halves that use different encodings and can’t be combined into one end-to-end speedup number. The first half is measured on the GPU: one head, one layer, one stretch of valid history, with K/V stored as contiguous INT8 and output computed in FP32. It asks how much of the byte savings survive addressing and reductions. The second half is CPU numerical experiments asking how different encodings change attention output: absmax, random rotation with a spherical codebook, and a QJL residual.

What one decode step reads

Say there are NNN visible tokens, each key and value has ddd components, and the current query is q∈Rdq\in\mathbb R^dq∈Rd. The computation is

zt=1d∑j=0d−1qjkt,j,pt=exp⁡(zt−m)∑uexp⁡(zu−m),oj=∑t=0N−1ptvt,j,z_t=\frac{1}{\sqrt d}\sum_{j=0}^{d-1}q_jk_{t,j},\qquad p_t=\frac{\exp(z_t-m)}{\sum_u\exp(z_u-m)},\qquad o_j=\sum_{t=0}^{N-1}p_tv_{t,j},zt​=d​1​j=0∑d−1​qj​kt,j​,pt​=∑u​exp(zu​−m)exp(zt​−m)​,oj​=t=0∑N−1​pt​vt,j​,

with m=max⁡tztm=\max_tz_tm=maxt​zt​. Subtracting the max doesn’t change softmax’s proportions; it just keeps large positives out of the exponent. The first sum runs over channels and the last over historical tokens. Those two reductions go in different directions, and that’s what decides how threads are organized.

The cache stores kt,vtk_t,v_tkt​,vt​, not finished ptp_tpt​: next step’s query is different, so weights must be recomputed. This entry point takes only caller-filtered valid history and doesn’t handle masks, GQA head mapping, paged addressing or cache appends. With HHH heads, K/V are laid out contiguously as [H,N,d], with the last dimension adjacent.

The INT8 format

The most direct compression gives each token’s K and V vector its own scale. For one row xxx:

s=max⁡j∣xj∣127,cj=clip⁡(round⁡even(xj/s),−127,127),x^j=scj.s=\frac{\max_j|x_j|}{127},\qquad c_j=\operatorname{clip}\left(\operatorname{round}_{\rm even}(x_j/s),-127,127\right), \qquad \widehat x_j=sc_j.s=127maxj​∣xj​∣​,cj​=clip(roundeven​(xj​/s),−127,127),xj​=scj​.

Rounding is to nearest even, the integer range excludes −128-128−128, and a zero vector stores a zero scale with all-zero integers. Decoding means reading a signed byte, converting to float and multiplying by the scale. The scale itself is FP32, so validation has to use the stored copy, not slip in a recomputed high-precision value.

Figure 1: The scale fields are drawn enlarged.

At d=64d=64d=64, one FP16 K/V pair is 256 bytes, while the INT8 data is 128 bytes plus two FP32 scales, 136 bytes total. For HHH heads and NNN tokens:

BFP16=4HNd,BINT8=2HNd+8HN.B_{\rm FP16}=4HNd,\qquad B_{\rm INT8}=2HNd+8HN.BFP16​=4HNd,BINT8​=2HNd+8HN.

So at d=64d=64d=64 this INT8 format is really 8.5 bits per scalar, 136/256136/256136/256 of the original, about 1.882× compression. In general the budget is 8+32/d8+32/d8+32/d bits per scalar. That counts only K/V and scales; weights, Q, outputs and temporary workspace take space separately.

The implementation is three kernels: QK, softmax, PV. Intermediate scores go into an FP32 workspace S[H,N], softmax turns it into probabilities in place, and PV reads the probabilities. That costs an extra 4HN4HN4HN bytes, in exchange for being able to observe the two reductions separately. Both paths below, simple and split, have this structure; the three steps aren’t fused into one kernel.

Two ways to map threads

One thread per token

The most straightforward QK layout gives each thread one token: take the query and accumulate along that key row’s ddd components in order. The loop in kv_cache/new_kvint8.cu, with original variable names:

float sum = 0.0f;
for (int i = 0; i < head_dim; i++) {
    float K = k_scale[row * seq_len + col]
        * static_cast<float>(
            K_int8[(row * seq_len + col) * head_dim + i]);
    sum += Q[row * head_dim + i] * K;
}
S[row * seq_len + col] = sum / sqrtf(float(head_dim));

row is the head and col the token. For one thread that’s certainly a contiguous read, but what the GPU sees is the set of addresses one warp issues in the same instruction. This version uses block(16,16), so a warp splits into two 16-lane groups, each handling neighboring tokens of one head. With loop variable i fixed, neighboring threads in a group are head_dim bytes apart. At d=64d=64d=64, each thread takes one byte and neighboring threads are already two 32-byte sectors apart. One thread reading contiguously and one warp reading contiguously at the same moment are different things.

One warp per token

The second layout flips it and gives one token to a whole warp: lane 0 takes channels 0, 32, 64, …, lane 1 takes 1, 33, 65, and so on. At d=64d=64d=64 each lane computes just two products, the 32 lanes in each round cover one contiguous 32-byte stretch, and warp shuffles combine the results.

A key’s scale is the same across the whole row, so it can move outside the sum:

q⊤(stct)=st∑jqjct,j.q^\top(s_tc_t)=s_t\sum_jq_jc_{t,j}.q⊤(st​ct​)=st​j∑​qj​ct,j​.

The compute part of kv_cache/KV_int8_split_optimized.cu therefore reads:

const int8_t* k_row = K_int8 + (head * seq_len + token) * head_dim;
float sum = 0.0f;
for (int d = lane; d < head_dim; d += WARP_SIZE) {
    sum = fmaf(q_smem[d], static_cast<float>(k_row[d]), sum);
}
sum = warp_sum(sum);
if (lane == 0) {
    S[head * seq_len + token] =
        sum * k_scale[head * seq_len + token] * inv_sqrt_dim;
}

A block has 8 warps covering 8 tokens of one head. The query is loaded cooperatively into q_smem and read after a block sync, so one copy serves 8 dot products. warp_sum shuffles at 16, 8, 4, 2, 1. The invalid-token check comes after loading the query and the block sync, and every lane in a warp has the same token, so half a warp can’t skip the sync.

This change has costs too. One short dot product now occupies 32 threads and a five-level reduction, and both FP32 addition order and where the scale multiply happens change. Real-number algebra makes the two equivalent; it doesn’t guarantee bitwise-identical floats, or that short inputs are always faster.

PV: reducing along the other axis

PV reduces along the token axis, with each thread owning one output channel and iterating over all tokens:

oj=∑t(ptstV)ct,jV.o_j=\sum_t (p_ts^V_t)c^V_{t,j}.oj​=t∑​(pt​stV​)ct,jV​.

The bracketed weight doesn’t depend on the output channel, so it can be shared. split stages 256 probability * v_scale values into shared memory each round for every output channel to reuse; simple has each output thread read probabilities and scales itself. When the last tile has fewer than 256 tokens, only the valid length is traversed, and threads without an output channel still take part in block syncs, so the next round can’t overwrite weights others are still using. Both versions read every key and merge every value; they differ only in how work is divided and how many outputs share each read.

What the compiler and hardware say

No IMMA in sight

In the binary under test, simple’s QK inner-loop PTX looks like this, with line-number comments removed:

ld.global.s8 %rs1, [%rd17+-3];
cvt.rn.f32.s16 %r46, %rs1;
mul.f32 %r47, %r3, %r46;
ld.global.b32 %r48, [%rd43+-16];
fma.rn.f32 %r49, %r48, %r47, %r127;

ld.global.s8 reads a signed byte, which is converted to FP32, multiplied by the scale and FMA’d with the query. The s16 in the conversion source type refers to the value in the register after loading; it doesn’t mean the cache became 16-bit. split also shows five levels of shfl.sync.down.b32, the warp reduction. SASS agrees: ordinary loads, conversions and FFMA, with no IMMA or HMMA.

That gives the performance analysis a specific object. What’s being reduced here is cache bytes and inefficient access, not a race toward the theoretical peak of INT8 matrix multiply.

Splitting the error: implementation vs. representation

So far both CUDA paths read the same INT8 data. Comparing them studies implementation; it can’t say whether compression hurts attention. For that, the pre-quantization inputs have to come back into the picture.

For a general set of queries, write

P=softmax⁡(QK⊤/d),O=PV,P^=softmax⁡(QK^⊤/d).P=\operatorname{softmax}(QK^\top/\sqrt d),\quad O=PV, \qquad \widehat P=\operatorname{softmax}(Q\widehat K^\top/\sqrt d).P=softmax(QK⊤/d​),O=PV,P=softmax(QK⊤/d​).

K’s error is projected by the query first. A Δk\Delta kΔk of the same length changes the dot product along the query direction, while its component perpendicular to the query doesn’t, which is why K reconstruction MSE alone can’t predict attention. V takes another route, entering the output directly in the weighted sum.

Figure 4: Two routes for quantization error.

With ΔV=V^−V\Delta V=\widehat V-VΔV=V−V, there’s an exact decomposition:

O^−O=(P^−P)V+PΔV+(P^−P)ΔV.\widehat O-O=(\widehat P-P)V+P\Delta V+(\widehat P-P)\Delta V.O−O=(P−P)V+PΔV+(P−P)ΔV.

The first two terms are K-only and V-only quantization, and the last is the interaction from quantizing both. So K-only and V-only errors can’t simply be added, and taking RMSE introduces cross terms between error vectors on top of that.

The CUDA checks keep three answers: ooriginalo_{\rm original}ooriginal​ from the original FP32 K/V promoted to CPU binary64; odecodedo_{\rm decoded}odecoded​ from the actual INT8 plus FP32 scales decoded and computed in binary64; and oGPUo_{\rm GPU}oGPU​. They satisfy

oGPU−ooriginal=(oGPU−odecoded)+(odecoded−ooriginal).o_{\rm GPU}-o_{\rm original} =(o_{\rm GPU}-o_{\rm decoded})+(o_{\rm decoded}-o_{\rm original}).oGPU​−ooriginal​=(oGPU​−odecoded​)+(odecoded​−ooriginal​).

The first difference comes from the CUDA implementation and finite-precision compute; the second from the cache representation. A kernel can compute quantized attention very accurately while quantized attention itself has already drifted, and that shouldn’t be “fixed” by loosening kernel tolerances.

When the first channel is amplified, CUDA still tracks the decoded reference closely, while cache quantization error rises sharply. The cause is per-row absmax scaling: one large coordinate sets the whole row’s step size, and every other coordinate has to round onto a coarser grid. Amplifying the query raises it too, because the same key perturbation now causes a larger logit perturbation.

Starting from model activations, you could also change the grouping. KIVI sends keys and values along different directions, keys per channel and values per token; both paths here are per token, so this INT8 kernel can’t be called a KIVI implementation (KIVI paper). Another route keeps per-vector encoding but changes the coordinate distribution first, which brings us to random-rotation quantization.

Random rotation: flattening the direction

absmax sets its step size from each row’s maximum. TurboQuant’s MSE route at a 4-bit budget starts from a different idea: if every coordinate has a similar distribution before quantization, a shared codebook can be designed in advance, putting more reconstruction values where values are more common (TurboQuant paper).

First write a nonzero vector as x=rux=rux=ru with r=∥x∥2r=\|x\|_2r=∥x∥2​ and ∥u∥2=1\|u\|_2=1∥u∥2​=1. Store the length rrr and encode only the direction. Then apply a random orthogonal matrix RRR to get z=Ruz=Ruz=Ru. Rotation doesn’t change length, and without quantization, multiplying by R⊤R^\topR⊤ undoes it exactly; what it does is scatter one fixed direction randomly over the sphere, losing no information by itself.

For a uniformly random direction on the sphere, a single coordinate ttt has density

fd(t)=Γ(d/2)π Γ((d−1)/2)(1−t2)(d−3)/2,−1<t<1,f_d(t)=\frac{\Gamma(d/2)}{\sqrt\pi\,\Gamma((d-1)/2)} (1-t^2)^{(d-3)/2},\qquad -1<t<1,fd​(t)=π​Γ((d−1)/2)Γ(d/2)​(1−t2)(d−3)/2,−1<t<1,

with mean zero and variance 1/d1/d1/d. At d=64d=64d=64 a typical coordinate is about 1/81/81/8, so spreading 16 reconstruction values evenly over [−1,1][-1,1][−1,1] wastes most of them. Lloyd–Max iteration places codepoints by this density: each codepoint is the conditional mean of its interval, and each boundary the midpoint between neighboring codepoints. After iterating, the grid is denser where probability concentrates.

This design doesn’t need all coordinates to be fully independent. Their squares sum to 1, and total squared reconstruction error is the sum of per-coordinate squared errors, so expectations add term by term. With the codebook map CbC_bCb​, the reconstruction is

x^=rR⊤Cb(Ru).\widehat x=rR^\top C_b(Ru).x=rR⊤Cb​(Ru).

The CPU implementation takes a QR decomposition of a Gaussian matrix and flips columns of the orthogonal factor by the signs of the triangular factor’s diagonal, giving a Haar orthogonal matrix; the codebook comes from integrating the finite-dimensional spherical density. Each row’s length is still stored in FP32, so the experiments include rounding error from storing it. The rotation and codebook are shared across many vectors, so their storage has to be amortized over that sharing scope.

This design spreads one large coordinate across many directions, exactly the outlier channel that absmax tends to lose. But if a vector was originally very sparse, rotation also turns exact zeros into ordinary nonzero values. Whether that trade pays off at low bit widths can’t be judged by looking at max coordinates before and after rotation.

Unbiased only protects the mean

K is used for dot products with the query, so besides vector reconstruction error you can look directly at dot-product estimates. TurboQuant’s other route adds a QJL residual after MSE quantization, making the dot product with a fixed query, for a fixed input, unbiased in expectation over the random quantizer.

Let the coarse quantization be x0x_0x0​ and the residual e=x−x0e=x-x_0e=x−x0​. Fix that residual, draw mmm Gaussian vectors gi∼N(0,I)g_i\sim\mathcal N(0,I)gi​∼N(0,I) independent of the coarse quantization, store only the projection signs bi=sign⁡(gi⊤e)b_i=\operatorname{sign}(g_i^\top e)bi​=sign(gi⊤​e), and estimate the residual with

e^=∥e∥2mπ2∑i=1mbigi.\widehat e=\frac{\|e\|_2}{m}\sqrt{\frac\pi2}\sum_{i=1}^m b_i g_i.e=m∥e∥2​​2π​​i=1∑m​bi​gi​.

The coefficient falls out directly. Let u=e/∥e∥u=e/\|e\|u=e/∥e∥ and split the Gaussian vector into a parallel part auauau and an orthogonal part g⊥g_\perpg⊥​. The sign depends only on aaa, and the orthogonal part is independent of it with mean zero, so

E[sign⁡(g⊤e)g]=E[∣a∣]u=2/π u.\mathbb E[\operatorname{sign}(g^\top e)g] =\mathbb E[|a|]u=\sqrt{2/\pi}\,u.E[sign(g⊤e)g]=E[∣a∣]u=2/π​u.

Multiplying the scale back gives E[e^∣e]=e\mathbb E[\widehat e\mid e]=eE[e∣e]=e, so x0+e^x_0+\widehat ex0​+e has an unbiased dot product with any fixed query. A zero residual returns zero separately. That’s the core of QJL’s asymmetric inner-product estimate: the cache side keeps only signs, the query side keeps real-valued projections (QJL paper).

Here m=dm=dm=d, so each coordinate averages 1 bit for the residual sign. To fit a roughly 4-bit codeword budget, the base drops to MSE3 plus QJL1. K needs two FP32 norms, so at d=64d=64d=64 it’s actually 5 bits/value; V uses MSE4 at 4.5 bits/value, averaging 4.75 for K/V. The earlier table’s K-prod4 / V-MSE4 column is this configuration, which isn’t strictly 4 bits/value and isn’t a uniform default across the paper’s experiments.

That doesn’t refute QJL’s theoretical goal; it just shows that at the current budget, “unbiased” can’t substitute for evaluating at the output.

These CPU experiments all reconstruct vectors explicitly, to make errors comparable. A real compressed dot product can compute bi(gi⊤q)b_i(g_i^\top q)bi​(gi⊤​q) directly, without building e^\widehat ee; whether projection, packing and reads are fast needs separate measurement.

What this does and doesn’t show

  • It shows that this INT8 format costs 8.5 bits per scalar at d=64d=64d=64 (1.882× compression), and that mapping one warp per token cuts QK sectors about 11× on one shape.
  • It shows that the end-to-end call is faster on some shapes and 23% slower on another, with a device-check asymmetry not yet separated out.
  • It shows that implementation error and representation error separate cleanly, and that an outlier channel raises INT8 representation error by two orders of magnitude while kernel error stays tiny.
  • It shows, in controlled CPU experiments, that random rotation helps a spherical codebook a lot on outlier and sparse inputs and barely at all on Gaussian ones, and that absmax still wins on sparse inputs.
  • It shows that a QJL residual moves the dot-product mean toward zero while raising RMSE and attention output error at this budget.
  • There’s no FP16 GPU baseline, no compressed-domain TurboQuant kernel, and no real-model activations or generation-quality experiments.

Conclusion

Let’s recap both halves. On the GPU, compressing the cache only pays off if the decode kernel reads it efficiently: per-warp channel reads cut sectors dramatically, while the end-to-end result still depends on shape and on what else the call does. On the numerical side, quantization error reaches attention through two routes, K via the query and V via the weighted sum, and has to be measured at the output. Rotation helps exactly when the input doesn’t match the codebook’s assumed distribution, and a format that preserves zeros can still beat it. Unbiased dot products protect the mean, while softmax and RMSE care about more than the mean.

A smaller cache is a storage result; whether attention got faster, or stayed accurate, are two more experiments.

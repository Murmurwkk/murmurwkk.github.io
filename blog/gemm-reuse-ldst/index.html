Where a Naive CUDA GEMM Loses 5× to cuBLAS

One output per thread took 3.26 ms on a 1024³ matrix; cuBLAS took 0.62 ms. Block tiling, register outer products and float4 loads, checked in SASS and measured across square, skinny and short-K shapes.

更新于 2026/11/6 · 8 个章节
#CUDA#GEMM#float4#CUB#performance experiments

This is probably my first GEMM blog post. Putting it together now feels pretty nostalgic. I’d kept it to myself for a long time, a bit too embarrassed to show anyone, but here it is, as light reading over tea or a study aid for anyone learning this stuff (

Matrix multiplication itself isn’t hard: A∈RM×KA\in\mathbb R^{M\times K}A∈RM×K, B∈RK×NB\in\mathbb R^{K\times N}B∈RK×N, C=ABC=ABC=AB, about 2MNK2MNK2MNK floating-point operations. The hard part is keeping the GPU busy. Every multiply-add waits on two operands, and if both have to come from global memory every time, the multipliers spend most of their time idle. That’s exactly where my first GEMM was: on a 1024³ square matrix with one output element per thread, it took 3.2601 ms. On the same machine, also in FP32, cuBLAS took 0.6164 ms. More than five times faster.

That 5× breaks down into three separate questions:

  1. Block tiling: can one element of A serve a whole block of outputs?
  2. Thread tiling: once an operand is in a register, can it be used for several multiplies?
  3. Vector loads: how many instructions does it take to move the same data?

They interact, but none substitutes for another. In this post we’ll go through them in that order: start from a 64×64 output tile, then compare scalar, float4 and CUB loads under the same thread mapping. Then we’ll check what the compiler actually emitted, and finish by measuring everything across square, skinny and short-K shapes, all on one RTX 5070 Laptop.

Fundamentals: one output per thread

First, the layout. A, B and C are contiguous row-major arrays, so A[i*K+k] is AikA_{ik}Aik​ and B[k*N+j] is BkjB_{kj}Bkj​. One output element is the dot product of a row and a column:

Cij=∑k=0K−1AikBkj.C_{ij}=\sum_{k=0}^{K-1}A_{ik}B_{kj}.Cij​=k=0∑K−1​Aik​Bkj​.

The most direct kernel gives each thread one output and accumulates along K:

// Teaching version: A[M,K], B[K,N], C[M,N], all contiguous row-major.
__global__ void gemm_naive(const float* A, const float* B, float* C,
                           int M, int N, int K) {
    int row = blockIdx.y * blockDim.y + threadIdx.y;
    int col = blockIdx.x * blockDim.x + threadIdx.x;
    if (row >= M || col >= N) return;
    float sum = 0.0f;
    for (int k = 0; k < K; ++k)
        sum = fmaf(A[row * K + k], B[k * N + col], sum);
    C[row * N + col] = sum;
}

fmaf(a,b,c) computes ab+cab+cab+c with a single rounding. When K=0 the loop doesn’t run and the output is naturally 0. There’s no communication between threads, so boundary threads can simply return.

Launched with 16×16 blocks, 256 threads cover 16×16 outputs. CUDA groups threads into warps of 32; a thread’s index within its warp is its lane. In a 2D block, x varies fastest, so one warp covers two rows of 16 outputs each.

Fix k and look at one memory access: threads on the same output row read the same A element, while the B column index varies contiguously across threads. That address pattern decides what the warp’s requests look like (same address, contiguous or strided), and hardware handles each very differently.

But even with perfectly coalesced access, the same data is loaded over and over. The threads computing Ci,jC_{i,j}Ci,j​ and Ci,j+1C_{i,j+1}Ci,j+1​ both need AikA_{ik}Aik​; those computing Ci,jC_{i,j}Ci,j​ and Ci+1,jC_{i+1,j}Ci+1,j​ both need BkjB_{kj}Bkj​. Caches may catch some of it, but every load, every address calculation and every dependency is still there. I wanted the program to arrange that reuse explicitly, rather than hoping the cache keeps the data around.

That means using three kinds of storage deliberately:

  • Global memory holds the full matrices.
  • Shared memory lets the threads of one block share a small piece of input.
  • Registers hold each thread’s accumulators.

A block resides on one SM; whether several blocks can reside together depends on registers, shared capacity and thread count. Shared memory and registers are close to the compute units, but they’re small, and a whole matrix won’t fit.

Level 1: block tiling, so one load serves many outputs

Take one 64×64 block of C. It needs 64 rows of A and 64 columns of B. There’s no need to read all of K at once: cut K into chunks of 32, and for each chunk load just a 64×32 slice of A and a 32×64 slice of B. Compute with that chunk, then load the next, while partial sums stay in the same threads throughout.

The decomposition doesn’t change the product:

Ctile=∑tAtile,tBt,tile.C_{\rm tile}=\sum_{t}A_{\rm tile,t}B_{t,\rm tile}.Ctile​=t∑​Atile,t​Bt,tile​.

Each chunk of input is 64×32+32×64=409664\times32+32\times64=409664×32+32×64=4096 floats, 16 KiB, and it performs 64×64×3264\times64\times3264×64×32 FMAs, 262144 FLOP. Ignoring the cost of writing C, this level’s logical input arithmetic intensity is 16 FLOP/B. For a general BM×BN×BKB_M\times B_N\times B_KBM​×BN​×BK​ tile,

Itile=2BMBNBK4(BMBK+BKBN)=BMBN2(BM+BN).I_{\rm tile} =\frac{2B_MB_NB_K}{4(B_MB_K+B_KB_N)} =\frac{B_MB_N}{2(B_M+B_N)}.Itile​=4(BM​BK​+BK​BN​)2BM​BN​BK​​=2(BM​+BN​)BM​BN​​.

Notice that BKB_KBK​ cancels. Making the K chunk bigger doesn’t improve this input reuse ratio; it only changes loop count, synchronization frequency and shared memory needs. What makes each element take part in more outputs is a bigger output tile. That’s why, in GEMM, output tiling matters more than “reading a bit more of K at a time.”

📝 Note: This formula counts input bytes the algorithm requests, not DRAM bytes. Neighboring blocks can still reuse L2, and even the naive kernel may hit in cache. Use it to decide which direction to tile, not to predict time; for that, measure.

Level 2: thread tiling, outer products in registers

A 64×64 tile has 4096 outputs, still handled by 256 threads, so each thread gets a 4×4 block:

int local_m = (threadIdx.x / 16) * 4;
int local_n = (threadIdx.x % 16) * 4;
float acc[4][4] = {};

Thread 0 computes rows 0–3, columns 0–3; thread 1 rows 0–3, columns 4–7; thread 16 rows 4–7, columns 0–3. 16×16 of these small blocks tile the output exactly, with no overlaps or gaps.

Now it’s more natural to think of matrix multiplication as a sum of outer products. For a fixed k, a thread needs only 4 elements of A and 4 of B, and those 8 numbers update 16 outputs:

for (int kk = 0; kk < 32; ++kk) {
    float a[4], b[4];
    for (int i = 0; i < 4; ++i)
        a[i] = shared_a[(local_m + i) * 32 + kk];
    for (int j = 0; j < 4; ++j)
        b[j] = shared_b[kk * 64 + local_n + j];
    for (int i = 0; i < 4; ++i)
        for (int j = 0; j < 4; ++j)
            acc[i][j] = fmaf(a[i], b[j], acc[i][j]);
}

Figure 1: Two levels of reuse. A shared tile serves many threads; a register operand serves four FMAs within one thread.

So reuse now happens at two levels. One global→shared load of input serves many threads; one shared→register operand takes part in four multiply-adds within its thread. After unrolling, several independent accumulators also give the compiler room to interleave FMAs, so a single accumulation dependency chain is no longer the only limit.

Loading and consuming shared memory needs block barriers. All threads must finish filling the A/B tiles before anyone reads data another thread brought in. After the current tile is consumed, everyone must meet again before the next K chunk overwrites the same storage; otherwise a fast warp is already writing the next tile while a slow one is still reading the last. The full structure is four steps: cooperative load, barrier, outer-product accumulate, barrier. C is written once, after all K chunks.

There’s one more step up. A 128×128 output tile with 8×8 accumulators per thread raises logical input intensity to 32 FLOP/B, at the cost of 64 outputs held per thread. Below I’ll call this the 128² register-tiled version: 256 threads, BK=16, A transposed in shared memory with padding, and separate handling for full interior tiles and boundary tiles. It changes several design parameters at once, so its results show the combined effect of a larger reuse scope, not a single-parameter change from the 64² version.

Level 3: fewer instructions with float4

Now fix the 64² output tile, BK=32 and 4×4 per thread, without enlarging the tile. The A and B tiles each have 2048 elements, so each of 256 threads loads eight. Thread t takes logical indices 8*t through 8*t+7. This is a blocked assignment: each thread gets a contiguous range rather than alternating by lane.

That’s easy to reason about, but look instruction by instruction and the access isn’t contiguous. On iteration i of a scalar loop, lane 0 reads i, lane 1 reads 8+i, lane 2 reads 16+i. Adjacent lanes are eight floats apart, 32 bytes. The only contiguity is within each thread’s own eight elements.

float4 exploits exactly that: each thread moves its eight elements with two wide loads. It doesn’t change which inputs a thread is responsible for, doesn’t change the shared memory layout, and not one line of the multiply-add code moves. That’s what makes these three versions directly comparable:

Load methodElements each thread obtainsShared layout and compute
Hand-written scalarEight scalar reads, logical indices 8*t+iSame
Hand-written float4Wide reads for two fully aligned groups, scalar fallback otherwiseSame
CUB DIRECTThe same blocked assignment expressed with BlockLoadSame

The implementation uses a 2D iterator that maps a tile’s logical index back to the real matrix address and returns zero out of bounds. A common mistake here is treating a 2D tile as one long contiguous run in global memory. Each row of the A tile has only 32 valid positions, and the real stride to the next row is K; for B, the row stride is N.

int row = index / TileCols;
int col = index % TileCols;
return row < valid_rows && col < valid_cols
     ? base[row * stride + col] : 0.0f;

The CUB version just hands this iterator to cub::BlockLoad<..., BLOCK_LOAD_DIRECT>. DIRECT keeps the blocked element ownership; it doesn’t switch to lane-contiguous striped loading on its own. Changing the load strategy would mean checking the order each thread receives elements in and rewriting the shared indexing. A library can express the loading method clearly, but it won’t decide the GEMM’s whole data layout for you (BlockLoad implementation).

When a wide load is allowed

Wide loads have conditions. Four floats are 16 bytes; the start must be aligned, and all four elements must be in range:

if (row_valid && col + 3 < valid_cols && aligned_16(ptr)) {
    float4 value = *reinterpret_cast<const float4*>(ptr);
    // The four components go into four consecutive positions owned by this thread.
} else {
    // Check element by element; read if valid, otherwise write zero.
}

Figure 2: Even with an aligned allocation, a view starting one float in is misaligned for 16-byte access.

Even if the allocation base is aligned, passing A_allocation+1 shifts the start by four bytes. Even when M, N and K are all exact tile multiples, you can’t keep doing unconditional wide loads. With K=33, A’s row pitch is 132 bytes, and every row starts with a different alignment (CUDA natural alignment requirements).

This bit me. The 128² version originally chose its fast path based on shape alone, and at M=N=128,K=32,offset=1 it issued a misaligned 16-byte read; memcheck reported misaligned immediately. After the fix, the fast path also checks A/B/C’s actual base addresses and the boundary path checks each wide read and write group, and all 36 memcheck runs including this counterexample report zero errors. The condition is specific: the matrix size didn’t change, but the address of the array view passed in did.

Tails need care too. M/N tails need an output mask; K tails need invalid inputs zero-filled. Threads taking part in cooperative loads can’t return early even if they have no valid output, because others are waiting on them to load data and reach the barrier. Whether a thread may exit depends on which cooperation it’s part of, not just on whether it has a C element to write.

Checking what the compiler actually emitted

float4 is just a type in the source; whether wide instructions exist depends on what the compiler produces. PTX is a virtual GPU instruction representation; SASS is the machine code the target architecture executes. Compiling with CUDA 13.1, -O3 -lineinfo -arch=sm_120, I extracted both along the actual load template.

A PTX excerpt from the float4 branch (register numbers assigned by the compiler):

@%p5 bra $L__BB2_5;
shl.b64 %rd28, %rd2, 2;
add.s64 %rd29, %rd4, %rd28;
ld.global.v4.b32 {%r1084, %r1083, %r1082, %r1081}, [%rd29];
bra.uni $L__BB2_13;

The index is shifted left by two to get a byte offset, added to the base, and then v4.b32 loads four 32-bit components at once. In SASS that’s LDG.E.128. If the conditions fail, control jumps to the scalar fallback, so seeing both scalar and vector instructions in one function isn’t a contradiction.

Site counts are static code locations, and none of the three has compiler-reported spills. One fun detail: after stripping symbol names and encoding comments, the scalar and CUB DIRECT SASS instruction text has the same SHA256. This CUB abstraction compiled to exactly the same code. float4 uses 15 more registers: wide loads save instructions, but they also change how temporaries and branches are compiled.

Now the runtime counters. A request is something submitted to L1TEX; a sector is a 32-byte region a request touches, and the same sector touched by different requests is counted again. Both measure activity in the middle of the memory hierarchy, so multiplying sectors by 32 and calling it DRAM read traffic is wrong (NCU metrics guide).

With M=N=K=1024,offset=0, one kernel launch:

Figure 3: float4 cuts both requests and sector accesses to a quarter on aligned 1024³.

Here’s why. The blocked assignment puts adjacent lanes 32 bytes apart, so one scalar instruction touches 32 sectors. The thread then reads the next three floats, and those three instructions touch the same batch of sectors again. With float4, the four elements land in one wide read: the warp still touches 32 sectors, but request count and sector accesses both drop to a quarter.

More registers don’t necessarily mean proportionally lower residency, either. Occupancy is resident warps as a fraction of hardware capacity; SMs allocate resources per block, and resource limits have discrete thresholds. For this input NCU reports a register block limit of 3 for both versions, and actual occupancy only moves from 45.14% to 44.12%, with zero local/shared spilling at runtime. No new residency threshold has been crossed here; changing thread count or accumulator size would require re-checking.

The moment the shape isn’t tidy, the 4× relationship breaks. At 129×131×65,offset=1, the float4 template makes 2220 requests and 41484 sectors: some lanes are invalid, some rows happen to be aligned, and wide and scalar loads mix. A template named float4 only says the path exists; how often the branch is actually taken needs dynamic counts.

The biggest step comes from reuse: naive to 64² tiling takes 1024³ from 3.2601 ms to 0.9029 ms. With both levels of reuse in place, switching to wide loads gives 0.9029→0.7338 ms, 1.23×, and 1.20× at 2048³. Requests fell by three quarters while total time fell only partly, and that’s expected: those two numbers measure different things.

The 128² version is faster on these two shapes, but its gain includes changes to shared layout, BK and interior-tile dispatch, so it can’t all be credited to “a bigger output tile.” On the cuBLAS side, this is cublasSgemm under CUBLAS_PEDANTIC_MATH, adapted to row-major via CT=BTATC^T=B^TA^TCT=BTAT without actually transposing inputs; it’s not a TF32-enabled library configuration (cuBLAS layout and math modes).

Figure 5: Throughput across square sizes.

Small matrices immediately expose the other side of big tiles. A 128³ problem with 128² output tiles produces exactly one block, leaving every other SM idle: it takes 0.01724 ms, slower than the naive kernel’s 0.01133 ms. How many reads a block saves and how many outputs the whole GPU can compute at once are two scales you have to watch together.

Skinny and short-K matrices

Non-square shapes waste work inside tiles too. These come from a separate measurement batch, with each row’s speed ratio relative to that batch’s scalar version:

Figure 6: Relative speed by shape.

8192×64×128 has only 64 valid output columns, but the 128² version still organizes work around 128 columns and throws half away: 41.089 µs, against 27.985 µs for 64² float4. Swap M and N and it’s 35.394 vs. 28.510 µs. Same arithmetic, different useful work per thread.

Short K dilutes the inner-loop optimizations. 512×512×16 is only half a BK; 64² scalar takes 10.576 µs and float4 10.919 µs. Boundary handling, load organization and launch cost are all still there, and wide loads don’t pay off. The offset tail at 129×131×65 behaves the same: float4 11.74 µs, scalar 10.69 µs. I haven’t yet separated how much of that comes from the fallback branch versus address calculation.

At 4096³ the ranking shifts again: cuBLAS 15.201 ms, 128² 24.321 ms; scalar, float4 and CUB 46.377, 27.580 and 35.097 ms. But that doesn’t mean CUB is 1.32× faster than the scalar version with identical SASS. Scalar’s three round medians are 46.377, 34.922 and 56.674 ms, CUB’s 35.097, 33.621 and 57.413 ms, with heavily overlapping ranges. The laptop warmed from 56°C to 63°C during measurement with clocks unlocked, and the data can’t apportion the variation among temperature, frequency or anything else.

Where launch overhead takes over

For kernels around ten microseconds, timing also picks up the rhythm of host submission. CUDA events mark points on the device, but when the GPU finishes faster than the CPU submits, the interval between two events includes waiting for the next launch. If the application also uploads A/B, downloads C and synchronizes every time, 1024³ scalar waits 1.772 ms and float4 1.622 ms, excluding allocation and compilation. The compute-phase saving is still there, but pageable host transfers eat a good part of it. So choosing a kernel takes more than M/N/K: you also need to know whether matrices stay on the device, whether other operators follow, and whether calls come back to back.

What this does and doesn’t show

  • It shows that most of the gap to cuBLAS on 1024³ comes from reuse (3.2601 → 0.9029 ms with 64² tiling), and that float4 then cuts load requests 4× and time by about 1.2× on large aligned squares.
  • It shows, from SASS, that CUB DIRECT compiled to the same code as the scalar loader, and that float4 costs 15 registers without crossing an occupancy threshold here.
  • It shows that big tiles lose on small and skinny matrices, float4 doesn’t help on short K or unaligned tails, and launch gaps dominate ten-microsecond kernels.
  • It doesn’t separate the fallback-branch and address-arithmetic costs in unaligned tails, or explain 4096³ variance; clocks weren’t locked.
  • Every number is FP32 SIMT on one SM120 laptop GPU.

Conclusion

Let’s recap the three questions from the start. Block tiling made each loaded element serve a whole tile of outputs, and that’s where most of the 5× went. Thread tiling turned the inner loop into register outer products, so each operand feeds several FMAs. Vector loads cut instruction and request counts, a real but smaller gain, and only on aligned, regular shapes. In this implementation, 64² float4 genuinely reduced load requests and won on a batch of large squares; it didn’t replace judgment about output tiling, thread mapping and how the kernel gets called.

The next problem moves into shared memory: do consumers collide on the same bank, and can the current tile keep computing while the next one loads? Shared layout and double buffering picks those up with the same thread mapping.

📝 Further reading: To see how TMA, WGMMA and persistent scheduling on Hopper hand loading and compute to different hardware paths, read Aleksa Gordić’s long post on matmul. Tiling and synchronization both change under those mechanisms; the FP32 SIMT measurements here describe only this SM120 implementation.

Most of making GEMM fast is making each byte you load do more work; the instruction count only matters once that’s done.

Experimental setup and method, correctness checks, reproduction

📝 Note: Paths in this appendix such as bench_mur/ and rep_mur/ are in my private research repository, so they aren’t public; they’re listed so each result can be traced.

Experimental setup and method

Test device: RTX 5070 Laptop GPU, SM120, about 8 GB. Compiled with Toolkit 13.1.115, MSVC 2022 14.44, driver 610.88, options -O3 -arch=sm_120 -lineinfo. Environment cross-checks recorded runtime API version 13.3. Since CUDA 13 the Windows runtime can ship with the display driver, so this value can differ from the build Toolkit; see the Runtime API version notes. The original GEMM CSVs didn’t query this field. Consumer SM120 and B200/SM100 differ in resources and instruction capability and should be considered separately.

All implementations use ordinary FP32 multiply-add, and the cuBLAS reference also runs pedantic FP32 without TF32, so speed differences can be explained purely by data organization without also dealing with reduced input precision.

Device timing uses CUDA events: 20 warm-ups, then batches sized to about 20 ms from a single-run estimate, with repeats per batch limited to 1–2000. Slower kernels exceed 20 ms in one run, and very short kernels may fall short of 20 ms after hitting the repeat cap; raw records keep the actual repeat count. Each round has 30 batches, three rounds in all, with in-round task order shuffled by a fixed seed. Inputs are reused and L2 isn’t flushed, so this measures repeated calls with a warm cache. The laptop’s clocks weren’t locked, and round-to-round variation is shown as-is.

End-to-end is timed separately: pageable host upload of A/B, one GEMM, C download and completion synchronization, excluding allocation, compilation and handle creation. Each round warms up five times then measures 30, calling once each time, so the amortized accounting of GPU-resident repeated calls isn’t applied to host-transfer scenarios.

Correctness checks

First, six variants × 12 shapes × three inputs, 216 checks: uniform random, all zeros and alternating-sign cancelling inputs; shapes covering K=0, a single element, tails near 63/64/65 and 127/128/129, asymmetric matrices and offsets of 1/2/3 floats. Outputs are pre-filled with NaN and guarded by sentinels before and after, so missed computation and out-of-bounds writes can’t be masked by initialization.

Small shapes are compared elementwise with CPU FP64. Each output’s engineering error budget is

∣Cij−Cij64∣≤10−6+16ϵ32∑k∣AikBkj∣.|C_{ij}-C^{64}_{ij}|\le 10^{-6}+16\epsilon_{32}\sum_k|A_{ik}B_{kj}|.∣Cij​−Cij64​∣≤10−6+16ϵ32​k∑​∣Aik​Bkj​∣.

This is this experiment’s acceptance threshold, not a floating-point proof for arbitrary inputs and K. All 216 pass, with max absolute error 6.6622e-6 and max actual-error-to-threshold ratio 0.1123. memcheck reports zero errors on all four corrected hand-written kernels.

Large matrices are compared in full against cuBLAS FP32 with atol=3e-4,rtol=3e-4, plus 257 deterministic positions (including first, last and scattered ones) against CPU FP64. That provides a full GPU comparison and a partial independent high-precision reference; it can’t be called full FP64 validation. Every performance task first passes its corresponding correctness check.

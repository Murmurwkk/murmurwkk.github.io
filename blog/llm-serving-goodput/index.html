Splitting Prefill from Decode: What DistServe Buys and Costs

Prefill and decode share weights but not shapes, so running them together slows both. How DistServe sizes two GPU pools, what moving KV between them costs, and what the paper measured.

更新于 2026/11/6 · 8 个章节
#LLM Serving#PD disaggregation#KV Cache#DistServe#paper reading

In LLM serving, one Transformer does two very differently shaped jobs. When it processes the input prompt, every token’s position is already known, so each layer can process them all at once. When it generates output, each new token has to wait for the previous one. The first is prefill and the second is decode. They share the same weights, but the matrix shapes and data reuse are completely different.

Run them together and they get in each other’s way. A long prefill inserted between two decode steps stretches the token interval for requests already generating. Prioritize those requests instead, and new ones wait a long time for their first token. DistServe gives the two jobs separate groups of GPUs. The model computation doesn’t change. What changes is how the two phases compete for resources, and it creates a job that didn’t exist before: moving the computed KV cache from one pool to the other.

This post walks through DistServe’s paper and its public implementation at a pinned commit. We’ll start with what makes prefill and decode different, define what “good serving” means as a number, and derive how to size two pools. Then we’ll count what it costs to move KV between them and look at how the public code does the handoff. After that come what the paper actually measured and how multi-turn conversations, where history KV is already resident somewhere, change the routing problem. All throughput and latency numbers are the authors’; I only recomputed byte counts, squared-length sums and table errors locally.

Fundamentals: one set of weights, two matrix shapes

For a prompt of length ℓ\ellℓ, one layer’s linear transform is XWXWXW with X∈Rℓ×hX\in\mathbb R^{\ell\times h}X∈Rℓ×h. All ℓ\ellℓ positions are known, and causality is expressed through attention’s visibility mask, so there’s no need to run the whole model token by token from the start. Every layer produces this input’s K/V at once, and the last position’s output is the first generated token.

Then the new token goes back in. For one sequence, each layer’s linear transform now has a single new position as input; attention uses that position’s query to read the history K/V and appends the new K/V. Repeating that is decode. The cache means old positions don’t rerun the whole model, but their keys and values still have to be read by the current position.

On the linear-layer side, prefill’s many tokens share one weight read and form a big matmul; single-sequence decode is closer to a matrix-vector product with little weight reuse. Batching several sequences for decode recovers some of it. The common saying “prefill is compute-bound, decode is bandwidth-bound” is a conditional observation: batch size, length, model structure and hardware can all move the bottleneck, so don’t conclude from the phase name alone.

Long inputs carry a separate attention cost. For a prefill batch with request lengths l1,…,lbl_1,\ldots,l_bl1​,…,lb​, the linear layers process

t=∑ilit=\sum_i l_it=i∑​li​

tokens, while within-request position pairing scales with

t2=∑ili2.t_2=\sum_i l_i^2.t2​=i∑​li2​.

Four 256-token requests and one 1024-token request are both 1024 tokens, but their squared-length sums are 262144 and 1048576, four times apart. Total prefill time doesn’t quadruple, because linear layers, attention kernels, parallel communication and fixed overhead all combine. That’s why DistServe’s Appendix A keeps both ttt and t2t_2t2​ and fits a latency model by profiling, instead of assigning each token a fixed cost.

Put both shapes in one execution instance and interference follows. Decode wants a short, punctual slot every iteration; long prefill wants to process enough input at once to amortize overhead. One long prefill between two decode steps stretches the token interval immediately.

Figure 1: Rectangle widths are illustrative, not measured, and the two schemes aren’t assumed to use the same number of GPUs. The decode appearing first below belongs to an existing request; the new request still has to go through prefill and KV handoff before it can generate.

Chunked prefill slices long inputs and interleaves them with decode. That limits the stall from any one interruption, at the cost of more iterations and lower per-iteration efficiency. PD disaggregation isolates execution resources at a larger scale, letting the P pool and D pool choose their own parallelism and scale independently. The two aren’t exclusive; the P pool can still chunk internally.

What “good” means: TTFT, TPOT and joint attainment

A service has to manage two kinds of waiting. Request iii arrives at aia_iai​, its first token returns at ti,1t_{i,1}ti,1​ and its last at ti,mit_{i,m_i}ti,mi​​. For mi>1m_i>1mi​>1,

TTFTi=ti,1−ai,TPOTi=ti,mi−ti,1mi−1.\mathrm{TTFT}_i=t_{i,1}-a_i,\qquad \mathrm{TPOT}_i=\frac{t_{i,m_i}-t_{i,1}}{m_i-1}.TTFTi​=ti,1​−ai​,TPOTi​=mi​−1ti,mi​​−ti,1​​.

TTFT is time to first token; TPOT is the average token interval after that. TPOT squashes a whole generation into one average, so it’s not the worst stall and not a high percentile of token intervals; requests with a single output token need their own TPOT rule.

Given thresholds TF,TOT_F,T_OTF​,TO​, a request has to pass both. At arrival rate λ\lambdaλ and full configuration ccc, the joint attainment is

A(λ,c)=1n∑i=1n1{TTFTi≤TF ∧ TPOTi≤TO}.A(\lambda,c)=\frac1n\sum_{i=1}^n \mathbf1\{\mathrm{TTFT}_i\le T_F\ \land\ \mathrm{TPOT}_i\le T_O\}.A(λ,c)=n1​i=1∑n​1{TTFTi​≤TF​ ∧ TPOTi​≤TO​}.

The configuration covers how many GPUs, how the pools split, how each parallelizes and how requests are routed. Requiring at least fraction qqq of requests to attain, DistServe’s goodput is the highest arrival rate per GPU that can be sustained:

Goodput⁡(c;q)=sup⁡λ:A(λ,c)≥qλG(c).\operatorname{Goodput}(c;q)= \sup_{\lambda:A(\lambda,c)\ge q}\frac{\lambda}{G(c)}.Goodput(c;q)=λ:A(λ,c)≥qsup​G(c)λ​.

That picks different configurations than “keep the GPUs as full as possible.” Bigger batches raise throughput while requests waiting to be batched miss their first-token deadline; giving everything to P makes D’s output intervals break the threshold. Capacity has to be counted over complete requests, and failed, timed-out or rejected requests can’t be dropped from the denominator.

Two separate percentiles can also hide a problem. Out of 100 requests, 80 pass both, 10 fail only TTFT and 10 fail only TPOT. Each metric shows 90%; joint attainment is 80%.

Figure 2: Constructed data showing why one request’s two times have to be evaluated together.

Whether you’re changing the P:D ratio or the transfer path, compare under the same joint requirement. Don’t give one phase a loose threshold and the other a strict one and then report only the flattering side.

Sizing two pools

Fix the model, length distribution and SLO. Say one P instance sustains μP\mu_PμP​ requests per second and one D instance μD\mu_DμD​. With nP,nDn_P,n_DnP​,nD​ instances, ignoring communication and queueing tails, a stable arrival rate needs at least

λ≤min⁡(nPμP,nDμD).\lambda\le\min(n_P\mu_P,n_D\mu_D).λ≤min(nP​μP​,nD​μD​).

The minimum makes a simple point: adding GPUs to the side that’s already idle does nothing for the other side’s backlog. It’s an idealized capacity model. Real μ\muμ varies with batch size, length distribution and parallelism, and near saturation, queueing breaks the SLO first.

DistServe’s Figure 1 gives a concrete motivating experiment: OPT-13B, 512 input tokens, 64 output tokens, A100 80 GB. Mixed execution manages about 1.6 requests/s. Run separately, P handles about 5.6 requests/s and D about 10. So 2P+1D has an ideal bottleneck of about min⁡(11.2,10)=10\min(11.2,10)=10min(11.2,10)=10 requests/s, or about 3.3 requests/s/GPU across three GPUs. That 3.3 is a ratio estimate ignoring handoff and real queueing, not a measured system capacity.

An “instance” isn’t one GPU, either. A model can spread intra-layer compute with tensor parallelism (TP) or split into layer segments with pipeline parallelism (PP). TP shortens some compute while raising intra-layer communication; PP lets several batches advance in different segments at once, with pipeline waits and bubbles. P wants to shorten long-input execution; D also cares about sustained generation batch size and KV capacity. The two pools may not suit the same TP/PP.

The authors’ actual choices from Appendix B:

This table isn’t a configuration to copy. It shows that disaggregation really does give each phase room to choose for itself. The results depend on the authors’ hardware, length distribution and latency targets; a larger decode batch or a model with fewer KV heads would move the bottleneck.

Memory is a constraint too. Active sequences on D keep growing, and KV usage determines how many requests fit at once; requests that P has finished but not yet handed off still occupy P’s cache. The first limit you hit isn’t necessarily compute.

The price of separation: moving KV

Once P and D are separate, each request has to migrate its state. For ordinary dense KV, ignoring padding and metadata, the payload per request is

MKV=2LNKVdhℓs.M_{\rm KV}=2L N_{\rm KV}d_h\ell s.MKV​=2LNKV​dh​ℓs.

The 2 is for K and V, LLL is layers, NKVN_{\rm KV}NKV​ KV heads, dhd_hdh​ head dimension, ℓ\ellℓ context length and sss bytes per element. With GQA, several query heads share each KV head, so this must be the KV head count, not the query head count.

Take 40 layers, 40 KV heads, head dimension 128, FP16 and 512 tokens:

MKV=2×40×40×128×512×2=419430400 bytes=400 MiB.M_{\rm KV}=2\times40\times40\times128\times512\times2 =419430400\ \text{bytes}=400\ \text{MiB}.MKV​=2×40×40×128×512×2=419430400 bytes=400 MiB.

Sent serially over one 25 Gbit/s link (an ideal 3.125 GB/s), that’s about 134.218 ms with zero protocol or queueing overhead. Cut KV heads to 8 and the payload drops to 80 MiB, about 26.844 ms. At 2048 tokens the two become 1600 MiB / 536.871 ms and 320 MiB / 107.374 ms.

Figure 4: Byte accounting, not NIC measurements; GB/s is decimal and MiB binary.

Once a model is split by TP/PP, the full payload is divided among ranks and links and doesn’t necessarily all go through one port. Multiple GPUs sending concurrently don’t each get independent bandwidth, either: NICs, PCIe uplinks or switch ports may be shared.

So deployment has to answer more than whether the network is fast enough. It also has to ask which data needs to cross the network at all. DistServe’s low-cross-node-bandwidth placement co-locates the corresponding P and D for each layer segment on the same node. With the model in two segments, node 1 holds segment one’s P and D and node 2 holds segment two’s. P’s intermediate activations flow to the next segment, while each segment’s KV stays on its node and goes to the matching D. Real TP ranks still have to be laid out, but activations and KV now travel different physical paths.

That shrinks configuration freedom: a P/D parallelism that’s ideal for compute may not satisfy the co-location requirement. DistServe therefore searches placement spaces separately for the high- and low-cross-node-bandwidth cases. A fast P instance that forces hundreds of MiB of state over a slow link every time won’t necessarily yield good request capacity.

A single transfer looking acceptable doesn’t settle it, either. At arrival rate λ\lambdaλ with mean KV size Mˉ\bar MMˉ, the system needs about λMˉ\lambda\bar MλMˉ of sustained effective bandwidth. Under full load, queueing makes a few requests wait a long time, and uncontended M/BM/BM/B can’t stand in for tail latency. The paper’s §4.3 has D pull KV on demand, with P holding the cache temporarily to absorb some backlog; a finite cache can buffer bursts but can’t absorb sustained overload.

How the public code hands off a request

In the public implementation, the handoff is an explicit call chain. DistServe calls prefill the context stage. When ContextStageLLMEngine._step gets results, it first delivers the generated token through the output callback, then builds a MigratingRequest for unfinished requests and puts it on the queue connecting the two stages. The request carries P’s block table and parallel config. P’s blocks can’t be freed yet, because D doesn’t have the contents.

On the receiving side, DecodingStageLLMEngine._migrate_blocks first allocates destination blocks to get D’s block table, then calls each worker to migrate. Here’s the migration and reclamation, with lifecycle logging omitted, from single_stage_engine.py at the pinned commit (Apache-2.0):

await asyncio.wait(self._remote_call_all_workers_async(
    "migrate_blocks",
    migrating_req.block_indexes,
    migrating_req.context_parallel_config,
    target_block_indexes
))
# ... lifetime logging ...
self.clear_migrated_blocks_callback(migrating_req)

The callback then has P free the request’s resources. migrate_blocks in worker.py passes both sides’ TP/PP config, source and destination block indices and K/V buffers to torch.ops.block_migration_ops.migrate_blocks. That’s more than copying a contiguous byte range: the same layer’s same logical KV slice has to be mapped onto a different set of parallel ranks (worker implementation).

This Python only shows the control-level handoff order. asyncio.wait alone doesn’t establish that low-level exceptions and GPU visibility are handled correctly; that depends on the completion semantics of the workers and the native migration op. I didn’t run this multi-GPU system or test its failure paths.

It does explain one thing you’d see on a client timeline: prefill can return the first token before handing off KV. So transfer latency isn’t all counted in TTFT; it may land between the first and second generated tokens instead. Recording only P time and D time makes it easy to miss that wait. Measurement should keep client-side token times and tie KV preparation, transfer and consumable time back to the same request.

Resource usage should be traced along the same chain. P finishing compute is one state change; it doesn’t mean P’s memory is reclaimed immediately. If the target D can’t accept, P accumulates completed requests; free the source cache too early and the next prefill may overwrite it.

What the paper actually measured

The main experiments use 4 nodes with 32 A100 SXM 80 GB GPUs, NVLink within nodes and 25 Gbps between them, running FP16 OPT-13B, 66B and 175B. The workloads provide input and output lengths but no arrival timestamps, so the authors generate arrivals as Poisson processes at varying rates. What’s measured is capacity under this controlled traffic.

The authors set these SLOs from application goals, and LongBench inputs are truncated by OPT’s maximum length. HumanEval’s first-token requirement is strict and LongBench’s inputs are long, which affect the two pools’ queueing and execution shares differently, so gains on different workloads aren’t a fixed multiple of one mechanism.

At a 90% attainment target, ShareGPT sustains 2.0–4.6× the request rate of vLLM and 1.6–7.4× that of DeepSpeed-MII; HumanEval is 5.7× vLLM and LongBench 4.3×. In a second set at fixed request rate with TTFT/TPOT thresholds tightened together, ShareGPT tolerates 1.8–3.2× stricter SLOs than vLLM and 1.7–1.8× than MII; HumanEval 1.4× and LongBench 12.6×. The two sets compare along different axes. 7.4× request rate and 12.6× SLO strictness aren’t the same operating point, and tightening thresholds 12.6× doesn’t mean latency fell 12.6× (DistServe §6).

The baselines’ conditions count too. vLLM’s TP is 1, 4 or 8 depending on model; the DeepSpeed-MII implementation used in the paper is limited by vocabulary partitioning and memory and has no corresponding OPT-175B configuration. That’s a limit of the measured versions and configurations, not a claim about other versions.

Earlier we estimated that 400 MiB over 25 Gbps takes about 134 ms. Yet the authors report that for OPT-175B/ShareGPT, transfer takes under 0.1% of total phase time, with over 95% of requests migrating in under 30 ms. The key is that the KV doesn’t all go over that 25 Gbps link: low-bandwidth placement keeps the corresponding layer segments’ handoff mostly within the node over NVLink. The denominator matters too. 0.1% is a share computed by summing each request’s phase times; per-request distribution comes from the transfer CDF, and the two aren’t interchangeable.

Figures 8–10 are real end-to-end results. Figure 11, which studies higher cross-node bandwidth and placement schemes, uses simulation, because the testbed lacked the bandwidth and the baselines didn’t support every configuration. Table 2 validates real vs. simulated at seven arrival rates; recomputing item by item, the maximum absolute difference is 1.8 percentage points. At arrival rate 2.0, for example, vLLM is 52.8% / 51.0% and DistServe-Low 99.3% / 99.3%. That agreement supports using simulation for those configurations, not an error bound for all bursty traffic. Appendix C also reports a 99% attainment target, within the same controlled experiments.

Together, these results make “separate pools help” concrete. It isn’t only less interference between phases. Disaggregation also allows different parallelism per pool, and a suitable placement keeps KV handoff from eating the gain. Take away any one of the three and capacity comes out different.

When history is already in place: routing multi-turn requests

DistServe’s main line starts from new requests. In a real conversation, the next turn changes the choice: the history KV already lives on some D machine, and the new message is short. Sending every new input to P would move a large existing state for a small amount of incremental compute.

With history length hhh and new input length uuu, reusing history means each layer’s linear transforms only process the new positions, while attention still reads the history K/V. That’s not a from-scratch prefill of length h+uh+uh+u, and not an ordinary decode adding one position per request either. This append-prefill needs its own compute and interference model.

PPD v1 studies keeping some later turns on D to execute appended input, choosing by offline measurement tables and TTFT/TPOT weights. That saves the transfer and the P queue, but appended compute still blocks other decodes; the TPOT degradation in its Figure 5 shows that keeping state in place doesn’t avoid compute contention. That experiment is a single node with 4 H100 80 GB GPUs, mainly Llama-3.1-8B, with 10-second runs per synthetic point and ZeroMQ transport in the appendix; cross-machine RDMA trade-offs need separate measurement.

Cross-request prefix reuse adds another conflict: the machine with the cache may be busy, and the idle machine has no cache. Mooncake uses a shared KV store that includes host memory, schedules cache hits, cache movement and compute load together, and can replicate hot caches to spread concentrated access. Routing is no longer just picking the shortest queue; it compares the total cost of waiting, fetching state and recomputing.

Mooncake’s numbers can’t be lined up after DistServe’s for ranking. Its relevant experiments use a dummy model shaped like Llama3-70B, 8 A800s and 4 × 200 Gbps NICs per node, 16 nodes per side in Figure 1. TBT is defined as the mean of the longest 10% of token intervals, and the TTFT threshold is 30 seconds, both different from the mean TPOT and thresholds above. What’s borrowed here is the cache-driven routing mechanism, not the multipliers.

So, should you split?

There’s no answer independent of workload. Long inputs, strict output requirements and enough devices make an independent P pool directly valuable; short appends to resident history KV are simpler to keep on D. With few GPUs, two pools each holding a copy of the weights may crowd out KV capacity first; offline jobs without strict first-token and interval requirements may do better with mixed execution and full batches. DistServe’s §7 discusses resource-constrained and offline-throughput settings, leaving advanced preemption and fault tolerance to future work.

What this does and doesn’t show

  • It shows, by derivation and byte counting, why prefill and decode interfere, how two pools’ capacity is bounded by the slower side, and how large KV handoff can be (400 MiB for the example configuration).
  • It shows, from the pinned source, that the first token can be returned before KV handoff, so transfer delay may appear between tokens one and two rather than in TTFT.
  • It reports the paper’s measured gains with their exact axes and conditions, and recomputes Table 2’s real-vs-simulated agreement (max 1.8 points).
  • It doesn’t run the multi-GPU system, measure any throughput or latency locally, or test failure paths.
  • PPD and Mooncake are discussed as mechanisms; their numbers aren’t comparable with DistServe’s.

Conclusion

Let’s recap. Prefill and decode are the same weights used in two matrix shapes, so running them together forces each to wait on the other. “Good” serving is the arrival rate per GPU at which enough requests meet both latency targets. Disaggregation lets each phase get its own pool size and parallelism, at the price of moving KV, and placement decides whether that price is negligible or dominant. Once conversations have history, the question shifts again, to where state already lives.

The thing worth keeping is one complete request: where it queued, which compute decided its first token, which path its KV took, and what each later token waited for. Account for that path along with the GPUs, memory and links it occupied, and PD disaggregation stops being an architecture name and becomes a deployment you can compare.

Disaggregation doesn’t make the work smaller; it lets you decide where each piece of it waits.

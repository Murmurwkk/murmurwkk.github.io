Online Softmax in CUDA: No Score Matrix, More Time

Skipping the 16 MiB score matrix for 2048-token attention should be a win, yet the online kernel ran slower. Deriving the online state, the CUDA kernel and its bugs, and why the cost sits outside the formula.

更新于 2026/11/6 · 6 个章节
#CUDA#Softmax#Attention#parallel reduction#performance measurement

Online softmax solves one specific dependency. Every softmax term depends on normalizing over the whole row, but when you process a row in tiles, you haven’t read the later scores yet. The derivation has to settle what state to keep when one row is split into pieces, and how two pieces’ states merge. Once that’s settled there’s a more practical question: does an implementation that skips the full matrix actually run fast? And if not, is the reason inside the formula or outside it?

For single-head attention with sequence length 2048, the matrix of every query’s scores against every key is 16 MiB of FP32, read exactly once in a weighted sum and then never used again. This post answers both questions with two implementations.

We’ll start by deriving the online state and checking it with a small hand example, then write a CUDA kernel that gives each query its own block, including three bugs found along the way. Next we’ll time it against a separated implementation and find out why it’s slower, and finish with the two-pass long-row softmax you need when the interface wants the full probability vector. All GPU experiments ran on an RTX 5070 Laptop (SM120), and the conclusions cover only these two hand-written implementations.

Fundamentals: two scalars and a vector

The setup: Q∈RM×dQ\in\mathbb R^{M\times d}Q∈RM×d and K,V∈RN×dK,V\in\mathbb R^{N\times d}K,V∈RN×d, all contiguous FP32. MMM is the number of queries, NNN the number of keys/values, ddd the feature dimension. Only single-head dense forward is considered: no mask, no dropout, no backward.

S=QKTd,Pij=eSij∑k=0N−1eSik,O=PV.S=\frac{QK^\mathsf T}{\sqrt d},\qquad P_{ij}=\frac{e^{S_{ij}}}{\sum_{k=0}^{N-1}e^{S_{ik}}},\qquad O=PV.S=d​QKT​,Pij​=∑k=0N−1​eSik​eSij​​,O=PV.

For one fixed query, score sjs_jsj​ is its scaled dot product with key jjj, and the output is a weighted sum of value vectors. The separated implementation runs four steps as four kernels: transpose KKK, QKQKQK, softmax, PVPVPV, with the storage for SSS overwritten in place by PPP.

Figure 1: Separated attention materializes SSS/PPP; online attention keeps only per-row state.

Subtracting the maximum in softmax is usually described as overflow protection, but it also sets the scale reference for merging tiles:

m=max⁡jsj,ℓ=∑jesj−m,pj=esj−m/ℓ.m=\max_j s_j,\qquad \ell=\sum_j e^{s_j-m},\qquad p_j=e^{s_j-m}/\ell.m=jmax​sj​,ℓ=j∑​esj​−m,pj​=esj​−m/ℓ.

Dividing numerator and denominator by eme^mem leaves probabilities unchanged in exact arithmetic, and since no exponent argument exceeds zero, overflow from exponentiating large positives goes away. That assumes finite scores; with positive infinity, ∞−∞\infty-\infty∞−∞ needs separately defined behavior.

Merging without rereading

The hard part is that when tiling you don’t yet know the final maximum. Walk through three scores, 0, 1, 3. After the first two, the stored exponent sum at the then-maximum of 1 is e−1+1e^{-1}+1e−1+1. When 3 arrives, both old terms have to move to the new reference 3:

(e−1+1)e−2+1=e−3+e−2+1.(e^{-1}+1)e^{-2}+1=e^{-3}+e^{-2}+1.(e−1+1)e−2+1=e−3+e−2+1.

No old score needs to be reread: multiply the whole stored sum by e−2e^{-2}e−2 and it’s rescaled. Abstracting that step, any processed set AAA stores two numbers:

mA=max⁡j∈Asj,ℓA=∑j∈Aesj−mA.m_A=\max_{j\in A}s_j,\qquad \ell_A=\sum_{j\in A}e^{s_j-m_A}.mA​=j∈Amax​sj​,ℓA​=j∈A∑​esj​−mA​.

Another block BBB has the same state, and joining the two takes one max, two rescaling factors and one addition:

m=max⁡(mA,mB),ℓ=emA−mℓA+emB−mℓB.m=\max(m_A,m_B),\qquad \ell=e^{m_A-m}\ell_A+e^{m_B-m}\ell_B.m=max(mA​,mB​),ℓ=emA​−mℓA​+emB​−mℓB​.

The new scale is no smaller than either old one, so both factors are at most 1 and the sum can’t overflow upward. The merged result is the union’s maximum and exponent sum, independent of merge order in exact arithmetic. That’s the property that lets “read once in order” generalize to tree reductions over threads, warps and blocks. Floating point isn’t exact, though: change the reduction tree’s shape and the last bits change, so error checks can’t be skipped and two trees won’t match bit for bit (online normalizer paper).

Attention also has to weight values, so the state gains a ddd-dimensional vector:

uA=∑j∈Aesj−mAVj.u_A=\sum_{j\in A}e^{s_j-m_A}V_j.uA​=j∈A∑​esj​−mA​Vj​.

It merges with the same two factors:

u=emA−muA+emB−muB,O=u/ℓ.u=e^{m_A-m}u_A+e^{m_B-m}u_B, \qquad O=u/\ell.u=emA​−muA​+emB​−muB​,O=u/ℓ.

As long as no other caller needs the full probabilities, each tile’s contribution can be added into uuu the moment VVV is read, and the tile’s scores thrown away. What remains is two scalars plus one ddd-dimensional vector, instead of NNN probabilities. FlashAttention combines exactly this online normalization with on-chip matrix tiling to avoid materializing the full attention matrix; how fast that gets depends on input reuse and compute layout.

The kernel: one block per query

The most direct mapping gives each query its own block: 128 threads, the query in shared memory, then K/VK/VK/V read tile by tile along NNN. Once a tile is ready, four warps split its keys. Each warp computes one key’s QK dot product with lanes dividing ddd and shuffles merging the partial sums. With the tile’s scores in hand, the block finds its max and exponent sum, and each thread updates the output dimensions it owns.

With d=64d=64d=64, each lane handles two products and the warp reduces to one score, with four warps computing four keys in parallel. In the PV phase, threads switch to dividing output features: the first 64 threads each accumulate one valid dimension, using the same score weights and reading their own VVV column, and finally write this query’s 64-dimensional output.

The fused update doesn’t need to store the current tile’s uBu_BuB​ separately; it accumulates directly at the common scale:

new_m = max(old_m, tile_max);
alpha = exp(old_m - new_m);
for (each valid key j in this tile)
    p[j] = exp(score[j] - new_m);

acc = alpha * acc + sum_j(p[j] * V[j]);
l   = alpha * l   + sum_j(p[j]);
m   = new_m;
// after all K/V tiles:
output = acc / l;

acc is a ddd-dimensional vector, while mmm and ℓ\ellℓ are shared by the block, and output components live in different threads’ registers. In attention/softmax_new.cu, multiply-adds use fmaf and exponents __expf, with old state initialized to (-FLT_MAX,0,0); N>0N>0N>0 guarantees every processed tile has at least one valid key. __expf is an approximate exponential in its own right; not passing --use_fast_math doesn’t make it an exact exp.

Three bugs worth knowing about

Bug 1: zero-padding tails. In GEMM, zero-padding KKK is natural because extra products don’t change the sum. Do the same in softmax and things break: a nonexistent key padded to 0 still gets positive weight and changes the denominator. “Pad the tile” has different semantics in the two operations. So NNN‘s tail can only process min(TileN,N-tile_start) valid keys.

Bug 2: a legal value used as a sentinel. The separated implementation’s reduction originally checked max_next > -FLT_MAX to decide whether a thread had input, treating -FLT_MAX as an impossible sentinel. With d=1d=1d=1, QQQ all -FLT_MAX and KKK all 1, every score is exactly that legal finite value, and non-empty threads are treated as empty. At M=3M=3M=3, N=2N=2N=2, d=1d=1d=1, both probabilities in each row became 1, row sums became 2, and final OOO had max error 0.108322. The correct test is sum_next > 0: with NNN non-empty the exponent sum is always positive, the same property as ”ℓ>0\ell>0ℓ>0 means non-empty” above. N=2N=2N=2, 33 and 257 cover small rows, cross-warp and cross-thread striding.

Bug 3: a race on shared scratch. This one has nothing to do with the formula. It’s in the shared scratch used by both the max and the sum reductions. The reduction helper has warp 0 write the final result, then runs a block barrier; the old ending was

__syncthreads();
return scratch[0];

A barrier makes writes before it visible to others; it doesn’t guarantee reads after it have finished. A fast warp reads, returns, and may already be in the next sum reduction overwriting scratch, while a slow warp is only now coming to read the previous max. Two function calls appear one after another in the source; warps don’t keep that order.

The fix reads, then confirms every reader has left:

__syncthreads();
const float result = scratch[0];
__syncthreads();
return result;

All 128 threads call this helper, so the second barrier is legal; if some thread skipped it, the participation scope would need redesigning. Giving max and sum separate scratch would also work, with those two regions’ lifetimes redefined.

What’s nasty about this bug is that ordinary output comparisons don’t catch it. The unfixed version passed all 72 ordinary output comparisons, yet racecheck on 31×37×6531\times37\times6531×37×65 reported 9 hazards (4 errors, 5 warnings), and that run’s max output error was 0.171574. After the fix, the same input gives 7.9103×10−87.9103\times10^{-8}7.9103×10−8, with memcheck, racecheck and synccheck at zero errors, zero hazards and zero errors. Ordinary inputs sometimes computing correctly is no substitute for checking the read/write order of shared storage.

Figure 3: The race only shows up as error on some inputs.

The interface ends up requiring positive M/N/dM/N/dM/N/d with d≤1024d\le1024d≤1024 and checks shared capacity. Inputs, QK accumulation and scaling, and the VVV weighted sum must all be finite, without scanning every element for special values. uuu isn’t normalized yet, so very large finite VVV can still overflow the accumulation: subtracting the max fixes exponent range, not every numerical problem. All performance numbers below come from code with these fixes.

The surprise: no matrix, more time

Eliminating the matrix should be faster. Measurements split into two groups. First, conditions: both paths use preallocated workspace with inputs resident on the GPU, so the separated version’s per-call temporary allocation doesn’t contaminate the kernel comparison. The separated version’s scores take MNMNMN floats and the transposed KKK NdNdNd floats:

Wseparated=4MN+4Ndbytes.W_{\rm separated}=4MN+4Nd\quad\text{bytes}.Wseparated​=4MN+4Ndbytes.

The fused version doesn’t allocate those two global workspaces, though shared memory, registers and output remain. At M=N=2048M=N=2048M=N=2048, d=64d=64d=64, separated scores are 16 MiB and KTK^\mathsf TKT 0.5 MiB; the formula gives 258 MiB at 8192, a size that wasn’t timed.

Why: the mapping, not the formula

Follow the thread mapping and the limit becomes clear. One block serves one query, and every query rereads all of K/VK/VK/V from start to finish, about 2Nd2Nd2Nd floats requested in source terms. Neighboring queries use the very same K/VK/VK/V, but they can’t share it within one shared tile. Caches catch some repeated requests, but loading, dot products and reductions are still organized query by query. At M=1M=1M=1 there’s exactly one block working on the whole GPU. Grouping several queries into one output tile is what would let one K/VK/VK/V sub-tile serve several rows at once, and nothing in the online formula requires one query per block.

A second, separately checkable resource issue: the default entry picks the largest K/VK/VK/V tile that capacity allows. With d=64d=64d=64, N≥128N\ge128N≥128, TileN=128 needs dynamic shared memory of

4(d+2Td+T+128/32)=66320 B,T=128.4(d+2Td+T+128/32)=66320\text{ B},\qquad T=128.4(d+2Td+T+128/32)=66320 B,T=128.

The ddd term holds QQQ, 2Td2Td2Td holds K/VK/VK/V, TTT holds current scores, and the last four floats are reduction scratch for four warps. TileN=32 needs only 16784 B, at the cost of four times as many loop iterations. “Is there enough capacity” can’t answer whether fewer iterations or more resident blocks matters more.

When you need the probabilities: two passes

All of the above is about attention. If the interface wants the full softmax vector, things change: (m,ℓ)(m,\ell)(m,ℓ) alone isn’t enough. It keeps what the denominator needs but can’t recover each original score. Unless the whole row stays on-chip, the input has to be read a second time once the full row state is known.

For a long row of 10610^6106 elements, one block scanning it leaves every other SM idle. Instead, GGG blocks can each compute a local state, and a second kernel produces the output. The real long-row implementation is in attention/softmax_self.cu, with 512 threads per block in both passes.

The second pass doesn’t launch a separate global state-reduction kernel. Instead, warp 0 of every output block re-merges all GGG local states, puts the result in its own shared memory, then outputs its own slice of input:

if (threadIdx.x < 32) {
    for (int i = threadIdx.x; i < num_blocks; i += 32) {
        float m = block_max[i], s = block_sum[i];
        // Merge into thread-local state, then reduce within warp 0.
    }
}

That saves one kernel launch, at the cost of statistic reads growing as G2G^2G2. With N=1000000N=1000000N=1000000, G=144G=144G=144, NCU reports 7813 global load requests and 125000 sectors for pass one, and 9253 and 130184 for pass two. The difference can be computed straight from the code:

Δrequest=144×2×⌈144/32⌉=1440,\Delta request=144\times2\times\lceil144/32\rceil=1440,Δrequest=144×2×⌈144/32⌉=1440, Δsector=144×2×144×432=5184.\Delta sector=144\times\frac{2\times144\times4}{32}=5184.Δsector=144×322×144×4​=5184.

Two contiguous FP32 statistic arrays of 144 entries, read once by each output block: the subtraction matches the samples exactly. These are L1TEX requests and sectors, not equal DRAM traffic, since repeated statistics can hit cache. So more blocks raise input-scan parallelism and add repeated merging, and this implementation can’t speed up indefinitely by adding blocks.

State has to belong to one request

The state between the two kernels must belong to one request. With a single global array shared by all calls, two rows of length 65537 (A=0, B=10) scheduled as A pass 1 → B pass 1 → A pass 2 → B pass 2 let B overwrite A’s max and exponent sum, and A’s output row sum becomes e−10≈4.53999×10−5e^{-10}\approx4.53999\times10^{-5}e−10≈4.53999×10−5. That’s an artificially arranged interleaving showing shared state isn’t fit to expose as a concurrent interface; it doesn’t mean the original synchronous solve fails every time.

So the interface now takes a request-private workspace of 2*G floats and a stream:

cudaError_t softmax_vector_launch(
    const float* input, float* output, int N,
    float* workspace, int num_blocks, cudaStream_t stream);

The workspace lives from before pass one launches until pass two finishes, doesn’t overlap input or output, and each in-flight request has its own. Input and output may be exactly the same address; partial overlap isn’t supported. Long-row state initializes to (-FLT_MAX,0) and merges directly by the formula; subtracting two empty states gives exactly zero, so no negative infinity appears. That’s a different concrete implementation from the separated attention’s non-empty test above, and the two shouldn’t be conflated.

With private workspaces, two streams each submitted 100 times, and both final output row sums are 0.999999999767. Only the last output on each stream was checked, not every intermediate value, and physical overlap wasn’t measured. Input and output address alignment was checked separately, with in-place and offset cases verified. At 10610^6106 elements, aligned/offset take 23.513 and 26.038 µs; at 1024 elements, 16.773 and 17.278 µs. The fixed launch cost of two passes doesn’t disappear with row length, and small-row round-to-round variation is already close to the alignment difference. What this does and doesn’t show

  • It shows that online softmax needs only (m,ℓ,u)(m,\ell,u)(m,ℓ,u) per row, with a merge rule that’s exact in real arithmetic and checked by hand.
  • It shows three real bugs (zero-padded tails, a legal value as sentinel, a shared-scratch race that passes 72 output comparisons) and the inputs and tools that caught them.
  • It shows that this one-query-per-block fused kernel is slower than the separated version on every large shape, and that the gap comes from residency and lack of cross-query reuse, not from host setup or extra loads.
  • It shows that the two-pass long-row softmax’s per-block re-merge costs exactly the predicted G2G^2G2 statistic reads.
  • There’s no mature FlashAttention or cuDNN baseline, no cycle breakdown of loop, barrier and residency costs, and no multi-query tiling implementation.

Conclusion

Let’s recap. The math part works exactly as advertised: two scalars and a ddd-vector per row are enough, and merges can happen in any order. The performance part depends on something the math doesn’t specify: the mapping. Giving each query its own block means every query rereads all of K/VK/VK/V, and the largest tile that fits leaves one block per SM. That made this fused kernel up to 20× slower than writing the full matrix out. And when the caller needs probabilities, the online state can’t avoid a second pass; what it can do is make that pass parallel, at a measurable cost.

So this implementation’s performance ceiling sits at “one block serves one query”: the same K/VK/VK/V can’t serve multiple rows at once. Grouping several queries into one output tile is the path not yet taken, and how many rows to fit in shared memory is something only measurement can answer.

Online softmax removes the need to store the matrix; it doesn’t remove the need to reuse the inputs.

In addition, the effective addresses of Q/K/V/output are deliberately offset by one float, so results don’t only hold at float4-aligned addresses, and outputs have a sentinel before and after. The separated path also reads the real probability matrix, checking non-negativity, finiteness, row sums and error against CPU probabilities; the fused path has no probability matrix, so its check target is the final output.

After the fixes, 72 base checks, 6 finite-extreme boundary checks and 48 same-shape pre-timing checks, 126 output comparisons in all, pass this bar. Actual max absolute error is 2.6226×10⁻⁶ and max RMSE 8.2390×10⁻⁷; all outputs are finite and sentinels unchanged. The separated path’s max probability error is 7.8355×10⁻⁸ and max row-sum deviation 1.7919×10⁻⁷.

Constant V’s expected output is 3.25, and after accumulating many positive weights and normalizing, rounding errors tend to pile up in the same direction, so absolute error is higher than in some random cases. Darker heatmap cells are still within the range above, and these synthetic inputs can’t predict quality changes in real language models.

The 13.1 in the table is the build Toolkit version; the environment integration check recorded runtime 13.3 (13030) via cudaRuntimeGetVersion, with the raw ENV line saved separately. Since CUDA 13 the Windows runtime can ship with the display driver and may differ from the build Toolkit; see the versioning API docs.

Error bars in the figures are p05 to p95 of 90 batch means, not single-request p95 and not statistical confidence intervals. CUDA events bracket the entire submitted work, so short kernels may still include device idle time from late host submission. The fused entry in particular calls the attribute-setting API when its shared configuration is large; this experiment keeps that checked-dispatch cost, so not all of the time can be attributed to kernel instructions.

Source and entry points

Single-head attention and long-vector softmax are the two problems actually run. The repository also has three multi-head files: multihead_attention.cu calls the separated path head by head; multi_head_attention.cu’s local accumulator arrays cover at most four 32-dimension chunks; multi_head_attention_op.cu returns immediately for head dimensions above 64. None of them are in the performance tables.

Long-row raw records, the global-array counterexample and source snapshots are in rep_mur/blog-rewrite/style-v2/softmax/, and the attribute/tile comparison in style-v2/attention/. Long-row curves are aggregated per round by bench_mur/editorial/style-v2/operator_softmax_shapes.py, and the hand-example and state figures are generated by operator_figures.py, with each batch counted separately.

Main source SHA-256 prefixes: separated path 14f3aa480ffb, fixed fused path 011e1ea83bd4. Source, scripts, binary hashes, build output, per-batch times and Sanitizer logs are in rep_mur/blog-rewrite/attention/; the original draft is in originals/, the racy version in before-race-fix/, and the version before the empty-state boundary fix in before-finite-boundary-fix/.

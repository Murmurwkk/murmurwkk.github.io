Serial and Parallel Selective-Scan Kernels Compared on a Laptop GPU

Three CUDA designs for one selective-scan recurrence: serial state updates, atomic output, and fixed-order reduction. Paired measurements test complete calls, scratch management and the number of independent chains, with explicit calibration limits.

A selective scan has more than one source of parallelism. Different channels have independent state, the state itself has many components, and affine composition can expose work across time. Choosing where to put the parallelism also chooses who owns each output, which intermediate arrays are stored, and how many kernels must run.

This post compares three designs, with two implementation variants of each, on an RTX 5070 Laptop GPU. The six source files are not six separate operators, and the four device kernels inside ssm.cu are dispatch paths within one implementation. Workspace adapters and historical snapshots serve as controls rather than additional designs.

The useful questions are concrete: how do the two serial implementations compare; how does moving scratch ownership outside the call change the atomic implementation; and when are there too few independent channels for a serial time loop? A long-prefix boundary also supplies an exact correctness test before any performance comparison.

Fundamentals: a recurrence with a data-dependent decay

The scan takes six inputs and produces one output. For a batch of BBB sequences, sequence length LLL, model width DDD and state width NNN:

u, Δ, y∈RB×L×D,A∈RD×N,B,C∈RB×L×N,skip∈RD.u,\ \Delta,\ y\in\mathbb R^{B\times L\times D},\qquad A\in\mathbb R^{D\times N},\qquad B,C\in\mathbb R^{B\times L\times N},\qquad \text{skip}\in\mathbb R^{D}.u, Δ, y∈RB×L×D,A∈RD×N,B,C∈RB×L×N,skip∈RD.

For every (b, t, d, n) the two coefficient arrays are

at,d,n=exp⁡(Δt,d Ad,n),bt,d,n=Δt,d ut,d Bt,n,a_{t,d,n}=\exp(\Delta_{t,d}\,A_{d,n}),\qquad b_{t,d,n}=\Delta_{t,d}\,u_{t,d}\,B_{t,n},at,d,n​=exp(Δt,d​Ad,n​),bt,d,n​=Δt,d​ut,d​Bt,n​,

and the state and output are

ht,d,n=at,d,n ht−1,d,n+bt,d,n,h−1,d,n=0,h_{t,d,n}=a_{t,d,n}\,h_{t-1,d,n}+b_{t,d,n},\qquad h_{-1,d,n}=0,ht,d,n​=at,d,n​ht−1,d,n​+bt,d,n​,h−1,d,n​=0, yt,d=∑n=0N−1Ct,n ht,d,n+skipd ut,d.y_{t,d}=\sum_{n=0}^{N-1}C_{t,n}\,h_{t,d,n}+\text{skip}_d\,u_{t,d}.yt,d​=n=0∑N−1​Ct,n​ht,d,n​+skipd​ut,d​.

These formulas define the whole operator. The files contain no input projection, causal convolution, softplus on Δ\DeltaΔ, gate or backward pass, because they implement only the inner scan of a Mamba block, not the whole block.

A direct evaluation computes ht−1h_{t-1}ht−1​ before hth_tht​, with an input-dependent decay at every step. Affine composition provides another route: combine the step maps before applying them, without serially materializing every preceding state. The designs below differ in where they perform that composition and how they produce yyy.

The one fact parallel scans rely on

One step is an affine map, h↦a h+bh\mapsto a\,h+bh↦ah+b, and the composition of two affine maps is again an affine map. A chunk of steps is therefore one map h↦α h+βh\mapsto \alpha\,h+\betah↦αh+β. Two chunks, an earlier “left” chunk and a later “right” chunk, combine as

α=αright αleft,β=αright βleft+βright.\alpha=\alpha_{\text{right}}\,\alpha_{\text{left}},\qquad \beta=\alpha_{\text{right}}\,\beta_{\text{left}}+\beta_{\text{right}}.α=αright​αleft​,β=αright​βleft​+βright​.

This rule can be checked by hand with two identical steps, a=0.5a=0.5a=0.5 and b=1b=1b=1, starting from h=0h=0h=0. Step by step, h=0.5⋅0+1=1h=0.5\cdot0+1=1h=0.5⋅0+1=1 and then h=0.5⋅1+1=1.5h=0.5\cdot1+1=1.5h=0.5⋅1+1=1.5. With the combined map, α=0.5⋅0.5=0.25\alpha=0.5\cdot0.5=0.25α=0.5⋅0.5=0.25 and β=0.5⋅1+1=1.5\beta=0.5\cdot1+1=1.5β=0.5⋅1+1=1.5, so the chunk maps 000 to 0.25⋅0+1.5=1.50.25\cdot0+1.5=1.50.25⋅0+1.5=1.5. Both ways give the same answer.

Because this combination is associative, the (α,β)(\alpha,\beta)(α,β) of every chunk can be computed in parallel, and a parallel prefix scan can then combine them. One more consequence matters later. Since the scan always starts from h−1=0h_{-1}=0h−1​=0, the state at the start of any chunk is just the β\betaβ of all earlier chunks combined, and the α\alphaα of the earlier chunks only ever multiplies zero.

Three designs for one recurrence

The grouping follows the computation and output ownership:

What “parallel” has to achieve

The time-serial design has B⋅DB\cdot DB⋅D independent chains. Each chain is LLL steps long, and each step updates NNN states. In the original twelve-shape grid, B⋅DB\cdot DB⋅D is between 64 and 512, so even without any scan technique there are 64 to 512 chains for the 36 SMs of the GPU. The chain-count control extends that range down to one. Each step updates the NNN states and reduces their contributions, and this work must finish before the next step can start.

A parallel scan replaces this dependency with more work: chunk-local scans, a prefix scan, a replay, and either atomic operations or a reduction buffer. The question is whether this extra work costs less than the dependency it removes.

Design 1: one chain per warp or block

ssm.cu has four kernels. Each kernel assigns a warp or a block to each chain, and it keeps the state in shared memory or, when the state does not fit, in a device buffer. solve uses the warp kernel when N≤64N\le64N≤64 and the block kernel when NNN is larger, so most shapes here use the warp kernel with shared state. This excerpt shows its vectorized time loop, omitting setup and the scalar fallback for state widths that are not divisible by four:

for (int t = 0; t < seq_len; ++t) {
  // load u, delta, B, C for this (b, t, d)
  float local_sum = 0.f;
  for (int i = lane; i < d_state / 4; i += 32) {   // one float4 of states per lane
    float4 hv = h4[i];
    local_sum += update_state4(hv, a4[i], b4[i], c4[i], delta_val, delta_u);
    h4[i] = hv;
  }
  const float sum = warp_reduce_sum(local_sum);
  if (lane == 0) y[udy] = sum + skip_d * u_val;
}

update_state4 is the arithmetic core. It updates four states in one float4, with one expf and one FMA for each state, and adds their share of C⋅hC\cdot hC⋅h. Each lane handles one float4, so at N=64N=64N=64 only sixteen of the 32 lanes do this work, and at N=32N=32N=32 only eight lanes do. On this shared-state path, the state remains on chip and each step writes one global output value.

The revision binary’s warp-shared kernel has 480 addressed SASS instructions, including 10 SHFL, 67 FFMA and 12 MUFU instructions. The source-object and linked-binary hashes are recorded with the counts in sass_revision.csv. These are static instruction sites, not dynamic execution counts or measured stall percentages.

One warp owning a chain does not itself order memory accesses between lanes. Lane jjj initially zeroes h[j]h[j]h[j], h[j+32]h[j+32]h[j+32], …, while lane iii later reads h[4i..4i+3]h[4i..4i+3]h[4i..4i+3] as one float4. The corrected source places __syncwarp() between initialization and the first read, as required for this exchange by the CUDA Programming Guide. The same ordering was added to the warp-global fallback. Inside the time loop, each lane owns its float4, so this initialization barrier is outside the repeated work. The historical audit reproduced a shared-memory RAW hazard in Racecheck: a small B=1,L=33,D=7,N=32B=1,L=33,D=7,N=32B=1,L=33,D=7,N=32 case reported 1,736 warnings. The revision’s supported sources pass fourteen sanitizer invocations: memcheck, racecheck and synccheck at N=32,64,65,128N=32,64,65,128N=32,64,65,128, plus memcheck and synccheck across the new long-prefix boundary. Racecheck requires zero warnings and hazards as well as zero errors.

The main comparison uses the synchronized source. In the older separate-process audit, corrected/historical median ratios ranged from 0.845 to 1.134, while the corrected kernel itself changed from 3.035 ms to 3.603 ms at L=8192L=8192L=8192 between suites. Those observations do not identify the barrier’s cost: process/session conditions changed too. The revised same-process audit uses 24 independent starts at each of the twelve shapes. Its corrected/historical point ratios span 0.9933–1.0023, and every interval contains one; at L=8192L=8192L=8192 the ratio is 1.00054 [0.99719,1.00390]. All twelve AA controls meet the calibration band. This audit does not resolve a timing difference under that protocol, and does not establish zero instruction cost or make the historical source race-free.

At B=1,D=64B=1,D=64B=1,D=64, the launch exposes 64 independent warp-sized blocks to 36 SMs. Increasing LLL adds dependent iterations within each block; increasing BDB DBD instead adds independent blocks. Their measured scaling can distinguish these two kinds of work, but static SASS alone cannot establish which hardware stall dominates.

selective_scan_rewrite.cu follows the same idea, but it assigns one block to each chain, keeps the state in registers and uses a block-wide reduction. This reduction needs shuffles across all warps of the block and barriers in every step: its SASS contains 45 SHFL and 6 BAR.SYNC instructions.

The two variants also use different FMA groupings: ssm fuses the input product with the rounded decay-state product, whereas rewrite fuses the decay-state product with the rounded input term. They implement the same real-valued recurrence without promising bitwise-identical FP32 outputs. Their comparison changes storage, vectorization, thread count and reduction together, so it does not isolate any one of those choices. Above N=1024N=1024N=1024, rewrite switches to a separate correctness fallback that recomputes each output from time zero; that O(L2)O(L^2)O(L2) path is outside the main timing grid.

Design 2: chunked scan with atomics

ssm_seq.cu and selective_scan_improved.cu share one design with two paths.

The short-sequence scan (L≤1024L\le1024L≤1024). In ssm_seq, one block per (b,d,n) covers the whole sequence. improved uses this path for 65≤L≤102465\le L\le102465≤L≤1024; at L≤64L\le64L≤64 it instead uses the output-parallel recurrence fallback described below. The scan block has at least 32 and otherwise next_pow2(L) threads, and a Hillis–Steele scan in shared memory combines the steps’ (a,b)(a,b)(a,b) pairs. Every thread then uses atomicAdd to add C·h for its step into yyy, after a separate kernel initializes skip·u. At L=1024L=1024L=1024 with the default shape, this path launches 4,096 blocks of 1,024 threads.

Long sequences. The sequence is split into chunks of 256 steps, and four kernels run one after another:

  1. write skip · u into yyy;
  2. scan each chunk, store the local (a,b)(a, b)(a,b) pair of every step, and write the summary (α,β)(\alpha, \beta)(α,β) of the chunk;
  3. scan the chunk summaries of each state into exclusive prefixes;
  4. replay each step from the prefix of its chunk, h = local_a · prefix + local_b, and use atomicAdd to add C · h into yyy.

This path needs one atomic operation per state and time step. At L=8192L=8192L=8192 with D=N=64D=N=64D=N=64, there are 4,096 states and 8,192 steps, so the path performs about 33.5 million atomic operations, 64 for each output element. The stored local pairs take 2×4096×8192×42\times4096\times8192\times42×4096×8192×4 bytes, or 256 MiB. Step 2 writes them and step 4 reads them back, although the inputs of the whole operator total only 8 MiB.

The bug that wasn’t

ssm_seq.cu keeps only the β\betaβ half of each prefix, while selective_scan_improved.cu keeps both halves. A comment in selective_scan_improved.cu says that keeping α\alphaα “fixes the old code’s loss of affine scale information”. That wording sounds like a correctness difference, but the zero initial state is decisive.

It is not a bug. As Figure 1 shows, the scan starts from h−1=0h_{-1}=0h−1​=0, so the α\alphaα of the prefix only ever multiplies zero. Both files replay with exactly the same expression, local_a · prefix_b + local_b. The improved implementation passes prefix_a to the replay kernel but does not use it: (void)prefix_a; discards the pointer without reading its stored values. The code comment also explains why the value is kept: the kernel may later accept a non-zero initial state. This is an interface choice rather than a fix for the stated recurrence. Numerical validation still has to check each implementation’s dispatch paths.

On the long path, an important difference is memory management. ssm_seq.cu allocates four scratch buffers with cudaMalloc and releases them with cudaFree. selective_scan_improved.cu instead allocates one workspace with the stream-ordered cudaMallocAsync/cudaFreeAsync, which can reuse pooled memory, and also accepts caller-owned workspace. Its extra output-parallel path for L≤64L\le64L≤64 means that the two complete interfaces are not a single-variable allocator comparison at every length. The workspace controls below keep the long-path kernels fixed.

For sequences longer than 1,024 chunks (262,144 steps), selective_scan_improved.cu falls back to a kernel that recomputes every output from time zero. This fallback needs O(L2)O(L^2)O(L2) work and exists only as a correctness fallback.

Design 3: chunked scan with a deterministic reduction

op_mur/selective_scan_seq_parallel.cu runs the same chunk scan and prefix scan. Instead of adding into yyy, it writes each state’s contribution into contrib[state,t], then sums the NNN contributions in a fixed order. At B=1,L=8192,D=N=64B=1,L=8192,D=N=64B=1,L=8192,D=N=64, its three per-step arrays occupy 384 MiB and the chunk summaries another 1 MiB, before alignment padding. This is allocated capacity derived from the source, not a measurement of memory traffic.

The historical source accepted 4,096 chunks while its prefix kernel covered only 1,024. A simple input exposes the discrepancy: set B=D=N=1B=D=N=1B=D=N=1, A=0A=0A=0, all of u,Δ,B,Cu,\Delta,B,Cu,Δ,B,C to one, and skip to zero. The recurrence requires yt=t+1y_t=t+1yt​=t+1. At L=262145L=262145L=262145, the untouched final chunk retains its own summary β=1\beta=1β=1; replay adds another one and calculates 2 where the required output is 262145.

The revision preserves the original <=1,024-chunk kernel and adds a grouped path for longer sequences. One CTA scans successive groups of at most 1,024 summaries, carries the group’s affine map forward, and composes that carry with every local exclusive prefix. It covers all 4,096 supported chunks without adding global workspace. This is a source correction as well as a measurement revision; the earlier source is retained as historical/seq_parallel_before_prefix_fix.cu for an explicit audit.

The exact-input GPU audit checks lengths 262143, 262144, 262145, 262400, 262401 and 1048576, twice each. The corrected materialized implementation and the streaming/recompute implementation match every output exactly. The historical implementation passes the first two lengths and fails at all four lengths above the boundary, beginning at output index 262144. At the smallest failing length, it actually returns 2 instead of 262145. These expected historical failures are retained separately from the supported implementations’ correctness checks.

The all-one case checks coverage but uses a=1a=1a=1, so its affine maps are translations and commute. To check composition direction as well, a separate audit uses the varying-coefficient distribution below, shapes (2,262401,2,3)(2,262401,2,3)(2,262401,2,3) and (2,1048576,2,3)(2,1048576,2,3)(2,1048576,2,3), and seeds 17, 29 and 101. Six fresh processes check each selected implementation twice against every FP64 output. All 24 supported checks pass, with maximum absolute error 1.05×10−71.05\times10^{-7}1.05×10−7 and maximum tolerance-normalized error 0.00363. The twelve historical checks fail as expected beyond the boundary. Multiple batches, channels, states and a second group containing at least two chunks exercise paths absent from the exact scalar example.

selective_scan_streaming_seq_parallel_fixed.cu does not store the pairs of each step at all:

  1. scan each chunk and keep only its summary;
  2. scan the summaries in two levels, first within groups of chunks and then across groups;
  3. for a tile of 32 states at a time, re-run each chunk from its prefix;
  4. when more than one state tile is needed, store and reduce the tile partials, then add skip·u. At N≤32N\le32N≤32, the sole tile writes the final output directly.

Its only large buffer is the partial output when more than one state tile is needed. At N=64N=64N=64, this buffer is twice the output size; at N≤32N\le32N≤32 it is absent. Among the four parallel-scan implementations, this file uses the least workspace on the default long-sequence shape.

What Mamba’s own kernel does

The upstream-style reference in op_mur/mamba.cu fuses the forward scan into one launch. A CTA processes chunks in order and carries the running prefix in shared memory, but it also writes each chunk/state prefix into the global auxiliary output params.x_ptr:

if (threadIdx.x == 0) {
    smem_running_prefix[state_idx + r * MAX_DSTATE] = prefix_op.running_prefix;
    x[(r * params.n_chunks + chunk) * params.dstate + state_idx] = prefix_op.running_prefix;
}

This kernel parallelizes time within a chunk while looping over chunks and states. It avoids the local implementations’ cross-kernel prefix and output-reduction phases, but does not avoid every auxiliary global write. The global x output is distinct from materializing every time/state pair.

Its SSMParamsBase interface also includes optional delta bias/softplus, grouping, gate and complex-weight paths. A real FP32 configuration with variable B/C, one group and those options disabled can match the recurrence above after layout adaptation. The file depends on upstream headers absent from this package, so it is a source reference rather than a seventh measured implementation or a complete Mamba inference baseline.

How I measured

The revised harness, bench_mur/selective_scan/paired.cpp, links the six sources as separate translation units with distinct exported names. A and B execute in the same process on the same input and output addresses. This keeps CUDA-context initialization and input allocation from changing between the members of a pair. It measures complete solve calls, preserving each implementation’s allocation policy.

Before timing, every selected implementation runs twice against an independent double-precision CPU recurrence. The output is poisoned before each check. NaN/Inf, missing writes, CUDA errors and any element outside ∣y−yref∣≤2×10−5+2×10−4∣yref∣|y-y_{\rm ref}|\le2\times10^{-5}+2\times10^{-4}|y_{\rm ref}|∣y−yref​∣≤2×10−5+2×10−4∣yref​∣ are failures. The separate grid covers thirteen boundary shapes and seeds 17, 29 and 101, including odd state widths, partial chunks, L=1023/1024/1025L=1023/1024/1025L=1023/1024/1025 and N=64/65N=64/65N=64/65: 468 validation records. Exact all-one long-prefix checks and noncommuting random long-prefix checks are separate correctness audits, not performance samples.

Inputs are uniform in [−0.5,0.5][-0.5,0.5][−0.5,0.5], except Δ∈[0.01,0.06]\Delta\in[0.01,0.06]Δ∈[0.01,0.06] and A∈[−0.6,−0.1]A\in[-0.6,-0.1]A∈[−0.6,−0.1], so the decay range is approximately [0.965,0.999][0.965,0.999][0.965,0.999]. Timing uses seed 17. Six calls warm each selected implementation. Every timed segment encloses four calls; an independent host interval also extends through GPU completion. Copies, correctness checks and caller-owned workspace preparation lie outside the segments. Inputs stay warm, with no cache flush. The CUDA-event interval includes host-submission gaps between its events, not just active kernel durations.

A pilot uses three independent process starts per shape with six blocks per pair; each process runs all planned pairs for that shape. Its observations are excluded from the formal estimate. The pilot’s between-session variability freezes the formal sample size at 8–24 independent starts per shape with sixteen blocks each, targeting a 2% upper multiplicative halfwidth, or a log halfwidth of log⁡(1.02)\log(1.02)log(1.02). Reaching the cap without meeting that target remains an imprecise result. Within every start, A/B and B/A occur equally often, with a shuffled block schedule whose recorded seed changes between starts. Same-function A/A pairs use the same addresses and call path to check measurement variation and order effects.

For each independent start sss, I average log⁡(tA/tB)\log(t_A/t_B)log(tA​/tB​) separately over its A/B and B/A blocks, then average the two order means. A two-sided Student-t interval uses those session values as its independent samples, assuming independent between-start log ratios under the recorded conditions. The repeated blocks reduce within-session variation; they do not increase the independent sample count. Ratios throughout the paired results are time A / time B, so values above one mean B is faster. The identical-function A/A calibration has a prespecified practical band of [0.98,1.02]: its entire 95% interval must fit inside that band. This criterion is separate from the precision target and does not assert equivalence for an A/B comparison. An A/B interval containing one leaves the difference unresolved. Intervals are pointwise, without a familywise claim about a winner across all shapes.

The GPU is an RTX 5070 Laptop (8 GiB, SM 120). The pre-run read-only query reports a current GPU power ceiling of less than half the reported default. This is a power-limited laptop experiment, not a maximum-performance specification for the device. Device temperature, clocks, power and utilization are retained around each process. Experimental GPU workloads run serially; no power, clock or driver settings are changed. Source, harness, runner, statistics and binary identities are recorded under rep_mur/experiment-revision-20261115/scan/; these working-repository materials are distinct from the older public reproduction below.

The largest warning is at L=8192L=8192L=8192. Its ssm/ssm interval is [0.980,1.058], while the symmetric order factor is 1.493 [1.438,1.550]. This factor is exp⁡((log⁡rAB‾−log⁡rBA‾)/2)\exp((\overline{\log r_{AB}}-\overline{\log r_{BA}})/2)exp((logrAB​​−logrBA​​)/2); the full AB-conditioned / BA-conditioned ratio is its square, about 2.229. The overall AA ratio partly cancels that order effect; it does not make the order effect disappear. CUDA event durations include gaps caused by the surrounding host and allocation work, and the laptop’s runtime conditions can depend on its recent work. Those are reasons to test the context, not measured explanations for the effect.

The main schedule includes nine different pairs, and each model appears in a different mixture of those pairs. Averaging every time belonging to a model would therefore mix different contexts and can even disagree substantially with a direct paired contrast. The table and figures use only the specified A/B pair. A separate diagnostic below changes the surrounding schedule and segment length while retaining the same executable.

It does not isolate cache behavior, host submission, allocation, power/DVFS or a single synchronization operation. Independent process starts alone do not make the laptop’s recent history interchangeable, and neither a failed calibration nor a wide interval is evidence of equal kernel performance.

Moving scratch ownership outside the call

The workspace control compares the original interfaces with caller-owned scratch. Validation, workspace preparation and destruction remain outside the timed segments. Normalized addressed SASS text is identical for all twelve corresponding base/adapter device kernels. Thus this intervention keeps their kernel instruction sequences fixed, while changing allocation/free policy, scratch lifetime, persistent addresses and associated cache history together.

Conclusion

The three designs implement the same recurrence while assigning state, time and output ownership differently. The long-prefix coverage defect requires a source fix, verified by both exact outputs and noncommuting random transforms. A parallel scan can also win decisively when too few serial chains are available: the calibrated one-chain controls favor the improved implementation at both lengths.

The larger matrix supplies conditional whole-call comparisons, including the calibrated N=32 result. It does not supply a universal intrinsic ranking: the separate context intervention changes ratios substantially and leaves order effects visible. Scratch-management controls and matching kernel instruction text narrow the question further without converting the difference into bare allocation-API time. Source structure explains the choices; measured calibration determines how far their timing conclusions can travel.

Environment and measurement method

  • Historical run: NVIDIA GeForce RTX 5070 Laptop, 8151 MiB, SM 120, driver 610.88. The paired revision retains its own runtime environment and per-process condition records; laptop power state is part of the measured setup.

  • Frozen build: CUDA 13.1 (V13.1.115), Visual Studio 2026 toolset (MSVC 14.51), -O3, -lineinfo, -arch=sm_120 and host /O2. This MSVC version is outside the toolkit’s supported host-compiler range. Locally, -allow-unsupported-compiler alone was followed by a cudafe++ access violation; compilation succeeded after also setting _ALLOW_COMPILER_AND_STL_VERSION_MISMATCH. The successful workaround does not identify the compiler crash’s precise internal cause:

    nvcc -std=c++17 -O3 -lineinfo -arch=sm_120 \
     -allow-unsupported-compiler \
     -D_ALLOW_COMPILER_AND_STL_VERSION_MISMATCH \
     -c selective_scan.cu -o selective_scan.obj

  • Paired timing: CUDA-event and host-wall intervals around four solve calls per segment after six warm-ups. Pilot and formal sessions remain separate; the frozen formal plan records the number of independent starts. Archived historical measurements used thirty calls and three separate-process rounds instead.

  • Reference: an independent CPU double-precision recurrence; finite-value checks and per-element absolute-plus-relative tolerance. Raw errors are retained.

  • Diagnostics: new same-binary Nsight Systems traces verify the two scratch-control call paths, separately from unprofiled timing. The explicit unsupported historical Racecheck audit exits 9 with 1,736 warnings; it is an expected failure, not part of the supported sources’ fourteen passing sanitizer invocations. Ordinary NCU counter permissions were unavailable in the earlier audit. This post makes no new permission request or driver change, and it infers no hardware-stall percentage. The revision’s SASS counts come from the linked source objects via cuobjdump --dump-sass, counting addressed instructions only, with their hashes tied to the final executable.

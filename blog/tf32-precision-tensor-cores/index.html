TF32 on Tensor Cores: Precision Loss and Speed Gain

A SIMT control passed a fixed error budget on independently rounded inputs, while two WMMA kernels failed it on the same input representation. This post follows the difference through conversion, accumulation and measured performance.

On one dynamic-range fixture with a 32×32 output and reduction length K=8192K=8192K=8192, my two WMMA GEMM kernels each exceeded a fixed error budget at 639 of 1024 outputs. A SIMT control fed independently rounded TF32 values passed the same budget. All outputs were finite. The change of input precision therefore did not account for the whole difference: the arithmetic after conversion mattered too.

TF32 keeps FP32 storage and exponent range while reducing each operand to 11 significant binary bits for multiplication. To follow what that reduction changes, this post starts with a dot product whose answer is exactly 1, checks the actual conversion rule, and follows the data into two WMMA implementations with different reuse scopes. Two FP64 references and the rounded-input SIMT control keep input-representation error separate from the following execution path. The performance comparison then asks whether these particular kernels earn the precision trade on an RTX 5070 Laptop (SM120). The numerical budget is a declared experiment criterion, and the results remain conditional on the inputs and implementations tested here.

Fundamentals: 24 bits in storage, 11 bits into the multiply

An FP32 number has 32 bits: 1 sign bit, 8 exponent bits and 23 explicit mantissa bits, plus an implicit leading bit that is not stored, for 24 bits of effective binary precision. TF32 is often described as a 19-bit format: 1 sign bit, 8 exponent bits and 10 explicit mantissa bits, plus the implicit bit, for 11 bits of effective precision. The first thing to separate is storage from computation.

TF32 does not change the storage format. A and B still take four bytes per element, and moving them from global memory to shared memory still costs four bytes each, so nothing is packed into 19 bits to save bandwidth. The change happens directly before the values enter the matrix instruction: the values in registers are rounded to a value that TF32 can represent. So TF32 can change the compute speed, but it does not automatically reduce the transfer bytes of A/B, and a memory-bound kernel will not necessarily become faster after switching to TF32.

The second point is the relationship between rounding spacing and error bounds. In [1,2)[1,2)[1,2), neighboring representable FP32 values are 2−232^{-23}2−23 apart, while TF32 values are 2−102^{-10}2−10 apart. Outside this interval, the spacing scales with the exponent, so 2−102^{-10}2−10 is not an absolute error bound for every TF32 number but the relative resolution within that binade.

A dot product you can do by hand

Bit counts alone do not give much intuition, so the next example uses a dot product that can be computed by hand both before and after rounding. Let A be 1+2−121+2^{-12}1+2−12 and 1, and let B be 1 and −1. All four values are exactly representable in FP32, and the original sum of products is

(1+2−12)⋅1+1⋅(−1)=2−12.(1+2^{-12})\cdot1+1\cdot(-1)=2^{-12}.(1+2−12)⋅1+1⋅(−1)=2−12.

1+2−121+2^{-12}1+2−12 is only a quarter step away from the TF32 value 1 (the step in this interval is 2−102^{-10}2−10), so it rounds to 1, and the difference disappears. If this pair is repeated 4096 times, for a dot product of length 8192, the original result is exactly 1, while the computation with the converted inputs gives exactly 0.

Figure 2: The same input through four implementations.

The measurements match the hand calculation. SIMT FP32 and cuBLAS pedantic FP32 return 1, while both WMMA implementations return 0. The return type is float and the accumulator really is declared as FP32, but the inputs of the multiplication have already lost their bits, and no accumulation precision can recover them.

What this input does is magnify the relative scale of the error. Here ∑k∣akbk∣=8193\sum_k|a_kb_k|=8193∑k​∣ak​bk​∣=8193 while ∣∑kakbk∣=1|\sum_k a_kb_k|=1∣∑k​ak​bk​∣=1, so a perturbation that is tiny relative to every term becomes 8193 times larger relative to the result: this is catastrophic cancellation. Random matrices rarely have this structure, and for exactly this reason ordinary precision tests miss it.

The rounding rule: RNA, not RNE

Reproducing this result requires knowing the exact rounding mode. With Toolkit 13.1 on this machine, wmma::__float_to_tf32 goes through cvt.rna.tf32.f32. RNA means round to nearest, ties away from zero, and this rule differs from the IEEE default RNE (round to nearest, ties to even). 1+2−111+2^{-11}1+2−11 lies exactly halfway between 1 and 1+2−101+2^{-10}1+2−10; RNA chooses 1+2−101+2^{-10}1+2−10, while RNE chooses 1, because the last mantissa bit of 1 is even.

This difference changes the meaning of an “independent reference”. A CPU reference written with RNE produces a set of differences that should not exist (PTX rounding modifiers).

So the conversion receives its own probe instead of relying on a reference implementation. On the CPU side, frexp writes the absolute value as f×2^e with 0.5≤f<1, f×2^11 is rounded to an integer with RNA, and the result is multiplied back by 2^(e-11) and given its sign again. The GPU side simply calls the real intrinsic and exports the bit pattern. The bit-by-bit comparison covers 262144 random normal numbers, 6144 positive and negative midpoints and their FP32 neighbors, and positive and negative zero, 268290 values in total, and there are zero mismatches.

This CPU model covers only the tested normal numbers and zero, so NaN payloads, subnormals and overflow boundaries lie outside what it validates. The appendix contains the code and the scope.

How WMMA divides the work

The numerical results also need to be connected to how the hardware executes the computation. In ordinary SIMT GEMM, each thread holds scalar accumulators and calls fmaf. WMMA divides the work differently: the 32 threads of a warp cooperate on one matrix sub-block. A fragment is an operand or an accumulator spread across the registers of these 32 threads, not a whole matrix stored in each thread. With this picture in mind, the alignment and mapping rules below are much easier to follow.

This post uses the TF32 shape 16×16×8: the A sub-block is 16×8, B is 8×16, and the output and the accumulator are 16×16. These dimensions belong to the whole warp, not to a single thread. The core of the API is only a few steps, without the copy from global to shared memory:

using namespace nvcuda;
wmma::fragment<wmma::matrix_a, 16,16,8,
               wmma::precision::tf32, wmma::row_major> a;
wmma::fragment<wmma::matrix_b, 16,16,8,
               wmma::precision::tf32, wmma::row_major> b;
wmma::fragment<wmma::accumulator, 16,16,8, float> c;
wmma::fill_fragment(c, 0.0f);

// Valid elements in shared have already been converted to TF32; invalid boundary elements are zero-filled.
wmma::load_matrix_sync(a, shared_a, 8);
wmma::load_matrix_sync(b, shared_b, 16);
wmma::mma_sync(c, a, b, c);

These cooperative operations require the whole warp to execute them with consistent arguments. The mapping from fragment elements to matrix coordinates cannot be inferred from the lane numbers, so code that only needs to apply the same conversion to every element should iterate over fragment.x. load_matrix_sync requires a base address aligned to 32 bytes, and for floats the leading dimension must be a multiple of 4 (WMMA API conventions).

Two implementations: warp-private vs. block-shared reuse

The two implementations compare reuse scopes.

In the first implementation, the warp version, each warp computes one 16×16 output, with eight warps per block, and each warp holds private shared regions for A, B and C. K advances eight at a time: the lanes read and convert A/B together, the warp synchronizes, loads the fragments, runs the MMA and moves to the next K chunk. Finally, the fragment is stored back to private shared memory, and the lanes write the valid outputs. The code is in gemm/tensor_gemm.cu.

The advantage of this version is simple data ownership: one warp completes one tile independently, and the boundaries are easy to check. The cost is reuse. Neighboring tiles do not share A/B, so two warps that compute different columns of the same rows each load the A sub-block themselves. K=1024 takes 128 K chunks, and the repeated loading, conversion and synchronization grow linearly with this count.

The second implementation, the block-tiled version in gemm/tensor_gemm_op.cu, enlarges the output of each block to 64×64 with BK=32 and four warps in a 2×2 layout, each responsible for 32×32. A warp holds four 16×16 accumulator fragments and, in each k step, fetches two A fragments and two B fragments for four combinations. The whole block loads A/B together, and two shared slots let the next K chunk be copied asynchronously.

This version is still tiled reuse for matrix multiplication, but the scalar outer product between threads is replaced by a cooperative MMA of the warp. The inputs are converted to TF32 element by element when they enter the fragment, legally aligned global pieces go through cp.async, and the boundaries are filled element by element. Both versions apply the same conversion rule to the same original values.

Wider reuse costs more on-chip resources, and the second version also keeps a shared region for the output. So no speed difference can be credited to cp.async alone, because the tiling, the thread count, the loop step and the reuse scope all change together between the two versions.

Both versions share the same interface: contiguous row-major A[M,K], B[K,N] and C[M,N], with K=0 writing zeros. The M/N/K tails are filled with zeros when shared memory is loaded, and the valid outputs are written back individually. In the warp version, a warp without a valid tile can exit early, while the lanes of a valid warp still take part in WMMA even if they hold no valid element. The base addresses are aligned to 32 bytes, and wide copies check the 16-byte requirement separately.

Splitting the error in two

If only a single error against the original FP32 task is reported, the bias from the reduced input precision can hide indexing or accumulation bugs. If the comparison uses only the converted inputs, the effect in which 1 becomes 0 disappears completely. To see both effects, two CPU FP64 references are built from the same inputs:

C64=AB(original FP32 values converted to double, then multiplied),C_{64}=AB\quad\text{(original FP32 values converted to double, then multiplied)},C64​=AB(original FP32 values converted to double, then multiplied), Cq=Q(A)Q(B)(independently converted on CPU, then multiplied in double).C_q=Q(A)Q(B)\quad\text{(independently converted on CPU, then multiplied in double)}.Cq​=Q(A)Q(B)(independently converted on CPU, then multiplied in double).

With the actual GPU output C^\widehat CC,

C^−C64=Cq−C64⏟Erep+C^−Cq⏟Eimpl.\widehat C-C_{64} =\underbrace{C_q-C_{64}}_{E_{\rm rep}} +\underbrace{\widehat C-C_q}_{E_{\rm impl}}.C−C64​=Erep​Cq​−C64​​​+Eimpl​C−Cq​​​.

ErepE_{\rm rep}Erep​ is the bias from changing the input representation, and EimplE_{\rm impl}Eimpl​ covers the products, the accumulation, the indexing and other effects of the implementation after the conversion.

Figure 3: Two references, two segments of error.

Calling the second part “implementation error” does not mean that all of it comes from bugs, because the rounding and the accumulation order of the Tensor Cores can legitimately differ from a CPU FP64 loop. The purpose of two references is that the reduced input precision no longer hides this difference. The cancelling input above is the extreme case: Eimpl=0E_{\rm impl}=0Eimpl​=0, while the total error is −1, and all of it lies in the first part.

One detail matters: the identity holds element by element, but the two Frobenius norms do not simply add up, because errors in different directions can partly cancel each other. All relative norms below are divided by the norm of the original C64C_{64}C64​, and the absolute error is kept separately for references that are zero.

SIMT FP32 and cuBLAS pedantic have no Q step and are checked directly against C64C_{64}C64​. The base set covers six input types (random, exactly representable, cancelling, midpoints, dynamic range and all zeros) across 12 shapes, tails and offsets, for 288 checks of the four implementations, and each implementation passes its budget on its own target input.

Long K

Long K forms its own group, because the implementation error accumulates with the reduction length and is hard to expose at short K. The output is fixed at 32×32, and K grows from 8 to 8192, so all 1024 outputs can still receive a full FP64 reference. Four input types, six K values and four implementations give 96 checks, with an elementwise budget fixed in advance:

∣C^ij−Ctarget,ij∣≤10−6+16ϵ32∑k∣Atarget,ikBtarget,kj∣.|\widehat C_{ij}-C_{{\rm target},ij}| \le 10^{-6}+16\epsilon_{32}\sum_k|A_{{\rm target},ik}B_{{\rm target},kj}|.∣Cij​−Ctarget,ij​∣≤10−6+16ϵ32​k∑​∣Atarget,ik​Btarget,kj​∣.

For WMMA the target is Q(A), Q(B), and for the FP32 baselines it is the original inputs. This budget is simply the acceptance threshold that I chose for this experiment and fixed before running it.

On random inputs at K=8192, both WMMA versions agree: the total relative Frobenius error is about 2.60×10−42.60\times10^{-4}2.60×10−4, of which the representation error is about 2.58×10−42.58\times10^{-4}2.58×10−4 and the implementation error about 3.76×10−53.76\times10^{-5}3.76×10−5. The total hardly moves from the level of 10−410^{-4}10−4, while the implementation part has risen from the range of 10−810^{-8}10−8 at short K. A view of only the total error would miss this change completely. On the same inputs, SIMT and cuBLAS have final relative errors of about 1.56×10−61.56\times10^{-6}1.56×10−6 and 2.52×10−72.52\times10^{-7}2.52×10−7.

That coverage does not rule out every implementation bug or identify the cause of the budget failures. The differences also cannot be attributed to one particular rounding step inside the Tensor Core, because PTX does not promise to match the accumulation order, the rounding or the subnormal handling of a CPU FMA loop bit for bit (WMMA precision notes).

Is it on Tensor Cores, and is it faster?

Historical disassembly: confirming the instructions

Before the performance discussion, it must be confirmed that both implementations really use matrix instructions. The PTX compiled with CUDA 13.1 and -arch=sm_120 contains:

cvt.rna.tf32.f32 ...;
wmma.load.a.sync.aligned.row.m16n16k8.tf32 ...;
wmma.load.b.sync.aligned.row.m16n16k8.tf32 ...;
wmma.mma.sync.aligned.row.row.m16n16k8.f32.tf32.tf32.f32 ...;

The types in the last line are the result, A, B and the accumulator input, and they match “TF32 inputs, FP32 accumulation”. In SASS, the operation is HMMA.1684.F32.TF32, and one PTX matrix operation expands into several machine instructions. The warp version has four HMMA sites in its binary and the block version sixteen, together with LDGSTS.E.BYPASS.128, while the SIMT baseline uses FFMA. (These are counts in the binary, not the number of times each instruction runs.)

The input requests drop to one sixteenth and the sectors to one quarter, consistent with a wider sharing scope and a coarser copy granularity. The Tensor pipe’s activity rises from 23.66% to 57.51%, consistent with better instruction supply, while achieved occupancy falls from 79.25% to 16.26%. The activity metric alone does not isolate the reason for that change. These metrics must be read together: many resident warps do not mean that matrix operations are ready to issue, and fewer warps with high reuse can keep the compute units better supplied.

The two percentages have different denominators. The Tensor pipe metric is the active share of the elapsed cycles, not the achieved share of theoretical TFLOPS, while occupancy describes the capacity for resident warps. So subtracting one value from the other does not give the idle cycles (NCU metric definitions).

Block tiling did not remove every bottleneck. The extra shared wavefronts increase, and 49152 B of program shared memory plus the driver usage comes to 50176 B, so the shared-memory block limit is only 2. Resources and the read layout remain relevant to the supply of operands. Conclusion

TF32 keeps FP32 storage and rounds the inputs to 11 bits just before the multiplication. A reference built only from converted inputs hides the representation error, which can dominate cancelling sums. A reference built only from original inputs hides a different question: how much error the following arithmetic adds. The rounded-input SIMT control makes that question concrete—on the dynamic-range long-K fixture it passes where both WMMA implementations fail. This identifies an execution-path difference after conversion, without identifying the internal accumulation rule that causes it. Reuse, resources and shape then decide whether the particular implementation earns a speed gain.

Taken together, choosing TF32 requires at least two conditions at the same time: the task can accept the converted input precision, and the specific kernel actually becomes faster on the target shapes. For the dot product that needed to keep its value of 1, the precision condition already fails; that fixture was not a separate performance benchmark.

TF32 reduces operand precision by 13 bits; the trade is worth it only after checking that speed appears and the task can accept the resulting numerical error.

Conversion model

The conversion reference corresponds to cvt.rna.tf32.f32 in this machine’s CUDA Toolkit 13.1 include/crt/mma.h, following PTX’s round-to-nearest, ties-away-from-zero rule.

The CPU model uses frexp to write the absolute value as f×2^e with 0.5≤f<1, rounds f×2^11 to an integer with ties going to the larger magnitude, then multiplies back by 2^(e-11) and restores the sign, without copying GPU bit encodings:

int exponent;
double frac = frexp(abs(double(x)), &exponent);
double significand = floor(ldexp(frac, 11) + 0.5);
float q = copysign(float(ldexp(significand, exponent - 11)), x);

This is only a numerical model for the finite normal numbers and zeros in this experiment, not a general standard-library implementation for every architecture and TF32 storage form. NaN payloads, infinities, subnormals and overflow boundaries aren’t validated by this model.

A separate GPU conversion kernel then calls only the real intrinsic and exports result bit patterns, compared bit by bit with the CPU model: 262,144 random normal numbers, 6,144 positive and negative midpoints and their neighboring FP32 values, plus positive and negative zero, 268,290 values in total, zero mismatches. Random normal numbers cover binary exponents from -80 to 80. Some raw probes, as FP32 bit patterns:

Historical timing protocol and environment

The base correctness set uses 12 shapes to check indexing and tails: K=0/1/3/7/8/9/31/32/33/64/65/129, plus M/N tail blocks and 0–3 float pointer offsets. Six input types (uniform random, TF32-exact eighths, paired cancellation, midpoint rounding, random mantissas times 2^[-10,10], and all-zero A) across four implementations make 288 checks, all passing their references and fixed budgets.

The performance set uses fixed-seed uniform random inputs over 16×16×8, 128³, 512³, 1024³, 2048³ and 129×131×65 with a one-float pointer offset. Four implementations, six shapes and three rounds make 72 timing tasks, each validated before timing. Large shapes check 257 CPU FP64 positions and use full cuBLAS pedantic FP32 to compute the target at the matching precision: WMMA uses independently Q’d CPU inputs, FP32 uses original inputs. Large matrices didn’t get a full CPU FP64 reference.

Device batch timing uses 20 warm-ups, 10 pilots, about 20 ms per batch, 1–2000 repeats per batch, 30 batches and 3 rounds, with in-round task order shuffled. Inputs are reused, L2 isn’t flushed and the laptop isn’t clock-locked. Figures report the median of three round medians, with error bars showing the range of round medians, not statistical confidence intervals.

The accuracy phase deliberately saves every numerical failure and keeps collecting other implementations, so you can’t declare success just because the outer script exited. Read the per-item status in the CSV and the recorded subprocess exit codes. Only a numerical-check return code of 1 in the accuracy phase continues collection; other exit codes such as CUDA runtime errors still abort the phase. Sanitizers run separately, and this round’s timing started only after those checks completed.

Subnormals, special values, other architectures, locked clocks and real-model quality haven’t been tested. The current results keep the six long-K numerical failures; after improving the accumulation implementation, it must be revalidated under the same budget.

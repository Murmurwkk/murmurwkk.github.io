Where TF32 Loses Precision, and What It Buys Back

TF32 keeps FP32's range but sends 11 bits into the multiply. A dot product you can check by hand, the RNA rounding rule, error split against two FP64 references, and whether two WMMA kernels are faster.

更新于 2026/11/6 · 9 个章节
#CUDA#TF32#Tensor Core#GEMM#numerical precision#performance experiments

TF32 is the format NVIDIA’s Tensor Cores use to multiply FP32 inputs. The usual one-line description is that it keeps FP32’s exponent range and squeezes the mantissa down to 10 bits. Behind that description are two questions that are easy to skip: where in the data flow does the squeezing happen, and how does it relate to storage format and accumulation precision? Skip them, and when a GEMM result differs from an FP64 reference by an order of magnitude, it’s hard to say which stage the error belongs to.

This post separates the stages using two explicit WMMA implementations. First we’ll pin down which bits get rounded away before values reach the matrix instruction, then see what that rounding does to a dot product you can compute by hand, and check the exact rounding rule bit by bit. With that in hand, we’ll look at how WMMA divides work across a warp, compare two implementations with different reuse scopes, and split their error into a representation part and an implementation part. Last comes the question of whether all this actually runs faster. Every GPU experiment ran on an RTX 5070 Laptop (SM120), and the conclusions cover only these two implementations, not every math library with a TF32 option.

Fundamentals: 24 bits in storage, 11 bits into the multiply

An FP32 number is 32 bits: 1 sign, 8 exponent, 23 explicit mantissa bits, plus an implicit leading bit that isn’t stored, for 24 bits of effective binary precision. TF32 is often described as a 19-bit format: 1 sign, 8 exponent, 10 explicit mantissa bits, plus the implicit bit for 11 bits of effective precision. The first thing to separate is storage from compute.

TF32 doesn’t change the storage format. A and B are still four bytes per element, and moving them from global memory to shared memory is still four bytes each. Nothing gets packed into 19 bits to save bandwidth. The change happens right before values enter the matrix instruction: values in registers are rounded to something TF32 can represent. So TF32 can change compute speed, but it doesn’t automatically reduce A/B transfer bytes; a memory-bound kernel won’t necessarily speed up by switching to TF32.

Second, the relationship between rounding spacing and error bounds. In [1,2)[1,2)[1,2), adjacent representable FP32 values are 2−232^{-23}2−23 apart, and TF32 values 2−102^{-10}2−10 apart. Outside that interval the spacing scales with the exponent, so 2−102^{-10}2−10 isn’t an absolute error bound for every TF32 number; it’s the relative resolution within that binade.

A dot product you can do by hand

Bit counts don’t build much intuition, so here’s a dot product that’s hand-computable before and after. Let A be 1+2−121+2^{-12}1+2−12 and 1, and B be 1 and −1. All four are exactly representable in FP32, and the original sum of products is

(1+2−12)⋅1+1⋅(−1)=2−12.(1+2^{-12})\cdot1+1\cdot(-1)=2^{-12}.(1+2−12)⋅1+1⋅(−1)=2−12.

1+2−121+2^{-12}1+2−12 is only a quarter step away from TF32’s representable 1 (the step in this interval is 2−102^{-10}2−10), so it rounds to 1 and the difference vanishes. Repeat this pair 4096 times for a dot product of length 8192: the original result is exactly 1, and computing with the converted inputs gives exactly 0.

Figure 2: The same input through four implementations.

The measurements match the hand calculation. SIMT FP32 and cuBLAS pedantic FP32 return 1; both WMMA implementations return 0. The return type is float and the accumulator really is declared FP32, but the multiply inputs have already lost their bits, and no amount of accumulation precision can get them back.

What this input does is magnify the error’s relative scale. Here ∑k∣akbk∣=8193\sum_k|a_kb_k|=8193∑k​∣ak​bk​∣=8193 while ∣∑kakbk∣=1|\sum_k a_kb_k|=1∣∑k​ak​bk​∣=1, so a perturbation that’s tiny relative to every term is 8193 times larger relative to the result: catastrophic cancellation. Random matrices rarely hit this structure, which is exactly why ordinary precision tests miss it.

The rounding rule: RNA, not RNE

Reproducing that result requires knowing the exact rounding mode. On this machine’s Toolkit 13.1, wmma::__float_to_tf32 goes through cvt.rna.tf32.f32. RNA means round to nearest, ties away from zero. That’s not the same as IEEE’s default RNE (round to nearest, ties to even). 1+2−111+2^{-11}1+2−11 sits exactly halfway between 1 and 1+2−101+2^{-10}1+2−10; RNA picks 1+2−101+2^{-10}1+2−10, while RNE picks 1, because 1’s last mantissa bit is even.

That difference changes what an “independent reference” means. Write the CPU reference with RNE and you’ll get a batch of differences that shouldn’t exist (PTX rounding modifiers).

So the conversion gets its own probe rather than trusting a reference implementation. On the CPU side, frexp writes the absolute value as f×2^e with 0.5≤f<1, f×2^11 is rounded RNA to an integer, then multiplied back by 2^(e-11) with the sign restored. The GPU side just calls the real intrinsic and exports the bit pattern. Comparing bit by bit over 262144 random normal numbers, 6144 positive and negative midpoints and their FP32 neighbors, plus positive and negative zero, 268290 values in total, there are zero mismatches.

This CPU model only covers the tested normal numbers and zero; NaN payloads, subnormals and overflow boundaries are outside what it validates. The code and scope are in the appendix.

How WMMA divides the work

The numerical conclusions have to land on execution. Ordinary SIMT GEMM has each thread hold scalar accumulators and call fmaf. WMMA divides work differently: the 32 threads of a warp cooperate on one matrix sub-block. A fragment is an operand or accumulator spread across those 32 threads’ registers, not a whole matrix stored per thread. Get that backwards and everything later about alignment and mapping goes wrong too.

This post uses the 16×16×8 TF32 shape: A sub-block 16×8, B 8×16, output and accumulator 16×16. Those dimensions belong to the whole warp, not a single thread. The core of the API is just a few steps, with the global→shared copy omitted:

using namespace nvcuda;
wmma::fragment<wmma::matrix_a, 16,16,8,
               wmma::precision::tf32, wmma::row_major> a;
wmma::fragment<wmma::matrix_b, 16,16,8,
               wmma::precision::tf32, wmma::row_major> b;
wmma::fragment<wmma::accumulator, 16,16,8, float> c;
wmma::fill_fragment(c, 0.0f);

// Valid elements in shared have already been converted to TF32; invalid boundary elements are zero-filled.
wmma::load_matrix_sync(a, shared_a, 8);
wmma::load_matrix_sync(b, shared_b, 16);
wmma::mma_sync(c, a, b, c);

These cooperative operations require the whole warp to execute with consistent arguments. The mapping from fragment elements to matrix coordinates can’t be inferred from lane numbers; if you only need to apply the same conversion to every element, iterate over fragment.x. load_matrix_sync requires a 32-byte-aligned base address, and for floats the leading dimension must be a multiple of 4 (WMMA API conventions).

Two implementations: warp-private vs. block-shared reuse

The two implementations compare reuse scope.

The first, the warp version, has each warp compute one 16×16 output, with eight warps per block, each holding private A/B/C shared regions. K advances eight at a time: lanes cooperatively read and convert A/B, the warp synchronizes, loads fragments, runs the MMA, and moves to the next K chunk. Finally the fragment is stored back to private shared memory, and lanes write the valid outputs. The code is in gemm/tensor_gemm.cu.

Its advantage is simple data ownership: one warp completes one tile independently, and boundaries are easy to check. The cost is reuse. Neighboring tiles don’t share A/B, so two warps computing different columns of the same rows each load the A sub-block themselves. K=1024 takes 128 K chunks, and repeated loading, conversion and synchronization grow linearly with that count.

The second, the block-tiled version in gemm/tensor_gemm_op.cu, enlarges block output to 64×64 with BK=32 and four warps in a 2×2 layout, each responsible for 32×32. A warp holds four 16×16 accumulator fragments and, per k step, fetches two A fragments and two B fragments for four combinations. A/B are loaded cooperatively by the whole block, and two shared slots let the next K chunk copy asynchronously.

It’s still tiled reuse for matrix multiplication, with the scalar outer product between threads replaced by warp-cooperative MMA. Inputs are converted to TF32 elementwise on entering the fragment, legally aligned global pieces go through cp.async, and boundaries are filled element by element. Both versions apply the same conversion rule to the same original values.

Wider reuse costs more on-chip resources, and the second version also keeps an output shared region. That sets up an attribution trap: crediting every speed change to cp.async doesn’t hold, because tiling, thread count, loop step and reuse scope all change together between the two, and none was ablated separately here.

Both share the same I/O contract: contiguous row-major A[M,K], B[K,N], C[M,N], with K=0 writing zeros. M/N/K tails are zero-filled when loading shared memory, and valid outputs are written back individually. In the warp version, a warp with no valid tile at all can exit, but lanes in a valid warp that hold no valid global element must still take part in WMMA. Common base addresses are explicitly aligned to 32 bytes, and wide copies separately check the 16-byte requirement. Exact aliasing, arbitrary strides and non-default stream integration weren’t validated.

Splitting the error in two

Report a single error against the original FP32 task, and the bias from reduced input precision can hide indexing or accumulation bugs. Compare only against converted inputs, and the 1-becomes-0 effect above vanishes entirely. To watch both, build two CPU FP64 references from the same inputs:

C64=AB(original FP32 values converted to double, then multiplied),C_{64}=AB\quad\text{(original FP32 values converted to double, then multiplied)},C64​=AB(original FP32 values converted to double, then multiplied), Cq=Q(A)Q(B)(independently converted on CPU, then multiplied in double).C_q=Q(A)Q(B)\quad\text{(independently converted on CPU, then multiplied in double)}.Cq​=Q(A)Q(B)(independently converted on CPU, then multiplied in double).

With the GPU’s actual output C^\widehat CC,

C^−C64=Cq−C64⏟Erep+C^−Cq⏟Eimpl.\widehat C-C_{64} =\underbrace{C_q-C_{64}}_{E_{\rm rep}} +\underbrace{\widehat C-C_q}_{E_{\rm impl}}.C−C64​=Erep​Cq​−C64​​​+Eimpl​C−Cq​​​.

ErepE_{\rm rep}Erep​ is the bias from changing the input representation; EimplE_{\rm impl}Eimpl​ covers products, accumulation, indexing and implementation effects after conversion.

Figure 3: Two references, two segments of error.

Calling the second segment “implementation error” doesn’t mean it’s all bugs: Tensor Core rounding and accumulation order can legitimately differ from a CPU FP64 loop. The point of two references is that the difference is no longer masked by reduced input precision. The cancelling input above is the extreme case: Eimpl=0E_{\rm impl}=0Eimpl​=0 while the total error is −1, all of it in the first segment.

One easy mistake: the matrix identity holds elementwise, but the two Frobenius norms can’t simply be added, because errors in different directions can partly cancel. All relative norms below are divided by the norm of the original C64C_{64}C64​, with absolute error kept separately for zero references.

SIMT FP32 and cuBLAS pedantic have no Q step and are checked directly against C64C_{64}C64​. The base set covers six input types (random, exactly representable, cancelling, midpoints, dynamic range and all zeros) across 12 shapes, tails and offsets, 288 checks for the four implementations, each passing its budget on its own target input.

Long K

Long K gets its own group, because implementation error accumulates with reduction length and is hard to expose at short K. Output is fixed at 32×32 and K grows from 8 to 8192, so all 1024 outputs can still get a full FP64 reference. Four input types, six K values and four implementations make 96 checks, with an elementwise budget fixed in advance:

∣C^ij−Ctarget,ij∣≤10−6+16ϵ32∑k∣Atarget,ikBtarget,kj∣.|\widehat C_{ij}-C_{{\rm target},ij}| \le 10^{-6}+16\epsilon_{32}\sum_k|A_{{\rm target},ik}B_{{\rm target},kj}|.∣Cij​−Ctarget,ij​∣≤10−6+16ϵ32​k∑​∣Atarget,ik​Btarget,kj​∣.

For WMMA the target is Q(A), Q(B); for the FP32 baselines it’s the original inputs. This is this experiment’s acceptance threshold, not a CUDA error theorem for arbitrary K, and not a tolerance loosened to absorb TF32 representation error.

Figure 4: The two error segments as K grows.

On random inputs at K=8192, both WMMA versions agree: total relative Frobenius error about 2.60×10−42.60\times10^{-4}2.60×10−4, of which representation error is about 2.58×10−42.58\times10^{-4}2.58×10−4 and implementation error about 3.76×10−53.76\times10^{-5}3.76×10−5. The total barely moves around 10−410^{-4}10−4, while the implementation segment has climbed from the 10−810^{-8}10−8 range at short K. Watching only the total would miss that change entirely. On the same inputs, SIMT and cuBLAS have final relative errors of about 1.56×10−61.56\times10^{-6}1.56×10−6 and 2.52×10−72.52\times10^{-7}2.52×10−7.

The dynamic-range inputs, random mantissas times different binary exponents, produce six failures: both WMMA versions exceed the budget at K=512, 2048 and 8192.

So the 96 checks are 90 passes and 6 failures, and the threshold wasn’t adjusted to move those six out of the failure set. Two caveats on reading the table. Maximum absolute error only means something relative to data scale. And overall relative error can’t substitute for the elementwise constraint: at K=8192, implementation relative error overall is only about 3.59×10−53.59\times10^{-5}3.59×10−5, yet 609 outputs fail the budget.

memcheck, racecheck and synccheck on both the main set and long K report no memory or shared race errors, and the numerical checks still fail. No illegal access doesn’t mean the precision is met. These differences also can’t be uniquely attributed to some particular rounding inside the Tensor Core; PTX doesn’t specify accumulation order, rounding or subnormal handling to match any CPU FMA loop bit for bit (WMMA precision notes).

Is it on Tensor Cores, and is it faster?

Confirming the instructions

Before discussing performance, confirm both implementations really use matrix instructions. PTX compiled with CUDA 13.1, -arch=sm_120, contains:

cvt.rna.tf32.f32 ...;
wmma.load.a.sync.aligned.row.m16n16k8.tf32 ...;
wmma.load.b.sync.aligned.row.m16n16k8.tf32 ...;
wmma.mma.sync.aligned.row.row.m16n16k8.f32.tf32.tf32.f32 ...;

The types on the last line are result, A, B and accumulator input, matching “TF32 inputs, FP32 accumulation.” In SASS it’s HMMA.1684.F32.TF32, with one PTX matrix op expanding into several machine instructions. The warp version has four static HMMA sites, the block version sixteen, along with LDGSTS.E.BYPASS.128; the SIMT baseline uses FFMA.

Two cautions: static site counts aren’t dynamic execution counts, and SM120’s HMMA can’t use Hopper’s WGMMA or SM100’s peak as its denominator.

Input requests drop to a sixteenth and sectors to a quarter, consistent with a wider sharing scope and coarser copy granularity. Tensor pipe activity rises from 23.66% to 57.51% as the compute pipeline gets a steadier instruction stream, while achieved occupancy falls from 79.25% to 16.26%. Read them together: lots of resident warps doesn’t mean there are matrix ops to issue, and fewer warps with high reuse can keep the compute units better fed.

The two percentages have different denominators. The Tensor pipe metric is the active share of elapsed cycles, not achieved theoretical TFLOPS; occupancy describes resident warp capacity. Subtracting one from the other doesn’t give idle cycles (NCU metric definitions).

Block tiling didn’t remove every bottleneck. Extra shared wavefronts go up, and 49152 B of program shared plus driver usage comes to 50176 B, leaving a shared block limit of just 2. Resources and read layout still constrain operand supply. Actual time has to account for all of those costs:

The block version beats the warp version at all four sizes, so widening the reuse scope works. Against SIMT, though, it’s still about 13.7% and 13.3% slower at 1024³ and 2048³. On those shapes, this TF32 implementation changes input precision and doesn’t buy device speed in return. The cuBLAS run here doesn’t enable fast TF32, and there’s no comparison against a same-precision library baseline using multi-pass TF32 decomposition, so this can’t be read as the Tensor Core ceiling.

At 128³ it’s the opposite: the block version takes 0.01212 ms, faster than both FP32 baselines. Shrink to 16×16×8 and the warp version takes about 8.34 µs against the block version’s 9.05 µs, so the larger cooperative organization loses its edge. Choosing an implementation has to be done per shape; “it uses Tensor Cores” isn’t enough to decide.

Device timing selects the kernel in advance and keeps the in-kernel TF32 conversion, excluding the public entry’s repeated device-property queries. Running the public interface once with host upload, compute, download and synchronization, 1024³ waits are SIMT 1.663 ms, warp 2.044 ms, block 1.548 ms and cuBLAS 1.487 ms, excluding allocation, compilation and handle creation.

Figure 7: Device timing vs. host round trip.

All four paths still transfer floats. Single host round trips vary a lot, and a ranking swap between block and SIMT there isn’t enough to overturn the device benchmark. Which number matters depends on where the data lives: if matrices stay on the GPU, look at device time; if the application transfers from the host every time, count total waiting along the real call chain.

What this does and doesn’t show

  • It shows that TF32 rounding happens on the way into the matrix instruction, not in storage, and that this machine’s conversion is RNA (268290 values, zero mismatches against an independent model).
  • It shows, with a hand-computable input, that TF32 can turn an exact result of 1 into 0 with an FP32 accumulator, entirely through representation error.
  • It shows that implementation error grows with K and fails a fixed elementwise budget on dynamic-range inputs at K≥512, kept as six failures.
  • It shows that block-level reuse raises Tensor pipe activity and beats warp-private tiles, yet still loses to SIMT FP32 at 1024³ and 2048³ on this GPU.
  • It doesn’t test subnormals, special values, other architectures, locked clocks, fast-TF32 cuBLAS or model-level quality; the accumulation path still needs improvement and revalidation under the same budget.

Conclusion

Let’s recap. TF32 keeps FP32 storage and rounds inputs to 11 bits just before the multiply, so its error is mostly representation error, invisible unless you compare against a reference built from the converted inputs, and devastating on cancelling sums. Splitting error into representation and implementation parts exposes what a single total hides: implementation error that grows with K. And using Tensor Cores doesn’t by itself make a kernel faster; reuse, resources and shape decide that.

Putting it together, choosing TF32 requires at least two conditions at once: the task can accept the converted input precision, and the specific kernel actually gains on the target shapes. For the dot product that needed to keep its 1, neither condition held.

TF32 is a deal: 13 bits of every input in exchange for speed. It’s only worth taking if you check that you actually got the speed and could afford the bits.

Conversion model

The conversion reference corresponds to cvt.rna.tf32.f32 in this machine’s CUDA Toolkit 13.1 include/crt/mma.h, following PTX’s round-to-nearest, ties-away-from-zero rule.

The CPU model uses frexp to write the absolute value as f×2^e with 0.5≤f<1, rounds f×2^11 to an integer with ties going to the larger magnitude, then multiplies back by 2^(e-11) and restores the sign, without copying GPU bit encodings:

int exponent;
double frac = frexp(abs(double(x)), &exponent);
double significand = floor(ldexp(frac, 11) + 0.5);
float q = copysign(float(ldexp(significand, exponent - 11)), x);

This is only a numerical model for the finite normal numbers and zeros in this experiment, not a general standard-library implementation for every architecture and TF32 storage form. NaN payloads, infinities, subnormals and overflow boundaries aren’t validated by this model.

A separate GPU conversion kernel then calls only the real intrinsic and exports result bit patterns, compared bit by bit with the CPU model: 262,144 random normal numbers, 6,144 positive and negative midpoints and their neighboring FP32 values, plus positive and negative zero, 268,290 values in total, zero mismatches. Random normal numbers cover binary exponents from -80 to 80. Some raw probes, as FP32 bit patterns:

Timing protocol and environment

The base correctness set uses 12 shapes to check indexing and tails: K=0/1/3/7/8/9/31/32/33/64/65/129, plus M/N tail blocks and 0–3 float pointer offsets. Six input types (uniform random, TF32-exact eighths, paired cancellation, midpoint rounding, random mantissas times 2^[-10,10], and all-zero A) across four implementations make 288 checks, all passing their references and fixed budgets.

The performance set uses fixed-seed uniform random inputs over 16×16×8, 128³, 512³, 1024³, 2048³ and 129×131×65 with a one-float pointer offset. Four implementations, six shapes and three rounds make 72 timing tasks, each validated before timing. Large shapes check 257 CPU FP64 positions and use full cuBLAS pedantic FP32 to compute the target at the matching precision: WMMA uses independently Q’d CPU inputs, FP32 uses original inputs. Large matrices didn’t get a full CPU FP64 reference.

Device batch timing uses 20 warm-ups, 10 pilots, about 20 ms per batch, 1–2000 repeats per batch, 30 batches and 3 rounds, with in-round task order shuffled. Inputs are reused, L2 isn’t flushed and the laptop isn’t clock-locked. Figures report the median of three round medians, with error bars showing the range of round medians, not statistical confidence intervals.

Device timing selects the WMMA kernel in advance; end-to-end timing keeps the public launch’s device-property query. Both include the in-kernel TF32 conversion.

Test device: RTX 5070 Laptop/SM120, about 8 GB, display driver 610.88, built with Toolkit 13.1.115 and MSVC 2022. Environment queries report runtime API 13.3, driver API 13.3 and compile headers 13.1; see the Windows CUDA 13 runtime versioning notes for field meanings. TF32 and the two previous GEMM posts are separate measurement batches, and absolute times aren’t aggregated together.
